# Архитектура

## Главная идея

Формат документа отделён от логики обезличивания **одной абстракцией** — плоским
списком сегментов с якорями. Парсер знает про PDF/DOCX/XLSX, всё остальное — нет.

```
 extract ─► detect ─► profile ─► judge ─┬─(есть вопросы)─► ask_human ─┐
 (парсер)   (3 слоя)  (субъекты)        │                             │
                                        └────────(нет)────────────────┤
                                                                      ▼
                                                                    plan
                                                                      │
                                       ┌──────────────────────────────┤
                                       ▼              ▼               ▼
                              масked_black.*  masked_highlight.*   report
```

Весь движок — этот граф. Узлы держат логику, состояние течёт через `State`,
чекпойнтер хранит его между шагами. `interrupt()` на уточняющих вопросах даёт
паузу, переживающую перезапуск процесса: веб-интерфейс может спросить человека
и вернуться через час.

Сегмент — это кусок текста плюс якорь, по которому его можно найти обратно
в исходном файле. Якорь у каждого формата свой, наружу не протекает.

| Формат | Якорь | Подсветка |
|---|---|---|
| DOCX | `("body", para_idx)` или `("table", tbl_idx, row, col, para)` + `Entity.start/end` | `run.font.highlight_color = YELLOW` |
| XLSX | `(sheet, cell, char_range)` | `PatternFill` + комментарий с типом |
| PDF (текстовый) | `(page, char_start, char_end)` + `Entity.start/end` | `add_redact_annot(fill=…)` + вставка маркера |
| PDF (скан) | `(page, bbox)` от OCR | тот же redact поверх изображения |

Номер run'а в якорь не входит намеренно: сущность может пересекать границу
run'ов («ИНН 36» + «62103003» — обычное дело после правок в Word), и одним
индексом она не адресуется. Рендер получает по якорю абзац и сам находит
покрывающие run'ы по смещениям через `docx_ingest.iter_runs()`, который
обходит и runs внутри гиперссылок.

Симметрично для PDF (`docs/plans/T2.2.1-pdf-defects.md`, шаги 8–9):
сегмент — блок `get_text("rawdict")`, а не строка, якорь — символьный
диапазон в тексте страницы, который строит один общий строитель
`page_chars(page)` (`ingest/pdf_ingest.py`) для ingest'а и рендера сразу.
Рендер локализует замену по срезу символьных боксов
(`anchor.char_start + entity.start` … `+ entity.end`), а не повторным
поиском строки по странице (`page.search_for`): поиск не различает
несколько одинаковых вхождений на странице и вставлял маркер в каждое
найденное совпадение, а не в одно заменённое. Не влезающий в узкое поле
маркер не роняет рендер — лестница отступления (полный маркер → короткая
метка типа из `mask/labels.py` → без текста, план T2.2.1, пачка 5)
деградирует, а не падает; каждый спуск виден в `report["render_degradations"]`.

## Агенты

Мультиагентность здесь — про разделение ответственности и разные источники
истины, а не про количество вызовов LLM. Каждый агент — класс с одним методом
и явным входом/выходом, оркестратор — обычный последовательный пайплайн.

| Агент | Отвечает за | Чем работает |
|---|---|---|
| **IngestAgent** | файл → `Document`, сохранение структуры, OCR для сканов | python-docx, openpyxl, PyMuPDF, tesseract |
| **DetectAgent** | найти сущности | 3 слоя, см. ниже |
| **ProfileAgent** | сгруппировать сущности в субъектов, определить роли | детерминированные блоки и ключи + LLM-уточнение всей пачки |
| **JudgeAgent** | оценить уверенность, собрать вопросы человеку | пороги + LLM на профиль целиком |
| **PlanAgent** | сущность → маркер, разрешение пересечений, согласованность | детерминированный |
| **ValidateAgent** | полнота, проверка утечек | повторный прогон детекторов по результату |
| **RenderAgent** | два документа из одного плана | форматные адаптеры, стиль — параметр |
| **ReportAgent** | перечень замен | JSON / XLSX / HTML |

## Три слоя детекции — и почему именно так

1. **Правила с контрольными суммами** (`detect/rules.py`), сборка адреса
   (`detect/address.py`) и календарные даты (`detect/dates.py` — 5 форматов
   плюс триггеры «дата рождения», ISO-ключ согласованности). ИНН, ОГРН,
   СНИЛС, расчётный счёт, БИК, КПП, паспорт, email, телефон проверяются
   контрольной цифрой; адрес собирается из индекса и словаря маркеров;
   даты — через `datetime.date`-валидацию (31 февраля отбрасывается сразу).
   У большинства реквизитов есть контрольная цифра — значит precision ≈ 1.0
   бесплатно и без модели. Это фундамент, а не «временное решение до
   подключения LLM».
2. **Локальный NER** (`detect/ner.py`, Natasha). ORG / PER дают названия
   организаций и ФИО. LOC не создаёт сущность и не задаёт границы адреса: это
   только дополнительный сигнал уверенности для частичного адреса. Офлайн,
   быстро, без GPU.
3. **LLM-арбитр** (`detect/llm_arbiter.py`). Только там, где первые два слоя
   не справляются: роли сторон, редкие формулировки, разрешение конфликтов,
   контекстные суммы. Вызывается пачкой на весь документ, не по одной сущности.

Слой знает свою `confidence` и пишет её в `Entity.source`. Отчёт показывает,
чем найдено — это то, что валидирует человек.

## Профили: почему не плоский список сущностей

Плоский список сущностей отвечает на вопрос «что замаскировать», но не
отвечает на «чьё это». Профиль — кластер сущностей одного субъекта:
организация вместе со своим ИНН, КПП, счётом, адресом и подписантом.

Даёт три вещи, которых у плоского списка нет:

- **Роль — свойство субъекта.** Требование «определить, кто поставщик, а кто
  покупатель» решается один раз на профиль, а не отдельно на каждый реквизит.
- **Читаемый результат.** `[ПОСТАВЩИК-ИНН]` и `[ПОКУПАТЕЛЬ-ДИРЕКТОР]` вместо
  `[ИНН-1]` и `[ФИО-3]`. Обезличенный договор остаётся договором, по которому
  можно работать, — ради этого всё и делается.
- **Дешёвая проверка.** Судья смотрит профиль целиком одним вызовом модели
  вместо пяти по числу реквизитов. При тарификации за запрос это прямая экономия.

Кластеризация сначала структурная, без модели: в договорах реквизиты сторон
идут единым блоком, и близость в этом блоке — сильный сигнал. ИНН тянет за
собой КПП, ОГРН, счёт и адрес из того же блока. Затем LLM получает всю пачку
блоков и может уточнить название роли или присоединить неразрешённый контекст,
но не может удалить сущность, изменить её спан или слить стороны с разными
ИНН/ОГРН. Роли открыты: в профиль попадает именно название из документа,
например «Заказчик» или «Исполнитель», а не значение закрытого перечисления.

## Судья: асимметрия, а не просто порог

Судья не спрашивает человека всегда, когда уверенность низкая. Правило разное
для разных типов, и это осознанный перекос:

| | критичный тип | обычный тип |
|---|---|---|
| уверенность высокая | маскируем молча | маскируем молча |
| уверенность низкая | **маскируем молча, помечаем в отчёте** | задаём вопрос |

Пропущенный ИНН — утечка, лишняя маска — косметика. Поэтому про критичное
не спрашивают: спрашивают только там, где ошибка обратима. Вопросы копятся
и задаются одной пачкой в одном прерывании — иначе демо превращается в допрос.

## Человек в цикле: ref-центричная модель решений

Судья решает по сущности; человек в T1.5.1 добавляет ещё два уровня выбора —
по типу («маскировать все телефоны?») и по профилю («маскировать реквизиты
Покупателя?»). Единица решения — **ссылка `ref`** (`E1..En` из детекции,
`C1..Cn` — кандидаты LLM, `H1..Hn` зарезервировано под будущую ручную
разметку), а не тип и не профиль: групповой ответ — это способ задать много
решений по ссылкам разом, а не самостоятельная сущность состояния. Так
будущий выбор «отметить вот этот конкретный фрагмент как PII» добавляет
только новый источник решений по тем же `ref`, не трогая ни формат вопроса,
ни формат ответа, ни отчёт.

Конфликты разрешаются фиксированным приоритетом `DECISION_PRECEDENCE`
(`model.py`), от самого частного к самому общему:

| Приоритет | Источник | Что это | Может дать |
|---|---|---|---|
| 0 | `critical_guard` | инвариант `CRITICAL_TYPES` без двойного подтверждения | только `mask` |
| 1 | `entity` | персональный ответ на вопрос судьи (`Q*`) | `mask` / `keep` |
| 2 | `profile` | ответ на `PROFILE-*` | `mask` / `keep` |
| 3 | `type` | ответ на `TYPE-*` | `mask` / `keep` |
| 4 | `judge` | вердикт судьи по уверенности | только `mask` |
| 5 | `default` | молчаливое «маскировать» | только `mask` |

Персональное решение по сущности сильнее решения по её профилю, решение по
профилю сильнее решения по её типу — иначе групповая галочка обесценивала бы
точечный выбор человека. Профиль частнее типа: он адресует конкретное
подмножество ссылок документа, тип — весь класс целиком. На практике это
значит, что групповой ответ на `TYPE-*` побеждает только для ссылок без
известного профиля (`PROFILE-UNASSIGNED` или кандидаты LLM вне профилей) —
любая сущность внутри документа с профилированием почти всегда решается на
уровне `profile`, а не `type`.

**Критичный тип снимается только двойным подтверждением.** Прямой запрет
снятия отпал бы с направлением «максимум контроля» и сделал бы выбор по
профилю наполовину фиктивным, поэтому решение — вариант A: снятие маски с
`CRITICAL_TYPES` возможно, но требует одновременно флага `--unmask-critical`
и осознанного варианта ответа `«оставить (осознанное решение)»` (не обычного
«оставить» — тем самым случайный клик не превращается в утечку). Без обоих
условий сразу `PolicyAgent.apply` добавляет решение уровня `critical_guard` с
самым высоким приоритетом, и оно побеждает независимо от того, что ответили
на `TYPE-*`/`PROFILE-*`. У профиля критичность не всё-или-ничего: обычное
«оставить» на профиль с критичными и некритичными реквизитами снимает маску
только с некритичной части, критичные остаются под гвардией. Каждое снятие
уходит в `decisions.critical_unmasked` отчёта, в `limitations` и красным
баннером в HTML; `masker.eval --gate` держит порог `critical_unmasked == 0`
для неинтерактивного прогона.

**Контракт паузы.** `thread_id` — детерминированная строка,
`sha256(RUN_SCHEMA_VERSION | sha256(файла) | канонизированные опции)[:16]`:
один и тот же файл с теми же опциями отбора PII всегда даёт один и тот же
тред, поэтому повторный `--ask` не пересчитывает детекцию и LLM — вопросы
читаются через `get_state`, узлы не выполняются заново. Значение
`interrupt()` — единый JSON-конверт (`schema_version`, `document`,
`questions[]`) с одним общим форматом для вопросов по типу, по профилю и по
конкретной сущности; будущий вид вопроса (`kind: "pii"`) добавляется без
изменения контракта. Значение возобновления — конверт `{"schema_version",
"answers"}`, а не голый словарь: экспериментально подтверждено (langgraph
1.2.11), что `Command(resume={})` с пустым словарём трактуется как
отсутствие значения, и узел просто ставится на паузу заново. Сервис
`src/masker/run.py` (`start_run`/`resume_run`/`read_questions`) — единственный
провод между графом и вызывающим; чекпойнтер передаётся снаружи фабрикой,
поэтому переезд CLI → веб меняет только вызывающего и чекпойнтер, а не
логику узлов (требование заказчика №6).

## Три артефакта из одного плана

| Артефакт | Кому | Отличие |
|---|---|---|
| `masked_black.*` | контрагенту наружу | чёрная заливка, маркер белым |
| `masked_highlight.*` | своему юристу на проверку | жёлтая подсветка, маркер виден |
| `report.html` / `.json` / `.xlsx` | в аудит | что, где, чем найдено, уверенность |

Оба документа собираются одним `RenderAgent` из одного `MaskPlan`, стиль —
параметр `MaskStyle`. В обоих исходный текст физически удалён: разница
только визуальная.

## Слой LLM (требование заказчика №6)

```python
class LLMProvider(Protocol):
    def complete(self, messages: list[Message], *, schema: type[T] | None) -> T | str: ...
```

Реализации: `GigaChatProvider`, `OpenAICompatProvider` (ollama/llama.cpp/vLLM),
`FakeProvider` (тесты, детерминированный). Выбор — через `config.yaml`,
переменную `MASKER_LLM=gigachat|local|fake`. Смена модели не трогает ни один
файл вне `src/masker/llm/`. Это проверяется тестом: `test_no_llm_imports_outside_layer`.

## Отчёт

Одна строка на замену: `тип | исходное значение | маркер | где (лист/стр/абзац) |
кем найдено | уверенность`. Плюс сводка: сколько найдено по типам, что вызвало
уточняющие вопросы, время обработки.

## Что делает решение «крутым» на защите

- Текст из PDF действительно **удалён**, а не закрашен — доказывается
  `pdftotext` на выходном файле прямо на сцене.
- Проверка утечек побайтово по всему контейнеру, включая метаданные.
- Работает офлайн: выдёргиваем сеть — всё, кроме LLM-арбитра, продолжает работать.
- Цифры вместо рассказа: `make eval` печатает precision/recall/F1 по типам.
