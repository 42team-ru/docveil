# Задачи

Порядок значим: каждая следующая опирается на контракты предыдущей.
Одна задача — одна сессия агента, контекст между задачами чистить.
Задачи из одного блока (T2.x, T3.x) отдавать **одним запросом пачкой** —
тариф шлюза за запрос, а не за токены.

Формат приёмки везде один: `make gate` = 0 плюс названный ниже конкретный факт.

## Блок 1. Вертикальный срез на DOCX (самое важное)

Цель блока — к концу дня 1 иметь **работающий сквозной путь** на одном формате.
Не начинать PDF и XLSX, пока DOCX не проходит целиком.

### T1.1 — IngestAgent для DOCX (основной текст)
Разобрать `.docx` в `Document`: сегмент — непустой абзац тела документа.
`Segment.text` посимвольно равен `paragraph.text`, включая видимый текст
гиперссылок; никакой нормализации — на этих смещениях работает рендер.
Якорь — `("body", para_idx)`, где `para_idx` — физический индекс абзаца
в `doc.paragraphs`; `Segment.order` — плотная нумерация 0..N-1 по порядку
чтения. Номер run'а в якорь не входит: сущность может пересекать границу
run'ов, поэтому рендер вычисляет их сам по `Entity.start/end` и
`docx_ingest.iter_runs()`. Метаданные (`core_properties`) сложить в `Document.meta`.

Вне скоупа: таблицы (T1.11), колонтитулы и сноски (T1.12).

**Приёмка:** на `fixtures/labeled/contract_01.docx` число сегментов равно числу
непустых абзацев тела (17), `[s.order for s in doc.segments] == list(range(17))`;
`doc.text()` содержит «ИНН 3662103003» и не содержит текста ячеек таблицы
(«Резистор МЛТ-0,25»); для каждого сегмента `Segment.text` посимвольно равен
`paragraph.text` и склейке `iter_runs(paragraph)`; `meta["author"] ==
"Петрова Мария Сергеевна"`, пустые свойства в `meta` не попадают;
два прогона `ingest_docx` дают идентичный список `(order, locator, text)`,
а входной файл после разбора не меняется побайтово.

### T1.2 — DetectAgent, слой правил
Регулярки на все типы из `EntityType`, для ИНН/ОГРН/СНИЛС/счёта/БИК —
обязательная проверка контрольной суммы из `checksums.py`. Счёт проверять
в паре с БИК, найденным рядом (в том же сегменте или соседнем).

**Приёмка:** `make eval` печатает по каждому критичному типу recall = 1.0
и precision ≥ 0.95 на размеченном корпусе.

Уточнение по `checksums.py` (найдено на реальном PDF-корпусе,
`docs/plans/T2.2.1-pdf-defects.md`, шаг 4, Д8): у БИК и у ключа проверки
банковского счёта **нет** контрольной суммы — это форматные правила
(БИК — первые два разряда `01`/`04`, признак учреждения Банка России;
ключ счёта — один из двух префиксов по разрядам БИК, а не выбор по
префиксу самого счёта). Выдумывать контрольную сумму для них — ошибка.
КПП тоже без контрольной суммы и поэтому выпускается только по контексту:
метка «КПП» в окне слева либо валидный ИНН в том же сегменте — без этого
любое девятизначное число в тексте (табличная величина, обрезок телефона)
становится ложным КПП.

### T1.3 — DetectAgent, слой NER
Natasha: ORG / PER → `ORG_NAME` / `PERSON`, `source=NER`. Метка LOC наружу
не выпускается: измерено, что на «Адрес: 394018, г. Воронеж, ул. Ленина,
д. 5, оф. 12» Natasha возвращает единственный спан `LOC 'Воронеж'`.
Замаскированный город при живом «ул. Ленина, д. 5» — видимость обезличивания,
а не обезличивание. Адрес целиком вынесен в T1.14.

Прогон посегментный, не по `Document.text()`: спаны Natasha пересекают `\n`,
а смещения `Entity` локальны к сегменту по контракту `model.py`.
Модель грузить один раз в процессе, не на каждый документ.

Слияние с правилами асимметрично. Правило точно по построению и не режется.
Модельный спан при пересечении **режется**, а не выбрасывается: на реальном
выводе Natasha `ORG 'ООО "Ромашка" (ИНН 3662103003'` выброс всего спана
оставил бы название организации в документе. Из модельного спана вычитаются
интервалы принятых сущностей, остатки обрезаются по краям и отбрасываются,
если в них нет букв или остались только организационно-правовые формы.

Границы спанов Natasha систематически не совпадают с разметкой: на
«Общество с ограниченной ответственностью «Ромашка»» модель возвращает только
«Ромашка», при том что в `fixtures/labeled/` размечена полная форма. Расширение
спана влево по словарю форм — часть задачи, а словарь — данные, не код.

**Приёмка:** тест на пересечение — «ИНН 3662103003» внутри спана организации
даёт **две** сущности: `INN` и `ORG_NAME` «ООО "Ромашка"», а не одну.
Тест на расширение — «АО «Триема»» и «Акционерное общество «Триема»» дают
одинаковый `normalized`. Тест на LOC — спан LOC наружу не выходит.
Тесты слоя гоняются на фейковом теггере; тест на настоящей Natasha помечен
маркером `models` (не `e2e`: модели лежат в пакете, сеть не нужна).

План — `docs/plans/T1.3-detect-ner.md`.

### T1.4 — ProfileAgent
Готово. Сущности сначала группируются детерминированно по блокам, реквизитам и
явным ролевым формулировкам документа. Затем LLM получает все чанки пачками по
бюджету объёма, может уточнить открытое название роли и предложить PII-кандидата.
Роли не хардкодятся; опасное изменение состава надёжного профиля отклоняется.

**Приёмка:** на договоре с двумя сторонами получается ровно два профиля;
ИНН, счёт и директор поставщика лежат в одном профиле; каждый элемент профиля
сохраняет свой `Anchor` — по нему человек находит место в документе.

### T1.5 — JudgeAgent
Готово. Вердикты и вопросы сериализуются в `State`; `ask_human` делает одно
переживающее чекпойнтер прерывание для всей пачки.

Уверенность по профилю и по сущности. Вопросы собираются пачкой.
Асимметрия обязательна: тип из `CRITICAL_TYPES` маскируется молча при любой
уверенности и в `questions` не попадает.

**Приёмка:** тест — ИНН с уверенностью 0.3 не порождает вопроса, но попадает
в план; телефон с уверенностью 0.5 порождает вопрос. Вопросов на документ —
одно прерывание, а не N.

### T1.5.1 — Человек в цикле: выбор типов и профилей
Готово. Человек до маскирования решает не только «маскировать ли эту
сущность» (T1.5), но и «маскировать ли весь тип X» и «маскировать ли
реквизиты субъекта Y» — групповые вопросы `TYPE-*`/`PROFILE-*` вдобавок к
`Q*` судьи, всё в одном прерывании. Единица решения — ссылка `ref`
(`E1..En`/`C1..Cn`), а не тип и не профиль: групповые ответы разворачиваются
в решения по ссылкам с фиксированным приоритетом `DECISION_PRECEDENCE`
(`model.py`) — персональное решение по сущности сильнее решения по её
профилю, решение по профилю сильнее решения по её типу, а всё это слабее
молчаливого «маскировать». Критичный тип/профиль (`CRITICAL_TYPES`) снимается
только двойным подтверждением: флаг `--unmask-critical` плюс отдельный
осознанный вариант ответа `«оставить (осознанное решение)»`; без обоих сразу
решение уровня `critical_guard` держит маску независимо от прочих ответов.

Сюда же перенесена сборка `StateGraph`/`compile(checkpointer=SqliteSaver)` из
T1.10 (`src/masker/graph/build.py`) — без неё «человек в цикле» через паузу,
переживающую перезапуск процесса, не собрать. У T1.10 после этого остаётся
только достройка полного набора узлов конвейера, когда он появится (после
T1.7).

Сервис `src/masker/run.py` (`start_run`/`resume_run`/`read_questions`) —
единственный провод между графом и вызывающим; чекпойнтер передаётся снаружи
фабрикой, поэтому переезд CLI → веб меняет только вызывающего и чекпойнтер, а
не логику узлов (требование заказчика №6). CLI: `--ask` (пауза, код 10,
`questions.json`), `--resume THREAD_ID --answers PATH` (код 0/3),
`--fresh`, `--thread-id`, `--state-db`, `--unmask-critical`; без `--ask` и
без `--resume` прогон неинтерактивный и не имеет права зависать — ни `make
demo`, ни `make gate` не трогают эти флаги.

**Приёмка:** `PolicyAgent.apply` разрешает конфликт «персональное против
группового» и «профиль против типа» строго по `DECISION_PRECEDENCE` (тест
падает при любой другой перестановке приоритетов); двойное подтверждение
проверено и для типа, и для профиля отдельно (обычное «оставить» на
критичный профиль снимает маску только с его некритичной части); durable
resume — новый объект графа и новый `SqliteSaver` на том же файле доводят
приостановленный тред до конца; `--ask` дважды подряд даёт побайтово
одинаковый `questions.json`; `masker.eval --gate` держит `critical_unmasked
== 0` для неинтерактивного прогона по корпусу. План —
`docs/plans/T1.5.1-human-in-the-loop.md`.

### T1.6 — PlanAgent
Сущность → маркер. Согласованность по `Entity.key`: одинаковое значение во
всём документе → один маркер с одним номером. Нормализация: «ООО "Ромашка"»,
«ООО «Ромашка»» и «Ромашка» — одна сущность. Фильтр по запрошенным типам.

**Приёмка:** тест — документ, где организация упомянута 5 раз в 3 написаниях,
даёт один маркер; два прогона дают идентичный план (детерминизм).

### T1.7 — RenderAgent для DOCX, оба стиля
Записать замены обратно. Run, попавший под замену, разрезается на три
(до / маска / после). `MaskStyle.HIGHLIGHT` — жёлтая заливка и видимый маркер,
`MaskStyle.BLACK` — чёрная заливка и маркер белым. Стили, нумерация, таблицы
не трогаются. Метаданные документа зачищаются.
Таблицы и колонтитулы на этом шаге не сегментируются (T1.11/T1.12) — значит и не
изменяются; их сохранность проверяется числом таблиц и отсутствием новых частей
в пакете.
Ячейки таблиц рендерятся тем же кодом, что и абзацы тела: после T1.11 у них
есть якорь. Проверка «исходного текста ячейки нет в `word/document.xml` обоих
вариантов» — здесь.

**Приёмка:** оба файла открываются Word'ом без предупреждений; число абзацев
и таблиц совпадает с исходным; в `docProps/core.xml` нет исходного автора;
в **обоих** вариантах исходного текста нет в распакованном XML — чёрная
заливка поверх живого текста не считается обезличиванием.

### T1.8 — ValidateAgent + проверка утечек
Прогнать детекторы повторно по **результату**. Любая сущность запрошенного
типа, найденная в выходном файле, — провал. Отдельно: распаковать выходной
контейнер и поискать исходные строки побайтово во всех его частях.

**Приёмка:** тест намеренно ломает Render (пропускает одну замену) —
Validate обязан вернуть непустой `leaked`. Ворота на этом падают.

### T1.9 — ReportAgent + CLI
`masker <файл> --types inn,person,org_name --out out/`. Отчёт: JSON + XLSX + HTML.
`--types all`. Ненулевой код возврата при непустом `leaked`.

**Приёмка:** `make demo` кладёт в `out/` три артефакта — чёрный вариант,
подсвеченный вариант, отчёт. В отчёте видно, чем найдена каждая сущность
(rule/ner/llm), её уверенность и к какому профилю она относится.

### T1.10 — Сборка графа
Сборка `StateGraph`/`compile(checkpointer=SqliteSaver)`, пауза → ответ →
возобновление после пересоздания объекта графа и тест на детерминизм — уже
сделаны в T1.5.1 (`src/masker/graph/build.py`), поскольку без них «человек в
цикле» не работает. Здесь остаётся только достроить в граф полный набор
узлов конвейера (`plan`/`render`/`validate`/`report`) — они появятся после
T1.6–T1.9, T1.10 лишь подключает их к уже существующей сборке графа.

**Приёмка:** новые узлы подключены в `build_graph`, полный прогон
extract→...→report проходит через граф с чекпойнтером; тест на детерминизм
из T1.5.1 остаётся зелёным на расширенном графе.

### T1.11 — Таблицы DOCX: ingest + подсветка в ячейках
Абзацы ячеек становятся сегментами с якорем `("table", tbl_idx, row, col, para)`.
Обход тела идёт по XML-детям `w:body`, чтобы таблица не уехала в конец и
`Segment.order` совпадал с порядком чтения. Preview режет run внутри ячейки тем
же кодом, что и в теле, — форматная ветка одна.

**Приёмка:** на `fixtures/labeled/contract_01.docx` сегментов 26 — 17 абзацев тела
плюс 9 непустых абзацев ячеек, `Segment.order` плотный, якоря тела не изменились;
на объединённых ячейках сегмент один, а не по числу колонок; число таблиц, строк,
ячеек и колонок сетки после разбора совпадает с исходным; каждое вхождение
критичного значения в таблице найдено (проверяется по числу вхождений, а не по
множеству значений); `document_coverage.tables.processed == true` при
`safe_to_export == false`. Требование «исходного текста ячейки нет в
распакованном `word/document.xml` обоих выходных вариантов» относится к T1.7 —
рендера замен на момент T1.11 не существует.

Порядок: T1.11 → T1.14 → T1.15 → T1.13. Часть приёмки про «оба выходных файла»
относится к T1.7 — рендера замен на момент T1.11 не существует; уточнение,
разбор объединённых ячеек и проверка по вхождениям — в
`docs/plans/T1.11-docx-tables.md`.

### T1.12 — Колонтитулы и сноски DOCX — НЕ РЕАЛИЗОВАНО
Реквизиты часто живут в нижнем колонтитуле, и про них забывают.
Якоря `("header", section_idx, para_idx)`, `("footer", …)`,
`("footnote", footnote_id, para_idx)`.
Обязательное условие: проверять `section.header.is_linked_to_previous` до
обращения к содержимому. В python-docx 1.2 чтение `section.header.paragraphs`
у секции без собственного колонтитула создаёт `word/header1.xml` в пакете —
то есть само чтение меняет структуру документа (проверено экспериментом).
Сноски python-docx не поддерживает: читать `word/footnotes.xml` через `lxml`,
но править — только через объектную модель, не строковыми заменами в XML.

**Приёмка:** на фикстуре с ИНН в нижнем колонтитуле он найден и замаскирован;
`unzip -l` выходного файла не содержит частей, которых не было во входном —
в частности, `header1.xml` не появляется у документа без колонтитулов.

### T1.13 — Реестр типов сущностей и пользовательские типы — НЕ РЕАЛИЗОВАНО

Открывает таксономию типов: пользователь тендера через REST-запрос описывает
словами свой тип («замажь даты отгрузки»), LLM-компилятор превращает описание
в исполнимую спецификацию (`CustomTypeSpec`), которую исполняет один из
executor'ов: literals / regex / regex+context / gliner_label /
gliner_structure / regex+LLM-filter. Открытый в этой задаче реестр
`EntityTypeRegistry` содержит и встроенные типы (из `EntityType`), и
пользовательские (пришедшие в теле запроса). `Entity.type` становится `str`,
валидируется по реестру.

Подключает **GLiNER2** (`fastino/gliner2.5-multi-v1`, Apache-2.0, ~1.1 ГБ)
как ещё один `EntityDetector` через уже готовый protocol в
`src/masker/detect/base.py`. GLiNER работает **только** для пользовательских
типов; для встроенных `person`/`org_name` остаётся Natasha (спайк подтвердил:
Natasha F1 1.000 на person, 0.941 на org_name — GLiNER её не бьёт). Последний
опциональный шаг — combo B: `GlinerBoundaryExtender` post-processor расширяет
границы Natasha-ORG-спанов через GLiNER на окне; включать по замерам на
реальном корпусе (`contract_pdf_02_school.pdf` из хендоффа T2.2.1).

Ask-ветвь компилятора — через LangGraph `interrupt()`, тот же механизм что и
T1.5.1. Preview компиляции — обязательный шаг: скомпилированный спек
прогоняется на 2-3 сегментах текущего документа и показывается пользователю
перед подтверждением. YAML/файловая конфигурация НЕ вводится — источник
`CustomTypeSpec` только API. Область жизни спека — per-request, но структура
готова к будущему сохранению per-user (без переделки узлов графа).

Идёт **после** хендофф-работ T2.2.1/T2.2.2 (уже влиты) и логично после T1.6
(PlanAgent) — фильтр «что искать» применяется в плане, не в детекции;
`ValidateAgent` T1.8 обязан искать утечки по всем типам, включая
пользовательские.

**Приёмка:** пользовательский тип, описанный словами в REST-запросе,
компилируется LLM в `CustomTypeSpec`, находится, маскируется, попадает в
отчёт с человекочитаемым названием и проверяется на утечку. Класс D
(семантическая роль поверх формата — «даты отгрузки vs подписания»)
разделяется через `gliner_structure` executor с F1 ≥ 0.9 (эмпирика спайка:
1.000). `grep -rn "type\.value" src` пуст. Тесты built-in типов не правились.

### T1.14 — ADDRESS: сборка адреса правилом
Вынесено из T1.3 по результатам замера: NER даёт город или улицу, но никогда
не даёт индекс, дом, корпус и офис. Адрес собирается правилом — почтовый
индекс плюс словарь маркеров («г.», «ул.», «д.», «корп.», «стр.», «оф.»,
«наб.», «пр-т»), LOC от Natasha используется как один из сигналов, а не как
готовый спан.

Требование: частичный адрес не выдавать за полный. Если правило собрало
только город, сущность либо не выпускается, либо помечается пониженной
уверенностью и отдаётся судье — но метрика по `address` не имеет права
показывать recall выше фактического.

**Приёмка:** на фикстуре с «394018, г. Воронеж, ул. Ленина, д. 5, оф. 12»
замаскирована вся строка адреса целиком, а не одно слово «Воронеж»;
тест на частичный адрес доказывает, что город без улицы и дома не проходит
как `ADDRESS` полной уверенности.

Идёт после T1.11: адрес в реальном договоре лежит и в теле, и в таблице
реквизитов, поэтому фикстура обязана иметь адрес в ячейке. Здесь же вводится
проводка «детектор → какие типы он умеет», которую переиспользует T1.15.
Место рождения этим правилом не покрывается и честно остаётся в ограничениях
отчёта до T1.16.

План — `docs/plans/T1.14-address-rule.md`.

### T1.15 — Даты: `DATE` и `BIRTH_DATE` — НЕ РЕАЛИЗОВАНО
Детектируются **все** календарные даты: `dd.mm.yyyy`, `dd/mm/yyyy`,
`yyyy-mm-dd`, «10 марта 2025», «„12“ февраля 2025». Незаполненный шаблон
«____» __________ 202__ года датой не считается. Дата с триггером рождения
(«года рождения», «д.р.», «род.») получает отдельный тип `birth_date` — у него
другой маркер, потому что он принадлежит субъекту, а срок оплаты не принадлежит
никому. `date` в `CRITICAL_TYPES` **не входит**: иначе судья молча замаскирует
и дату подписания, и сроки поставки, и договор перестанет быть читаемым. Отбор
«какая дата — персональные данные» — работа судьи и LLM-арбитра (T3.3), а не
детектора.

**Приёмка:** на `fixtures/labeled/contract_07_dates.docx` найдены все пять форм,
шаблон подписи не найден, «15 февраля 1982 года рождения» имеет тип
`birth_date`, а «10 марта 2025» рядом со словом «рождении» — тип `date`;
`normalize` сводит «14.10.1986» и «14 октября 1986» к одному ключу; в корпусе
каждая календарная дата размечена (проверяется независимой аудит-регуляркой в
тесте), precision по `date` ≥ 0.90 при recall ≥ 0.85.

Идёт после T1.14. План — `docs/plans/T1.15-dates.md`.

### T1.16 — Место рождения — НЕ РЕАЛИЗОВАНО
«место рождения: гор. Старый Оскол Белгородской обл.» — персональные данные,
но не адрес: маркер `[ПРОДАВЕЦ-АДРЕС]` на месте рождения делает договор
неверным по смыслу. Механизм тот же, что у `birth_date`: метка-триггер плюс
спан справа. До реализации тип честно перечислен в `limitations` отчёта как
непокрытый.

**Приёмка:** «место рождения: гор. Старый Оскол Белгородской обл.» даёт
сущность `birth_place`, а не `address`; в `fixtures/labeled/` есть случай, где
место рождения и адрес регистрации стоят в одном абзаце и получают разные типы.

### T1.17 — Детектор `contract_number` — РЕАЛИЗОВАНО
`EntityType.CONTRACT_NUMBER` был объявлен в `model.py`, метка маркера и
заголовок вопроса политики — заведены, а детектора не было вовсе:
`detection_coverage.requested_without_detector` держал `contract_number`
на каждом демо (найдено при разборе реального PDF-договора,
`docs/plans/T2.2.1-pdf-defects.md`, Д6). Не реестр типов (T1.13) — тип
встроенный и уже доезжает до отчёта, не хватало только правила.

Правило контекстное, без контрольной суммы: триггер (`договор`, `контракт`,
`протокол`, `извещени`, `закупк`, `реестров`) в окне слева, затем `№` с любым
числом пробелов и тело из цифр/точек/дефисов/слэшей длиной ≥ 5 (сама длина
уже отсекает «гимназия № 144» и «приложение № 1» независимо от триггера).
Сущность — тело номера без «№» (совпадает с уже размеченным корпусом).
Пересечения с ИНН/ОГРН/счётом разрешает существующий `PRIORITY` слоя правил —
`contract_number` в его хвосте. **Не** входит в `CRITICAL_TYPES`: номер
закупки публичен, молчаливая маскировка номера договора делает документ
неопознаваемым.

**Приёмка:** находит `№  32515504247-01` (два пробела) и `№2025.334807`
(без пробела, реальные строки `contract_pdf_02_school.pdf`); не находит
`гимназия № 144`, `приложение № 1`, `ТР ТС 021/2011`; `detection_coverage.requested_without_detector`
в `report.json` больше не содержит `contract_number`. Реализация и тесты —
`src/masker/detect/rules.py`, `tests/masker/detect/test_rules.py`. План —
`docs/plans/T2.2.1-pdf-defects.md`, шаг 10.

## Блок 2. Второй и третий форматы

### T2.1 — XLSX ingest + render
Ячейка = сегмент, якорь `(sheet, cell)`. Формулы не трогать — маскировать
только строковые значения и результат. Подсветка — `PatternFill`, тип замены —
в комментарий к ячейке.

**Приёмка:** книга с формулами после обработки пересчитывается без `#REF!`;
число листов и строк сохранено.

### T2.2 — PDF текстовый ingest + render
PyMuPDF. Решение П1 плана `docs/plans/T2.2.1-pdf-defects.md` (шаг 8):
сегмент = **блок** `get_text("rawdict")` (не span и не строка — строки
внутри блока склеены одним пробелом), якорь — символьный диапазон
`(page, char_start, char_end)` в тексте страницы, который строит один общий
строитель `page_chars(page)` (`ingest/pdf_ingest.py`) для ingest'а и
рендера сразу — двум независимым обходам страницы иначе неоткуда не
разъехаться. Блок дополнительно режется перед строкой-номером пункта
договора (`1.`, `2.3.`), чтобы блок реквизитов на десятки строк не смешивал
профили обеих сторон.

Замена в `render_pdf_redacted` — не поиском (`search_for`), а по срезу
символьных боксов `[anchor.char_start + entity.start, ...+entity.end)`,
`add_redact_annot(rect, fill=...)` + `apply_redactions()`, текст —
`insert_textbox` отдельным вызовом с проверкой настоящего возврата (лестница
отступления — `docs/plans/T2.2.1-pdf-defects.md`, шаг 9 и пачка 5: полный
маркер → короткая метка типа → без текста, вместо падения на узком поле).

**Приёмка:** `pdftotext` на выходном файле не содержит исходных значений —
проверяется тестом, а не глазами. Число страниц сохранено. Сущность,
разорванная переносом строки внутри блока (пример: ФИО подписанта на
границе строк реального PDF), — одна `Entity`, а не две. Маркер (или
короткая метка/пустой прямоугольник, если маркер не влезает) вставлен
**ровно один раз на `Replacement`**, а не по разу на каждое найденное на
странице вхождение строки, — `duplicate_markers == 0` в `masker.eval --gate`.

### T2.3 — Сканированный PDF (OCR)
Если на странице нет текстового слоя — рендер в изображение (300 dpi),
`pytesseract.image_to_data(lang="rus+eng")`, слова с боксами → сегменты.
Маскировка — закраска бокса плюс вписанный маркер. В выход добавить
невидимый текстовый слой с распознанным и уже обезличенным текстом.

**Приёмка:** на `fixtures/labeled/scan_01.pdf` найдены ИНН и ФИО;
в выходном файле их нет ни в тексте, ни визуально.

## Блок 3. LLM-слой и роли

### T3.1 — Абстракция провайдера
`LLMProvider` Protocol, реализации `GigaChat`, `OpenAICompat`, `Fake`.
Выбор через `MASKER_LLM`. Таймаут, ретрай, режим полной работы без сети.

**Приёмка:** тест `test_no_llm_imports_outside_layer` — grep по `src/masker`,
вне `llm/` нет ни одного импорта gigachat/openai. Плюс E2E-тест
`@pytest.mark.e2e`, который ходит в настоящий GigaChat и проверяет, что
переключение `MASKER_LLM=gigachat|local` меняет провайдера, а не логику.

### T3.2 — Роли в ProfileAgent
Приписать профилям Поставщика и Покупателя. Сначала эвристика: преамбула
«именуемое в дальнейшем «Поставщик»», подписи, порядок блоков реквизитов.
LLM — только если эвристика не сошлась, одним запросом на документ.

**Приёмка:** на размеченном корпусе роли определены верно ≥ 90%;
при недостатке данных `ValidateAgent` формирует уточняющий вопрос,
а не угадывает.

### T3.3 — LLM-арбитр в детекции
Один вызов на документ: список спорных фрагментов → решение по каждому.
Схема ответа строгая, невалидный JSON = фрагмент считается сущностью
(в пользу recall).

**Приёмка:** отключение LLM (`MASKER_LLM=fake`) не роняет пайплайн,
метрики по критичным типам не меняются. E2E-тест на живом GigaChat
показывает, что арбитр действительно разрешает спорные фрагменты.
