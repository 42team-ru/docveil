# Spike: GLiNER2 на русском

Эмпирическая проверка перед T1.13: работают ли GLiNER-модели на русском
тендерном тексте по типам, которые не покрыты regex и Natasha; плюс — не
бьёт ли GLiNER Natasha на её же поле (`person`, `org_name`, `location`).

## Что тестировали

Четыре Apache-2.0 модели на 31 фразе (58 спанов, из них 2 негативных):

| id | Модель | API | Энкодер |
|---|---|---|---|
| M1 | `urchade/gliner_multi-v2.1` | GLiNER v1 | mDeBERTa-v3-base |
| M2 | `fastino/gliner2.5-multi-v1` | GLiNER2 | mDeBERTa-v3-base |
| M3 | `nvidia/gliner-PII` | GLiNER v1 | DeBERTa-v3-large (EN-only) |
| M4 | `fastino/gliner2-privacy-filter-PII-multi` | GLiNER2 | mDeBERTa-v3-base |

Типы:

- **Класс C** (плоский NER, семантическая категория): `job_title`,
  `department`, `product_name`, `certification_number`
- **Класс D** (структурная роль поверх формата): `shipment_date` vs
  `signing_date` — одинаковый формат `dd.mm.yyyy`, разная семантическая роль
- **Natasha territory** (пересечение с уже стоящей Natasha):
  `person`, `org_name`, `location`

Стратегии подачи:

- S1 — английские лейблы (`["job_title", "department", ...]`)
- S2 — русские лейблы (`["должность", "отдел", ...]`)
- S3 — русские лейблы + описания (dict)
- S4 — hierarchical structure (только GLiNER2, только для класса D)

Пороги: 0.3, 0.5, 0.7.

## Как запустить

Все веса лежат в HF-кэше (`~/.cache/huggingface/hub/`), качать не надо.

```bash
uv run --with gliner --with gliner2 --with peft \
    --with 'torch>=2.0' --with python-docx \
    --index https://download.pytorch.org/whl/cpu \
    python spikes/gliner_ru/run_spike.py
```

Отчёт — `results/{ISO-timestamp}.md`.

## Три ключевых вывода

### 1. Natasha остаётся, GLiNER её не заменяет

Проверка гипотезы «может GLiNER2 бьёт Natasha на её же поле» дала однозначное
«нет»:

- **`org_name` — потолок 0.636 у GLiNER** (M4 S2@0.3). Много FP на границах:
  модель прихватывает «ИНН 3662103003» вместе с названием, либо теряет часть
  формы («Общество с ограниченной ответственностью») и берёт только кавычки.
  У Natasha по замерам T1.3 на этих же организациях F1 ≥ 0.85 —
  специализированный русский NER на организациях выигрывает у zero-shot.
- **`person` — GLiNER даёт до 0.968 (M4 S1@0.7)**, паритет с Natasha. Но
  очень чувствителен к лейблу: `"person"` на английском (M4 S1) = 0.938, а
  `"фамилия имя отчество"` на русском (M4 S2) = 0.516. Компилятор не должен
  подбирать русский лейбл для этого типа.
- **`location` — паритет** (обе модели 0.857-1.000), но Natasha уже стоит
  и стоит 36 МБ vs 1.1 ГБ, менять смысла нет.

**Роль GLiNER в проекте — только пользовательские типы** (C и D). Natasha
остаётся источником PERSON/ORG/LOC для встроенных типов. GLiNER подключается
в реализации T1.13 как отдельный executor для custom types.

### 2. Одна модель, а не две — берём M2 fastino/gliner2.5-multi-v1

Разница M2 vs M4 в среднем по 9 типам: **0.04 F1** (0.744 vs 0.783 у S3@0.5).
Не оправдывает +1.2 ГБ второй модели, +9 сек к загрузке, +сложность выбора
executor'а в компиляторе.

Аргументы за M2 как единственную GLiNER-модель:

- **Class D через structure API — F1=1.000** идеальный (M4 = 0.928).
  Это то, ради чего изначально был спайк.
- **product_name (0.857)** и **location (0.857)** сильные — часто
  встречающиеся типы в тендерах.
- **shipment/signing_date через S4** — 1.000 с любым порогом, устойчиво.
- **`person` через S3 с описанием — 0.933** (у M4 S3 person = 0.429!),
  то есть с грамотным промптом от компилятора person тоже покрывается.
- Универсальность через schema API — расширяется на новые структурные типы
  без апгрейда модели.

Аргументы за M4 (отвергаются):
- +0.04 F1 в среднем на классе C — но при живом human-preview на компиляции
  это компенсируется корректировкой пользователем.
- Лучше `certification_number` (0.75 vs 0.35) — но для явных ID-шаблонов
  компилятор предпочтёт `regex`, GLiNER здесь не должен работать.

### 3. Descriptions на GLiNER2 — must have

Стабильно +0.05..+0.15 F1 к S3 против S2 у GLiNER2 (у GLiNER v1 M1/M3 они
игнорировались — `predict_entities(text, dict)` берёт только keys).

**Промпт компилятора обязан генерировать описание вместе с русским лейблом.**

Особенно ярко на `person` у M2: S2 (только `"фамилия имя отчество"`) = 0.000
FP, S3 (с описанием `"имя человека, полное или инициалы"`) = 0.933. Разница
в 0.9 F1 от одной строки описания.

## Что это значит для плана T1.13

1. **Одна GLiNER-модель**: `fastino/gliner2.5-multi-v1` через `pip install
   gliner2 peft`. Torch на CPU ~500 МБ + модель ~1.1 ГБ + peft ~50 МБ.
   Apache-2.0. Через `[gliner]` extra в `pyproject.toml`.

2. **Два executor'а у одной модели**:
   - `gliner_label` — `extract_entities(text, {label: description},
     threshold=X)`. По умолчанию `threshold=0.3` (у M2 S3 стабилен на всех
     порогах), но параметр в спеке.
   - `gliner_structure` — `create_schema().structure().field(name, dtype,
     description)`. Для класса D и любых других multi-field типов.

3. **Порог — часть спека executor'а**, не глобальная константа. Компилятор
   при необходимости передаёт `threshold=0.5` или `0.7` (зависит от типа).

4. **Компилятор обязан генерировать русский лейбл + описание**. Без описания
   GLiNER2 деградирует драматично (person 0.000 → 0.933 от добавления
   описания).

5. **GLiNER НЕ вызывается для built-in типов** — Natasha их обрабатывает
   лучше и она уже в проекте. Компилятор должен явно отклонять пользовательские
   запросы, которые дублируют built-in типы (например «замажь ФИО»), и
   направлять к соответствующему built-in.

6. **Для явных ID-шаблонов компилятор предпочитает regex.** У GLiNER
   `certification_number` F1 = 0.75, у regex с корректным шаблоном будет 1.0
   (при чётком «Лицензия № ЛО-77-..»). GLiNER — не универсальный молот.

7. **Скорость на CPU:** 200-240 мс/фраза у M2. Для документа в 500
   сегментов — ~2 минуты на детекторный проход. Батчинг при массовом
   прогоне возможен, но за пределами T1.13.

## Combo B — Natasha + GLiNER для расширения границ ORG

Отдельный прогон `results/2026-09-02T212434Z-natasha.md` сравнивает три
варианта на типах, где Natasha уже работает (person, org_name, location):

| Вариант | person | org_name | location | AVG F1 | ms/фраза |
|---|---|---|---|---|---|
| NatashaOnly (с постобработкой проекта) | 1.000 | 0.941 | 0.000* | 0.647 | 23 |
| NatashaRaw (без постобработки) | 1.000 | 0.417 | 0.857 | 0.758 | 2.5 |
| NatashaGlinerCombo (M2 boundary ext.) | 1.000 | 0.941 | 0.000* | 0.647 | 67 |

*Natasha намеренно игнорирует LOC-метку (см. `NatashaDetector`
docstring — LOC уходит в T1.14 ADDRESS).

**Три вывода:**

1. **Natasha уже даёт 1.000 F1 на person** — GLiNER (M2 S3 person = 0.933)
   её не бьёт. Замена Natasha на GLiNER для PERSON — регрессия на этой
   фикстуре.

2. **Postprocessing проекта работает на org_name** — с ним F1 = 0.941
   (1 FP), без него = 0.417 (11 FP). Убирать `orgforms.py`/`persons.py`/
   `org_rules.py` на этой фикстуре означает regress precision в 3 раза.
   Handoff-документ прав: не удалять постобработку заранее.

3. **Combo B на этой фикстуре ничего не добавил** (тот же F1=0.647, но
   тратит +44 мс). Причина — фикстура не содержит проблемных для Natasha
   случаев (обрезанные ФИО в родительном падеже, гимназии в номинативе).
   Combo B **не отвергнут** — на реальном корпусе (contract_pdf_02_school
   из хендоффа) может показать выигрыш.

**Практика для T1.13:** GLiNER подключается **только для пользовательских
типов**. Natasha остаётся как есть. Combo B оставить как «шаг 9» реализации
T1.13 — включить если после подключения GLiNER замеры на реальном корпусе
покажут выигрыш по org_name.

## Побочные наблюдения (для истории)

- **M1 urchade/gliner_multi-v2.1** (v1 API, multilingual): пик 0.516,
  descriptions игнорирует. Слабее fastino в разы.
- **M3 nvidia/gliner-PII** (deberta-v3-large **английский** encoder): пик
  0.606. На русском лучше M1 благодаря большому энкодеру + PII fine-tune,
  но у M2/M4 лицензионно эквивалентен и хуже — не берём.
- **certification_number** — самый слабый тип у всех моделей. Регэкс на
  «Лицензия № ...» / «Сертификат соответствия ...» справится точнее.
  Компилятор LLM должен для явных ID-шаблонов выбирать regex-executor,
  а не GLiNER.
- **S4 structure API у M2/M4 даёт F1=0** на *плоских* типах (C-класс) —
  это корректное поведение: schema там не описана, модель ищет только
  структуру. Столбцы C в таблице S4 — «модель не искала».
- **person у M4 с русским лейблом теряется до 0.429**, но с английским
  лейблом `"person"` даёт 0.938. При этом M2 с русским лейблом + описанием
  даёт 0.933 — то есть у M2 более устойчивый языковой перенос.

## Что этот спайк не проверял

- Производительность на длинных документах (>2048 токенов, лимит энкодера).
- Батчинг (потенциал ускорения на CPU для многих сегментов).
- Fine-tuning на нашем корпусе (+5-10 F1 при 50-100 примерах, потенциально).
- Устойчивость к OOV пользовательским типам вне корпуса (модели насосов,
  коды проектов) — этих типов в фикстуре нет.
