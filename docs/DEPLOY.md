# Развёртывание стенда

Инструкция про публичный стенд: один скрипт, один домен, TLS автоматом.
Про запуск на своей машине для разработки — `SETUP.md`; про то, какие
переменные на что влияют — `CONFIGURATION.md`.

## Демо за одну команду

```bash
./scripts/deploy.sh up --demo
```

Готовое окружение из `deploy/env.demo`, ни одного вопроса, две учётные
записи с паролями из README (`admin@docveil.local` / `docveil-admin`,
`demo@docveil.local` / `docveil-demo`). Стенд поднимается по http на IP
машины, без TLS.

Пароли опубликованы в репозитории, поэтому такой стенд публичен по
определению: настоящие документы на него не загружаются. Всё, что ниже, —
про стенд, который можно показывать заказчику и держать десять рабочих
дней.

## Коротко

```bash
git clone <repo> docveil && cd docveil
./scripts/deploy.sh up
```

Скрипт проверит окружение, создаст `.env.prod` со случайными секретами,
соберёт образы, поднимет стек, дождётся здоровья каждого сервиса, заведёт
администратора и напечатает адрес с паролем.

Повторный запуск безопасен: секреты не перегенерируются, пароль
администратора не сбрасывается, тома с данными остаются на месте.

## Готовые образы вместо сборки

Релизный workflow публикует образы в GHCR:

```bash
./scripts/deploy.sh up --images          # latest
./scripts/deploy.sh up --images=0.6.1    # конкретный выпуск
```

Так разворачивание занимает минуты вместо десяти: бэкенд не собирается, а
скачивается (`ghcr.io/42team-ru/docveil-backend`).

**Фронтенд в этом режиме всё равно собирается локально, и это не лень
скрипта.** Адрес API вшивается в бандл на сборке
(`frontend/src/shared/api/mutators/authMutator.ts`), а релизный workflow
собирает образ фронта без `VITE_BACKEND_PROD_URL` — то есть опубликованный
`docveil-frontend` ходит в `https://42team.ru`, зашитый дефолт. На любом
другом домене такой образ показал бы пустой экран и ошибки CORS в консоли,
причём без единого сообщения о причине. Скрипт берёт готовый образ фронта
только тогда, когда стенд и правда живёт на `https://42team.ru`.

Чинится это в релизном workflow — передать `VITE_BACKEND_PROD_URL` в
`build-args` фронтового шага бессмысленно (домен неизвестен на сборке),
поэтому правильное решение — научить фронт брать адрес API из origin
страницы, когда переменная не задана. Тогда один образ будет работать на
любом домене. Пока этого нет, действует правило выше.

## Что требуется от сервера

| Ресурс | Минимум | Рекомендуется | Откуда цифра |
|---|---|---|---|
| CPU | 2 ядра | **4 ядра** | прогон CPU-bound и однопоточный; одно ядро на параллельный прогон плюс одно на обслуживание |
| ОЗУ | 4 ГиБ | **8 ГиБ** | пик одного прогона — 545 МиБ (`make bench`, README), база стека ~1,5 ГиБ |
| Диск | 20 ГиБ | **50 ГиБ** | образы ~4 ГиБ, остальное — документы в MinIO |
| GPU | не нужен | — | локальные модели считаются на CPU; torch в прод-образ не ставится |

Формула на случай другого профиля нагрузки:

```
ОЗУ ≈ 1,5 ГиБ + 0,6 ГиБ × (максимум одновременных прогонов)
CPU ≈ 1 ядро × (максимум одновременных прогонов) + 1
```

Оговорка: 545 МиБ — один замер на 46-страничном скане. Документы на сотни
страниц не мерились; если такие ожидаются в потоке, замерьте `make bench`
на своём худшем файле, прежде чем закладывать размер машины.

Порты 80 и 443 должны быть свободны: их занимает Caddy. Всё остальное
(Postgres, MinIO, бэкенд) наружу не публикуется вовсе.

## Что проверяет скрипт до того, как что-то делать

`./scripts/deploy.sh check` — только проверки, ничего не меняет:

- `docker` в PATH, демон отвечает, текущий пользователь имеет к нему доступ
  (отдельно подсказывает про группу `docker`);
- плагин `docker compose` v2 — старый `docker-compose` v1 этот файл не поймёт;
- ядра, доступная память, свободное место;
- свободны ли порты 80 и 443 — иначе `up` упал бы уже после сборки образов,
  потратив десять минут;
- наличие `openssl` (генерация секретов) и `git` (команда `update`).

## Локальные модели

Скачивать отдельно нечего — это устройство продукта, а не упущение:

| Слой | Как попадает на сервер |
|---|---|
| Natasha (NER) | приезжает зависимостью Python, веса внутри пакета |
| Tesseract + русский язык | системный пакет, ставится в `backend/Dockerfile` |
| RapidOCR | зависимость Python, фоллбек при отсутствии tesseract |
| GigaChat | внешний API: нужен только ключ, локальных весов нет |
| PaddleOCR, EasyOCR, GLiNER | в прод-образ **не ставятся** (extras `[ocr]`, `[gliner]`) |

GLiNER исключён намеренно: он тянет torch (около 2 ГиБ к образу), а на
корпусе возвращает ноль предсказаний — `docs/BENCH-MATRIX.md`.

Natasha и провайдер OCR прогреваются на старте процесса
(`WARMUP_ON_START=true`, `src/api/core/warmup.py`), чтобы за загрузку не
платил первый пользователь. Прогрев греет именно тот интерпретатор, который
потом считает прогоны, — отдельной командой снаружи это сделать нельзя.

## GigaChat

Без ключа стенд поднимается и работает: `MASKER_LLM=fake`, роли сторон
определяет эвристика. Ключ добавляется в любой момент:

```bash
# в .env.prod
MASKER_LLM=gigachat
GIGACHAT_CREDENTIALS=<ключ авторизации>

./scripts/deploy.sh update
```

Если GigaChat отвечает ошибкой TLS, добавьте сертификат Минцифры: положите
PEM в `deploy/gigachat-ca.pem`, раскомментируйте монтирование в
`docker-compose.prod.yml` и укажите
`MASKER_LLM_GIGACHAT_CA_BUNDLE=/certs/gigachat-ca.pem`. Отключение проверки
сертификата (`MASKER_LLM_GIGACHAT_INSECURE_SKIP_TLS_VERIFY`) — для
локальной отладки, не для стенда.

## Домен и TLS

Скрипт спрашивает домен. Если A-запись уже смотрит на сервер, Caddy выпустит
сертификат Let's Encrypt при первом запросе — отдельного шага нет.

Без домена стенд поднимается по http на IP-адресе: `SITE_ADDRESS=:80` и
`COOKIE_SECURE=false`. Так можно показывать демонстрацию, но не работать с
настоящими персональными данными — refresh-токен ходит по открытому каналу.

**Смена домена требует пересборки фронта.** Адрес API вшивается в бандл на
сборке (`frontend/src/shared/api/mutators/authMutator.ts`), поэтому после
правки `PUBLIC_URL` нужен `./scripts/deploy.sh update`, а не просто
перезапуск.

## Команды

```bash
./scripts/deploy.sh check     # проверки окружения, ничего не меняет
./scripts/deploy.sh up        # полное развёртывание (по умолчанию)
./scripts/deploy.sh up --images=0.6.1   # то же, но бэкенд берётся из GHCR
./scripts/deploy.sh update    # пересобрать и перезапустить после git pull
./scripts/deploy.sh status    # что поднято и в каком состоянии здоровья
./scripts/deploy.sh logs      # живая лента
./scripts/deploy.sh admin --reset-password   # сменить пароль администратора
./scripts/deploy.sh down      # остановить; тома с данными остаются
```

Неинтерактивно (CI, чужой сервер): значения берутся из окружения, вопросов
не задаётся.

```bash
DOMAIN=docveil.example.ru ADMIN_EMAIL=ops@example.ru \
  GIGACHAT_CREDENTIALS=... ./scripts/deploy.sh up --yes
```

Либо заполните `.env.prod` руками по шаблону `deploy/env.prod.example`.

## Эксплуатация

**Бэкапы.** Данные живут в томах `docveil_pgdata` (прогоны, пользователи) и
`docveil_miniodata` (сами документы). Снимок базы:

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_dump -U masker masker | gzip > backup-$(date +%F).sql.gz
```

**Хранение документов — это хранение персональных данных.** В MinIO лежат
исходные файлы со всем, что продукт потом обезличивает. Для системы
обезличивания держать их вечно — отдельный риск; настройте lifecycle-правило
на срок, который вы готовы защищать.

**Ограничение параллелизма не реализовано.** Прогоны уходят в
`BackgroundTasks` → `run_in_threadpool`, а лимит пула по умолчанию — 40
потоков. Сорок одновременных прогонов по 0,55 ГиБ съедят любую машину.
Лимит памяти контейнера (`BACKEND_MEMORY_LIMIT`, по умолчанию 3 ГиБ)
защищает хост, но прогоны при этом будут убиты OOM-killer, а не поставлены в
очередь. Пока очереди нет, не открывайте стенд десяткам пользователей
одновременно.

**Перезапуск теряет прогоны в полёте.** Состояние графа лежит в Postgres, но
сама фоновая задача живёт в процессе: после `update` прогон, шедший в этот
момент, останется в статусе `running` навсегда. Перед обновлением убедитесь,
что активных прогонов нет (`./scripts/deploy.sh status` и журнал в
интерфейсе).
