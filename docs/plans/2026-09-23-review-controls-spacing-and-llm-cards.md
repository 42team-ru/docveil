# План: бухгалтерский UX, завершённая проверка и админка

Статус: план реализации. Само перечисленное в этом плане ещё не реализовано.
Рабочая ветка: `feat/accountant-report-resources-ux`.

## Не потерять из запроса

- После завершения проверки нельзя повторно нажать «Завершить проверку».
- После завершения нельзя менять тип найденной сущности.
- После завершения нельзя создавать новые ручные PII-отметки выделением.
- Не показывать бессмысленный счётчик `0/0 подтверждено`.
- Переделать тесный/непонятный зазор между контролами тулбара просмотра документа.
- Увеличить поля у админских графиков и таблиц: текст не должен липнуть к границе карточки/экрана.
- Исправить обрезание «Активировать» в списке профилей LLM.
- Вместо тесной таблицы профилей сделать отдельные крупные карточки с уместными иконками.
- Перенести удачные паттерны концепта в настоящий журнал документов: таблица-карточка, заметное состояние строки, аккуратная зебра.
- Не обещать поиск по контрагенту: в журнале искать по имени документа и так же назвать поле.
- В просмотре документа сократить пустые поля вокруг листа и отдать больше полезной ширины панели замен.
- Экран результата сделать понятным и предметным, но оставить вкладку «Отчёт».
- Перенести концепт «Рабочий стол» в настоящий продукт без вымышленных цифр и имени.

## Порядок работ и критерии приёмки

### 1. Зафиксировать единое состояние «проверка завершена»

Файлы: `frontend/src/pages/masker/document-page.tsx`,
`frontend/src/features/masking-run/api/masking-run.ts` (только если нужен общий
предикат), тесты страницы документа.

- Определить завершённость по состоянию прогона (`done`/`leaked`), а не по
  счётчику подтверждений.
- Пока прогон в `awaiting_review`, оставить доступным штатное завершение.
- В терминальном состоянии убрать кнопку «Завершить проверку» из действий;
  во время отправки запроса показывать загрузку и блокировать повторный клик.
- Повторно проверить состояние внутри `handleApprove`, чтобы устаревший
  обработчик/диалог не мог отправить второй запрос после завершения.
- Не менять контракт API и не считать успешный ответ `202` терминальным:
  до фактического перехода статуса прогон ещё обрабатывается.

Приёмка: в `awaiting_review` завершение доступно; после перехода в `done` или
`leaked` кнопки нет и повторный POST не отправляется; двойной клик во время
запроса даёт один запрос.

- Передавать в экран проверки явный `isReadOnly`/`isReviewFinished` для

- Скрыть «Сменить тип» и меню смены типа одного вхождения после завершения;
  защитить также сами callbacks изменения типа.
- Не захватывать выделение для новой PII после завершения, скрыть плавающую
  кнопку и закрыть уже открытый диалог добавления при смене статуса.

Приёмка: для `done`/`leaked` отсутствуют активные редакторы и меню типа,
выделение не открывает создание PII; при `awaiting_review` все текущие

### 3. Убрать `0/0 подтверждено` и ложный сигнал готовности

- Не показывать бейдж подтверждений при `totalCount === 0`.

Приёмка: нулевой счётчик не появляется ни на мгновение при загрузке/пустом

## Минимальные проверки

- Тесты состояний документа: `awaiting_review`, `done`, `leaked`, запрос в
  полёте, ноль групп и обычные группы.
- Тесты read-only: нет меню типа/создания PII в терминальном статусе;
  добавление и смена типа продолжают работать в `awaiting_review`.
- Тест списка LLM-профилей: активный/неактивный, встроенный/свой, длинные
  подписи, отсутствие обрезанных действий.
- Тест/ручная проверка журнала: фильтр по имени, статусы, hover/focus/zebra,
  карточный контейнер, мобильный режим и пустые результаты.
- Проверка экранов просмотра/отчёта: широкая и узкая ширина, длинные значения,
  реальный текст итогов, доступная кнопка скачивания.
- Рабочий стол проверить на отсутствие моковых данных и корректные переходы.
- `yarn typecheck`, затем узкие изменённые тесты и `yarn build`.
- Проверить вручную макеты минимум на ширинах 1440, 1024, 768 и 375 px.

Полный `make gate` в рамках этого плана автоматически не запускать; запускать
только по явному запросу или перед общей сдачей существенного батча.

## Дополнительные идеи для фронтенда (не входят в обязательный объём)

1. **Следующее действие у каждого статуса.** В журнале и на рабочем столе
   показывать короткий глагол по состоянию: «Продолжить проверку», «Скачать»,
   «Открыть причину ошибки»; не заставлять бухгалтера разбираться в именах
   внутренних статусов.
2. **Отдельная очередь проблемных прогонов.** Ошибку объяснять человеческим
   текстом и предлагать только применимое действие: повторить, скачать лог,
   обратиться к администратору. Не смешивать ошибку обработки с найденной
   утечкой.
3. **Сохранение черновика проверки.** Явно показывать, есть ли неприменённые
   решения, и что произойдёт при уходе со страницы; не терять ручные изменения.
4. **Адаптивная плотность.** На таблицах/панелях проверить масштаб браузера
   125–150%, фокус клавиатуры, перенос длинных названий и поведение при
   увеличенном системном шрифте.
5. **Проверка на реальных бухгалтерах.** Короткий тест без обучения: найти
   ожидающий документ, проверить сомнительную замену, завершить и скачать.
   Записывать места заминки, а не спрашивать только «нравится ли дизайн».

Эти идеи отмечены как рекомендации, а не как уже согласованные изменения.

## Уже есть в рабочем дереве

Незакоммиченные изменения предыдущего шага по отступам и объединению отчёта с
ресурсами находятся в той же рабочей ветке. При дальнейшей реализации их надо
сохранить и включить в визуальную проверку, а не откатывать или перезаписывать.
