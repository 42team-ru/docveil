# T1.13 — Design notes: реестр типов сущностей и пользовательские типы

**Статус:** предпланирование, до написания собственно плана. Собирает все
архитектурные решения из чат-сессии по T1.13 в форме, из которой можно
собрать план имплементации.

**Отношение к `docs/plans/T1.13-entity-type-registry.md`:** тот план
устарел в нескольких принципиальных пунктах (YAML как источник конфигурации,
GLiNER отложен, семантические типы через T3.3 LLM-арбитр). Настоящие
нотки его переопределяют — писать план имплементации нужно, исходя из
них.

**Отношение к `docs/handoff/2026-09-02-detect-render-fixes.md`:** хендофф
уже спланировал подключение GLiNER2 как **замену Natasha** для
`person`/`org_name`/`address`. T1.13 надстраивается над этим и
переиспользует ту же модель для пользовательских типов, а также добавляет
LLM-компилятор пользовательского ввода. Это два **разных**, но
пересекающихся направления работы.

---

## 1. Зачем задача существует

`EntityType` — закрытый `StrEnum` в `src/masker/model.py:13`. Он покрывает
встроенные типы (ИНН, ОГРН, ФИО, организация и т.д.). Пользователь тендера
может попросить замаскировать что угодно: «даты отгрузки», «наименование
поставляемых товаров», «внутренние коды проектов». Такой тип нельзя
объявить в коде — его придумает пользователь во время сессии.

Задача T1.13:

1. **Открыть таксономию типов** так, чтобы пользовательский тип был
   гражданином первого сорта (маскируется, попадает в отчёт, проверяется
   на утечку).
2. **Дать пользователю UI-механизм описания типа** — через REST-запрос,
   не через файл. Пользователь описывает тип **словами** («замажь даты
   отгрузки»), backend компилирует это в исполнимую спецификацию через LLM.
3. **Подключить GLiNER2** как ещё один детектор (executor) — не только
   для пользовательских типов, но и для встроенных, где Natasha даёт
   плохие границы (пересечение с задачами хендоффа).

---

## 2. Ключевые архитектурные решения

Каждое решение — с обоснованием и с явно отвергнутыми альтернативами. Это
основной материал для нового чата: если что-то из этого меняется, надо
переоткрывать соответствующее обсуждение.

### 2.1. Источник конфигурации пользовательских типов — REST, не YAML

**Решение:** пользовательские типы приходят в теле REST-запроса на
маскировку, отдельной секцией `custom_types: [CustomTypeSpec, ...]`. YAML
(`masker.types.yaml`) в проекте не появляется.

**Обоснование:** проект живёт под frontend/backend с UI, где юзер
описывает тип в форме. Файловая конфигурация — dev-удобство, которое в
проде никем не используется, а её присутствие тянет за собой инфраструктуру
(валидация схемы, загрузка, override-флаг CLI и env, документация).
Единственный истинный формат — Pydantic-схема тела запроса, она же
валидатор.

**Отвергнутые альтернативы:**
- **YAML основной, REST поверх** — из `docs/plans/T1.13-entity-type-registry.md`.
  Заставляет писать AST-валидатор, load_type_config, тесты формата — впустую,
  потому что реальный вход всё равно API.
- **YAML для CLI, REST для API** — двойной source of truth. Тесты будут
  проверять оба, разъезды будут появляться.

### 2.2. Область жизни спецификации — per-request, но артефакт хранимо-совместим

**Решение:** сейчас `CustomTypeSpec` действует только в рамках одного
запроса. Но структура объекта — plain JSON, immutable, без ссылок на
user/session/document — специально такая, чтобы **позже** можно было
добавить эндпоинты сохранения без переделки логики.

**Как заложить сейчас:**
- `CustomTypeSpec` — plain dataclass с `schema_version`. Никакого
  `user_id`/`session_id` внутри.
- Разделить **компиляцию** и **исполнение** в разные модули:
  - `POST /custom_types/compile` (user_description → `CustomTypeSpec + preview`)
  - `POST /mask` принимает `custom_types: List[CustomTypeSpec]` (уже
    скомпилированные)
- Никакая логика узлов графа не знает, откуда пришёл `CustomTypeSpec`.

**Что оставляем на потом (v2, ~T2.5):**
- Эндпоинты `POST /users/{id}/custom_types` — сохранить пресет
- `POST /mask` принимает альтернативный `preset_ids: [...]` — сервер
  хидрирует ID в `CustomTypeSpec` перед стартом графа
- Логика узлов графа не меняется

**Проекты как область жизни — не нужны** (явно уточнено в чате).

### 2.3. Компилятор пользовательского ввода — LLM с `ask`-ветвью

**Решение:** любой пользовательский текстовый запрос (`"замажь даты
отгрузки"`) проходит через LLM-компилятор. Промпт компилятора содержит:
- Паспорт доступных executor'ов (literals, regex, regex_context,
  gliner_label, gliner_structure, regex_llm_filter)
- Реестр built-in типов (для отказа от переопределения ФИО и т.п.)
- Ограничения (не писать regex с катастрофическим бэктрекингом; писать
  описания на русском; предпочитать более дешёвые executor'ы)

**Компилятор возвращает** JSON с одним из четырёх исходов:

| Исход | Действие |
|---|---|
| `use_builtin { type_id, marker_override? }` | Тип уже есть, ничего компилировать не надо |
| `compile { spec: CustomTypeSpec }` | Готовый спек, отдаётся на preview |
| `ask { question, options, target }` | Неоднозначность, юзер уточняет |
| `cannot_compile { reason }` | Не понимаем что делать, юзер переформулирует |

**Ask-ветвь ложится на существующий T1.5.1 human-in-the-loop** через
LangGraph `interrupt()`. Это отдельное прерывание графа — на этапе
компиляции, до этапа маскировки. Ту же инфраструктуру мы уже используем
для ProfileAgent/JudgeAgent — не строим новый механизм.

**LLM выбирается через `LLMProvider`** (проектное требование: не завязываемся
на GigaChat, замена на локальную модель не должна трогать логику узлов).
Практически — начнём с GigaChat, стенд может подключить Qwen через
провайдер.

**Отвергнутая альтернатива:** UI где юзер сам выбирает `literals | regex |
description` — заставляет пользователя знать таксономию executor'ов,
барьер входа.

### 2.4. Пять executor'ов, класс E НЕ поддерживается

**Executor'ы:**

| id | Когда компилятор выбирает | Стоимость на прогоне |
|---|---|---|
| `literals` | Юзер дал список строк | ~0 |
| `regex` | Явный синтаксический шаблон | ~0 |
| `regex_context` | Regex + якорные слова в окне ±N chars | ~0 |
| `gliner_label` | Именованная категория, semantic поиск | ~4-20 мс/сегмент CPU |
| `gliner_structure` | Роль поверх формата (класс D) | ~200 мс/сегмент CPU |
| `regex_llm_filter` | Стабильный шаблон, семантика решает | LLM-вызов на кандидата |

**Класс E (open-ended semantic без anchor'а) не поддерживается.** Из чат-
дискуссии: все реальные тендерные запросы после `ask`-ветвления сводятся к
executor'ам A-D. Runtime `llm_semantic` детектор (LLM на каждом сегменте)
не окупается по цене и не даёт качественного выигрыша.

**Если компилятор не может свести к A-D после уточнений → `cannot_compile`.**

### 2.5. Live preview на компиляции — обязательный шаг

**Решение:** после того как LLM-компилятор выдал `CustomTypeSpec`, backend
**сразу прогоняет его на 2-3 сегментах текущего документа** и возвращает
пользователю: `preview_matches: [{sample_text, matched_spans, ...}]`.

Пользователь либо подтверждает — тип сохраняется в запросе — либо
отклоняет/уточняет, компилятор пересобирает спек с учётом фидбека.

Компиляция обязательно должна быть частью того же запроса, где уже загружен
документ. Раздельный «сначала опиши тип, потом загружай документ» —
не рассматриваем (мы не знаем без документа, какие сегменты показывать).

**Отвергнутые альтернативы:**
- LLM-компилятор синтезирует «примеры совпадений» без прогона — соблазн
  выдать желаемое за действительное; получим plausible-выглядящие цифры,
  не подтверждённые реальным executor'ом.
- Пилотный документ отдельно от прогона — усложняет UX.

### 2.6. Отношения с built-in типами

Компилятор проверяет: не покрыт ли запрос уже built-in типом (ФИО → PERSON,
ИНН → INN и т.д.). Если да — возвращает `use_builtin`. При этом:

**Разрешено:**
1. **Переопределение маркера** (`marker_override`). Юзер хочет
   `[ФИО-СВИДЕТЕЛЯ]` вместо `[ПЕРСОНА]` — компилятор возвращает
   `use_builtin { type_id: "person", marker_override: "[ФИО-СВИДЕТЕЛЯ]" }`.
   Custom type c таким же executor как built-in, но своим маркером.
2. **Фильтр поверх built-in** (позже, v2). Юзер хочет маскировать только
   *определённых* людей — это фактически subset built-in по правилу. Пока
   не в scope.

### 2.7. Бюджеты — есть, конкретные

**Ограничения:**
- `max_custom_types_per_request = 20`
- `max_llm_filter_calls_per_document = 500`

При превышении — падение запроса с чётким сообщением. Никакой magic
degradation с молчаливо пропущенными типами.

### 2.8. GLiNER2 — **одна модель, `fastino/gliner2.5-multi-v1`**

**Модель выбрана эмпирически** по спайку `spikes/gliner_ru/` на 31 фразе /
58 спанах / 9 типах. Результаты в `spikes/gliner_ru/results/` и в
`spikes/gliner_ru/README.md`.

**Что дала M2:**
- Плоский NER (RU labels + descriptions): F1_avg = 0.744 (все 9 типов)
- Structure API на классе D (shipment vs signing date): **F1 = 1.000**
- Person через S3: F1 = 0.933 (с корректным описанием)
- Универсальный API (`create_schema()`) — расширяется на новые структурные
  типы без замены модели
- Apache-2.0, ~1.1 ГБ на диске, 200 мс/фраза на CPU

**Отвергнутые альтернативы:**
- M4 `fastino/gliner2-privacy-filter-PII-multi`: +0.04 F1 в среднем и лучше
  на некоторых типах, но 0.928 vs 1.000 на классе D и +1.2 ГБ вторая
  модель — не оправдано (решено пользователем: универсальность важнее).
- M1 `urchade/gliner_multi-v2.1`: v1 API, descriptions игнорирует, пик
  0.516 — не берём.
- M3 `nvidia/gliner-PII`: EN-only encoder, тащит DeBERTa-v3-large — не берём.
- Комбинация M2+M4: удвоение зависимостей ради +0.04 F1, не окупается.

### 2.9. Descriptions must-have для GLiNER2

**Эмпирическое наблюдение из спайка:** у M2 добавление описания к лейблу
меняет `person` с F1 0.000 (без описания, лейбл `"фамилия имя отчество"`) на
F1 0.933 (с описанием `"имя человека, полное или инициалы"`). Разница в
0.9 F1 от одной строки.

**Промпт компилятора обязан генерировать описание вместе с русским
лейблом.** Это часть контракта: `gliner_label` executor обязательно
принимает `{label: str, description: str}`, не list of str.

### 2.10. Русские лейблы > английских

**Эмпирика:** +0.05 F1 в среднем при русских лейблах у M2. Компилятор пишет
русские лейблы и русские описания.

### 2.11. Порог модель-зависим, часть спека executor'а

У M2 оптимум ~0.3-0.5, у M4 ~0.7. Значение порога — параметр
`gliner_label`/`gliner_structure` executor'а, компилятор его назначает
исходя из типа. Не глобальная константа.

### 2.12. Natasha остаётся для built-in типов

**Эмпирика по спайку с расширенной фикстурой:**
- GLiNER M4 на `org_name` — F1 = 0.636 (много FP на границах)
- GLiNER M2 на `org_name` — F1 = 0.588
- Natasha (по замерам хендоффа): recall 0.950, precision 0.463, F1 0.623

Все три близки, но Natasha уже 36 МБ в проекте, а GLiNER — 1.1 ГБ. Замена
Natasha на GLiNER для `org_name` **сама по себе не оправдана** — качество
паритетное, а весы разные на порядок.

**Но:** GLiNER всё равно подключается ради пользовательских типов (это
единственная роль ради которой мы платим 1.1 ГБ). Раз он уже подгружен —
имеет смысл **параллельно** использовать его на встроенных типах через
**combo B** (см. 2.13).

**Хендофф `docs/handoff/2026-09-02-detect-render-fixes.md` предлагает
заменить Natasha на GLiNER2 полностью.** Это отдельное направление работы,
которое можно доделать в T1.13 или после. По итогам моего спайка я
рекомендую **не удалять Natasha сразу**, а действовать по плану хендоффа:
подключить GLiNER рядом (`GlinerDetector` в `default_detectors()`), запустить
`make eval`, увидеть, что меняется — потом выносить `persons.py` /
`orgforms.py` / `org_rules.py` по одному.

### 2.13. Combo B — GLiNER расширяет границы Natasha-спанов ORG

**Наблюдение:** главная слабость Natasha — обрезание длинных ОПФ
(«Общество с ограниченной ответственностью «Вектор»» → только «Вектор»).
GLiNER на плоском NER эту проблему не решает лучше, но на **окне вокруг
Natasha-спана** может расширить границу.

**Post-processor `GlinerBoundaryExtender`:**
1. Пробегается по всем entities типа ORG_NAME из Natasha
2. Для каждого — вызывает GLiNER M2 на окне `text[start-50 : end+50]`
   с лейблом `"название организации"` + описанием
3. Если GLiNER возвращает более длинный ORG-span, содержащий Natasha-спан
   — заменяет Natasha-версию GLiNER-версией

**Стоимость:** N × GLiNER-вызов, где N = число ORG-спанов в документе.
Для типичного договора это 5-20 вызовов вместо 500 (полный проход GLiNER).
Порядок 1-5 сек вместо 2-3 мин на прогон.

**Замер на spike-фикстуре (`results/2026-09-02T212434Z-natasha.md`):**

| Вариант | person | org_name | location | AVG F1 |
|---|---|---|---|---|
| NatashaOnly | 1.000 | 0.941 | 0.000* | 0.647 |
| NatashaRaw (без постобработки) | 1.000 | 0.417 | 0.857 | 0.758 |
| NatashaGlinerCombo (M2) | 1.000 | 0.941 | 0.000* | 0.647 |

*Natasha игнорирует LOC (T1.14 задача).

**Combo B ничего не добавил на этой фикстуре** — Natasha уже нашла все ORG
правильно, GLiNER на окне не расширил границы. Но фикстура намеренно не
содержит проблемных для Natasha случаев (длинных ОПФ, обрезанных ФИО в
родительном падеже). На реальном корпусе (`contract_pdf_02_school.pdf` из
хендоффа) combo B может показать выигрыш — эмпирика на этом spike не
исключает, но и не подтверждает.

**Также подтверждено:** постобработка проекта работает — увеличивает
precision на org_name с 0.312 (raw Natasha) до 0.889 (с постобработкой).
Убирать её нельзя до замеров.

**Combo B — последний шаг в реализации T1.13**, после того как всё
остальное работает. Замерить precision/recall до и после combo на
реальном корпусе — оставить только если польза подтверждена.

## 3. Как это ложится на существующую архитектуру

Проект уже имеет всё для подключения GLiNER без переделок:

### 3.1. `EntityDetector` protocol — точка расширения

`src/masker/detect/base.py:10-19`. `GlinerDetector` реализуется как
ещё один `EntityDetector` с `source=Source.NER`, `priority=50` (как у
NatashaDetector). Добавляется в `default_detectors()` в
`src/masker/detect/__init__.py:12-21` — вопрос одной строки.

### 3.2. `DetectAgent._resolve_overlaps` — уже правильно приоритизирует

`src/masker/detect/agent.py:64-91`. Priority 100 (RULE) > 50 (NER). GLiNER
не сможет «съесть» ИНН, потому что `_carve` вычитает точные rule-спаны из
модельных. Это записано и в хендоффе.

### 3.3. `DetectAgent._validate` — контракт entity.text == segment.text[start:end]

`src/masker/detect/agent.py:47-62`. GLiNER2 возвращает **текст** спана
(не оффсеты), значит наш адаптер должен через `text.find()` восстанавливать
позиции — иначе `_validate` уронит. Это уже реализовано в
`spikes/gliner_ru/run_spike.py::_spans_from_label_texts`, оттуда переносится
в prod.

### 3.4. `Entity.type: EntityType` — вот тут ломается

Для пользовательских типов надо `Entity.type: str`. Существующие
потребители (`entity.type.value` в 6 местах — по grep из старого плана T1.13)
поправить. `EntityType` не удаляем — остаётся как enum built-in типов,
подтип `str`, все isinstance-проверки заменяются на проверку по реестру.

Список правок — в старом плане (`docs/plans/T1.13-entity-type-registry.md`
раздел «Полный список потребителей контракта типа»), актуален с точностью
до сдвига номеров строк после хендофф-коммитов.

### 3.5. `RuleDetector` (priority=100) — GLiNER не тронет числовые типы

Хендофф прямо говорит: спрашивать у GLiNER **только** `person`, `org_name`,
`address`, возможно `site`. ИНН/ОГРН/паспорт/счёт — остаются за
`RuleDetector` с контрольной суммой. То же для пользовательских типов —
компилятор выбирает `regex` executor для явных ID-шаблонов, `gliner_*`
только для semantic категорий.

### 3.6. `LLMProvider` — контракт для компилятора

`src/masker/llm/`. Требование заказчика №6: замена GigaChat на локальную
модель не должна трогать логику узлов. Компилятор пользовательского ввода
использует `LLMProvider`, а не прямой вызов GigaChat/Anthropic/OpenAI.

### 3.7. LangGraph `interrupt()` для ask-ветви компилятора

Уже используется в T1.5.1 (human-in-the-loop). Спек новой interrupt-
точки — на этапе компиляции, до detect/mask цикла. Отдельный `AskType`
или расширить существующий.

   Natasha (не вместо), прогнать `make eval`, вынести
   `persons.py`/`orgforms.py`/`org_rules.py` по одному. Наш T1.13 этот
   порядок соблюдает — Natasha остаётся, combo B добавляется поверх.
2. **Метка → тип через explicit таблицу**, а не по совпадению имён.
   Наш `gliner_label` executor это делает.
3. **API:** `include_spans=True`, `include_confidence=True`. Для длинных
   документов — `batch_extract_entities_long` по сегментам, не один вызов
   на 46 страниц. `Entity` живёт в локальных смещениях сегмента.
4. **Детерминизм:** инвариант проекта. `torch.set_num_threads(1)` + eval-
   mode + явная сортировка. Прогон существующий `tests/masker/test_determinism.py`.
5. **Скорость на CPU:** замерить до, не после интеграции. Спайк дал
   200 мс/сегмент — приемлемо.
6. **Схема меток вести к `EntityType`:** проси у модели только `person`,
   `org_name`, `address`, `site`. Число тонов, ИНН, паспорт — за
   `RuleDetector`.
7. **Постобработка Natasha (~700 строк):** не удаляй заранее. Часть
   словарей (оргформы, госорганы, ролевые стоп-слова) полезна и модели —
   как фильтр precision. Не выбрасывай словари вместе с логикой расширения.
8. **Незакрытые долги, важные для T1.13:**
   - `leaked_total = 8` — есть 8 утечек на корпусе. `ValidateAgent` уже
     работает (T1.8), должен ловить и пользовательские типы.
   - `org_name precision = 0.463` (22 FP) — часть от `OrgFormDetector`,
     исчезнет если GLiNER справится. Combo B — путь к этому.
   - `policy_questions_per_document = 13.0` — «слишком много вопросов»,
     отдельная задача. Custom type ask-ветвь не должна её усугублять.
9. **Модель, которую предлагает хендофф:** `fastino/gliner2-privacy-filter-
   PII-multi` (мой M4). Наш выбор — M2 `fastino/gliner2.5-multi-v1`
   (универсальность + идеальный structure API на классе D). Разница
   принципиальна для класса D (M2 = 1.000 vs M4 = 0.928); для person/org
   разница копеечная. Решение — M2, обосновано выше в 2.8.

**Итого:** хендофф и T1.13 согласованы концептуально. Разница только в
выбранной модели GLiNER (обоснована в спайке).

## 5. Что делает T1.13, и что — нет

### В scope T1.13

- Открытие `Entity.type: str`, реестр `EntityTypeRegistry`, `EntityTypeSpec`
- `CustomTypeSpec` dataclass + Pydantic-схема API
- LLM-компилятор `POST /custom_types/compile` (input: natural language,
  output: `CustomTypeSpec` или `ask`/`cannot_compile`)
- Live preview на компиляции
- Executor'ы: `literals`, `regex`, `regex_context`, `gliner_label`,
  `gliner_structure`, `regex_llm_filter`
- `GlinerDetector` через `EntityDetector` protocol
- Маркеры пользовательских типов
- Валидация утечек по всем типам (не только запрошенным) — уже делает
  `ValidateAgent` T1.8, надо чтобы новые executor'ы туда попали
- Тесты каждого executor'а (мин. один падающий тест на ветку)
- Corpus fixture с несколькими пользовательскими типами

### Возможно в scope T1.13, обсудить в плане

- Combo B (`GlinerBoundaryExtender`) — как последний шаг реализации,
  если данные из спайка `results/*-natasha.md` покажут выигрыш.
- Обновление `mask/labels.py::MARKER_TYPE_LABELS` под custom-типы (или
  через сам `EntityTypeSpec.marker_label`).

### Не в scope T1.13

- Замена Natasha на GLiNER полностью для built-in типов — это отдельное
  направление после T1.13 (хендофф предлагает).
- Удаление `persons.py`/`orgforms.py`/`org_rules.py` — только после
  замеров.
- Per-user preset сохранение (`POST /users/{id}/custom_types`) —
  задел архитектурный есть, реализация отдельно.
- Проекты как область жизни — не делаем никогда.
- Runtime `llm_semantic` executor (класс E) — не поддерживаем, компилятор
  возвращает `cannot_compile`.
- Fine-tuning GLiNER на нашем корпусе — не в T1.13, потенциальный follow-up.

## 6. Открытые вопросы для планирования

Эти вопросы намеренно не решены в чате — они возникают уже в фазе плана,
на них должен ответить следующий чат в диалоге с пользователем.

1. **Какая LLM у компилятора первой?** Требования: русский, JSON structured
   output, разумная цена. Кандидаты — GigaChat-Max, Claude Sonnet, Qwen
   32B локально. Требование проекта — через `LLMProvider`. Первый выбор
   — вероятно GigaChat (уже интегрирован), но качество structured output
   у него надо проверить.
2. **Формат `preview_matches` в ответе `/custom_types/compile`.**
   Возвращаем спаны в исходных сегментах или markdown-outline документа?
   Frontend это отрисовывает, надо согласовать с UI.
3. **Обработка ошибок compile-time** — если пользователь описал 5 типов
   и один упал `cannot_compile`, что делать с остальными четырьмя?
   Скорее всего partial success: компилируем что удалось, возвращаем
   ошибки для остального.
4. **Ретрай при `ask`.** Максимум N-раундов уточнений? После N — падаем
   или отдаём последнее лучшее?
5. **Cache спеков.** Одинаковые описания — одинаковые спеки? С учётом
   стохастичности LLM (temp>0) — хеш от нормализованного описания →
   уже готовый спек. Уровень: per-user, глобальный?
6. **Combo B — включать в T1.13 или отдельной задачей?** Реалистично
   уложиться в T1.13 или лучше вынести в T1.13.1?
7. **Тестовые фикстуры для пользовательских типов** — добавить
   `contract_09_custom.docx` с явными пользовательскими типами (даты
   отгрузки, названия товаров) для корпусного теста.
8. **`recall_critical = 1.0`** для пользовательских типов — если юзер
   указал `critical: true`, порог recall его типа = 1.0 в воротах `eval`?
   В старом плане T1.13 разрешалось, но с предупреждением. Здесь не
   переоткрываем — оставляем разрешённым.
