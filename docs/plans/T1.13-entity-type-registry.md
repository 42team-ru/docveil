# T1.13 — Реестр типов сущностей: выбор что искать и пользовательские типы

Новая задача, в `TASKS.md` её нет. Идёт **после T1.3** (см. «Зависимости»).

## Решение в одном абзаце

`EntityType` остаётся закрытым `StrEnum` встроенных типов, но перестаёт быть
единственным словарём: появляется **реестр** `EntityTypeRegistry` из
`EntityTypeSpec` (id, имя для человека, шаблон маркера, критичность, чем
детектится). `Entity.type` меняет аннотацию с `EntityType` на `str`.
Это дешевле, чем кажется: `StrEnum` хэшируется по значению (проверено:
`hash(EntityType.INN) == hash("inn")` → `True`, `"inn" in CRITICAL_TYPES` →
`True`), поэтому все существующие словари, множества и сравнения продолжают
работать без правок, а чинить надо ровно **пять строк** в четырёх файлах.
Пользовательские типы описываются в `masker.types.yaml` и детектятся одним
`ConfigDetector` — списком литералов или проверенной регуляркой. GLiNER в этой
задаче **не подключается, но и не отвергнут**: решение по нему принимается
после T1.3, когда корпусный тест покажет реальный дефицит Natasha по
`ORG_NAME` и `PERSON` (условия — в разделе про GLiNER). Семантические типы
вроде «все даты отгрузки» до тех пор обслуживает LLM-арбитр T3.3 через уже
существующий `LLMProvider`. Фильтр «что искать» применяется **в плане**, а не
в детекции.

## Открытие типа: принятое решение и его цена

`EntityType` — закрытый `StrEnum`. `CRITICAL_TYPES` — `frozenset[EntityType]`.
`DetectAgent._validate` требует `isinstance(entity.type, EntityType)`. Отчёт и
маркеры завязаны на членов enum. Пользовательский тип «замазать все даты
отгрузки» в эту схему не влезает физически: его нельзя объявить в enum на
этапе написания кода, потому что его придумает пользователь.

**Решение принято человеком: реестр плюс `Entity.type: str`.** `EntityType` и
`CRITICAL_TYPES` остаются в `model.py` как перечень встроенных типов и
продолжают использоваться везде, где тип известен статически; реестр
надстраивается над ними и добавляет пользовательские id. Это сквозная линия
всего плана, а не один вариант из трёх; альтернативы сведены в короткий раздел
«Почему не так» ниже.

`AGENTS.md` запрещает менять сигнатуры в `model.py` без правки всех
потребителей — поэтому потребители перечислены поимённо, с номерами строк на
текущем `master`.

### Контракт реестра

```python
# src/masker/entity_types.py
@dataclass(frozen=True, slots=True)
class EntityTypeSpec:
    id: str                 # "inn", "shipment_date" — то, что лежит в Entity.type
    title: str              # «ИНН», «Дата отгрузки» — для отчёта и UI
    marker: str             # шаблон: "[{ROLE}-ИНН]" или "[ДАТА-ОТГРУЗКИ-{n}]"
    critical: bool = False
    detector: str = "rule"  # "rule" | "ner" | "literals" | "regex" | "llm"
    builtin: bool = True


class EntityTypeRegistry:
    def __contains__(self, type_id: str) -> bool: ...
    def spec(self, type_id: str) -> EntityTypeSpec: ...     # KeyError с перечнем известных
    def ids(self) -> tuple[str, ...]: ...                   # отсортированы
    def critical_ids(self) -> frozenset[str]: ...
    def extend(self, custom: Iterable[EntityTypeSpec]) -> EntityTypeRegistry: ...  # НОВЫЙ объект

    @classmethod
    def builtin(cls) -> EntityTypeRegistry: ...             # из EntityType и CRITICAL_TYPES
```

Реестр **иммутабелен**: `extend` возвращает новый объект. Это прямо про
детерминизм — глобального изменяемого состояния, от порядка правок которого
зависит результат, не появляется.

Цена перехода — ровно то, что перечислено в таблице выше:

- `model.py` — одна строка аннотации плюс комментарий, что `EntityType`
  остаётся перечнем встроенных id и продолжает использоваться везде, где тип
  известен статически. `EntityType` **не удаляется**, `CRITICAL_TYPES` тоже.
- `detect/agent.py` — `isinstance` заменяется на `entity.type in self._registry`
  (агент получает реестр в конструкторе со значением по умолчанию
  `EntityTypeRegistry.builtin()`); два `.type.value` → `.type`.
- `detect/result.py`, `eval.py` — по одному `.type.value` → `.type`.
- `eval.py:87` — `name in registry.critical_ids()`.
- mypy: `Entity(type=EntityType.INN, …)` продолжает проходить, потому что
  `EntityType` — подтип `str`. Обратное (`Entity.type` присваивают в поле
  `EntityType`) в коде не встречается.
- Тесты: правок не требуют (проверено сравнением семантики `StrEnum`).

### Почему не так

**Гибрид `Entity.type: EntityType | str`.** `.value` всё равно ломается на
ветке `str`, то есть объём правок тот же, но mypy strict добавляет
`isinstance`-развилки в каждом потребителе, а одно значение получает два
способа записи (`EntityType.INN` и `"inn"`). Дороже при том же результате.

**Динамическое расширение enum из конфигурации.** mypy перестаёт видеть члены,
статические ссылки в `rules.py`, `ner.py` и тестах перестают проверяться, а
состав контракта начинает зависеть от того, какой файл лежал рядом при
импорте. `model.py` перестал бы быть единственным местом, где определены
контракты.

## Где применяется фильтр «что искать»: в плане, не в детекции

Пользователь передаёт `--types inn,person,org_name`. Соблазн — не запускать
детекторы лишних типов. Правильный ответ — **детектим всё, маскируем
запрошенное**. Четыре причины, три из них про инвариант «утечки нет»:

1. **ValidateAgent (T1.8) проверяет утечки повторным прогоном детекторов по
   результату.** Если детекция знает про фильтр, она обязана быть отфильтрована
   и на выходе — а тогда мы физически не сможем увидеть, что рендер оставил в
   документе незапрошенный, но реально утёкший реквизит. Проверка утечек
   должна быть шире маскировки, иначе она проверяет саму себя.
2. **Профилю нужны незапрошенные сущности.** По плану T1.4 ИНН — сильнейший
   ключ слияния блоков (`K1`). Пользователь, попросивший замаскировать только
   `person`, при фильтре на детекции лишит `ProfileAgent` ключа, и ФИО
   поставщика перестанет отличаться от ФИО покупателя — маркер
   `[ПОСТАВЩИК-ДИРЕКТОР]` выродится в `[ФИО-3]`.
3. **Метрики перестанут быть сравнимыми.** `make eval` считает recall по
   корпусу; если состав детекции зависит от запроса, цифры на защите зависят от
   того, какие галочки были нажаты.
4. **Экономии всё равно нет.** Измерено на T1.3: правила плюс NER на документе
   в 510 абзацев — 0.24–0.68 с, модели уже в памяти. Экономить нечего.

Единственное место, где фильтр по типам действительно уместен на входе, —
**вход LLM-арбитра (T3.3)**: там платят за запрос, и туда идут только спорные
фрагменты запрошенных типов плюс типы, нужные для профилирования
(`inn`, `ogrn`, `org_name`). Это записывается контрактом для T3.3, кодом здесь
не реализуется.

Что T1.13 даёт для фильтра прямо сейчас:

```python
# src/masker/mask/select.py
def filter_by_types(
    entities: list[Entity],
    requested: frozenset[str],
    registry: EntityTypeRegistry,
) -> list[Entity]:
    """Оставить сущности запрошенных типов. Порядок входа сохраняется."""
```

плюс `resolve_requested_types(raw: Sequence[str], registry) -> frozenset[str]`
с обработкой `all` и ошибкой на неизвестном id, содержащей перечень известных.
`PlanAgent` (T1.6) вызывает это первой строкой; CLI (T1.9) — только парсит
аргумент.

Отдельная оговорка про пользовательские типы: их детектор существует только
если тип объявлен в конфигурации. Это не фильтрация, а состав детекторов.
Объявленные типы детектятся все, даже если запрошена часть, — по причинам 1–3.

## Пользовательская конфигурация

### Где лежит

**И файл, и поле запроса, но источник истины один — структура
`EntityTypeSpec`.**

- Файл `masker.types.yaml` в корне проекта. Путь переопределяется
  `--types-config` (T1.9) или `MASKER_TYPES_CONFIG`. Это то, чем пользуется
  CLI, `make demo` и защита.
- API (`src/api/`) — **вне скоупа T1.13**. Когда дойдут руки: поле
  `custom_types: list[CustomTypeIn] | None` в схеме запроса
  `src/api/schemas/file.py`, сервис валидирует его тем же
  `load_type_config()` и кладёт результат в `State`. Ни одна строка логики
  узлов при этом не меняется — ровно ради этого конфигурация описана как
  данные, а не как код.

### Формат

```yaml
version: 1
types:
  - id: contract_no
    title: Номер договора
    marker: "[ДОГОВОР-{n}]"
    critical: false
    detect:
      kind: regex
      pattern: "№\\s?\\d+/\\d{4}"
      ignorecase: false

  - id: shipment_date
    title: Дата отгрузки
    marker: "[ДАТА-ОТГРУЗКИ-{n}]"
    detect:
      kind: regex
      pattern: "\\d{2}\\.\\d{2}\\.\\d{4}"
      ignorecase: false
      context: ["отгрузк", "поставк"]      # обязателен в окне ±80 символов

  - id: internal_secret
    title: Скрыть по списку
    marker: "[СКРЫТО-{n}]"
    detect:
      kind: literals
      values: ["Проект «Заря»", "внутренний код 42"]
      match: whole_word                      # whole_word | substring
      ignorecase: true
```

Правила валидации схемы (каждое — отдельный тест):

- `id` — `^[a-z][a-z0-9_]{2,31}$`, не пересекается с `EntityType`;
- `title` — непустой; `marker` — содержит `{n}` либо `{role}`;
- `critical: true` разрешён, но выводит предупреждение: критичный тип поднимает
  порог recall до 1.0 в воротах, и пользовательская регулярка обязана быть
  готова этот порог держать;
- `detect.kind` — только `literals` или `regex`;
- дубликаты `id` — ошибка с указанием обоих мест.

### Чем детектится пользовательский тип: три механизма

**1. Список литералов — механизм по умолчанию и ответ на «замазать вот это».**
Значения экранируются `re.escape`, сортируются по убыванию длины (детерминизм и
приоритет длинного совпадения), собираются в одну альтернацию с обрамлением
`(?<![\w])…(?![\w])` при `match: whole_word`. ReDoS невозможен: в паттерне нет
ни одного квантификатора. Это тот случай, когда правильный ответ — самый
скучный.

**2. Пользовательская регулярка — для «номеров договоров» и подобного.**
Опасность реальна: `re` в стандартной библиотеке не умеет таймаут, а
`(a+)+$` на строке из 30 символов вешает процесс. Защита в три слоя:

- **Статический валидатор по AST.** Разбираем паттерн через `re._parser.parse()`
  (стандартная библиотека, детерминированно) и отклоняем: вложенный
  квантификатор (`MAX_REPEAT`, внутри поддерева которого снова `MAX_REPEAT`);
  обратные ссылки (`GROUPREF`, `GROUPREF_EXISTS`); паттерн, сопоставимый с
  пустой строкой (`compiled.fullmatch("") is not None`); длину паттерна больше
  `MAX_PATTERN_LEN = 200`; флаги вне белого списка (разрешён только
  `IGNORECASE`).
- **Ограничение входа.** Регулярка применяется к одному `Segment.text`, а не к
  документу целиком; сегмент — абзац. Экспоненциальный взрыв требует длинной
  строки.
- **Бюджет времени.** Суммарное время пользовательских регулярок на документ
  меряется `perf_counter`; превышение `CUSTOM_REGEX_BUDGET_S = 2.0`
  завершается `CustomTypeError` с именем типа. Честно: бюджет **не прерывает**
  уже начавшийся `finditer` — он ловит «много умеренно медленных паттернов».
  Настоящая защита от катастрофического бэктрекинга — валидатор.
- Отвергнутая альтернатива: пакет `regex` (2026.7.19) поддерживает
  `finditer(..., timeout=…)` и убил бы проблему полностью. Не берём, потому
  что это ещё одна бинарная зависимость ради случая, которого валидатор не
  пропускает. Если в реальной эксплуатации всплывёт паттерн, который валидатор
  считает безопасным, а он вешается, — вот тогда `regex` и добавляем; это
  записано как явная точка эскалации.

**3. Zero-shot метка для GLiNER — в T1.13 не реализуется, решение отложено.**
`EntityTypeSpec.detector` уже допускает значение, которого нет ни у одного
детектора: добавление `GlinerDetector` будет означать новую реализацию
`EntityDetector` и запись в реестре — ни `model.py`, ни `DetectAgent`, ни
конфигурация типов при этом не меняются. Точка расширения готова, само
подключение — отдельное решение после T1.3 (см. раздел ниже). До тех пор
семантические типы («все даты отгрузки», «любые упоминания филиалов»)
обслуживает LLM-арбитр T3.3: `EntityTypeSpec.detector = "llm"` плюс поле
`description`, которое попадает в промпт. Это тот же zero-shot, но через
`LLMProvider`, то есть с соблюдением требования заказчика №6.

### `ConfigDetector`

```python
class ConfigDetector:
    name = "config"
    source = Source.USER        # новый член Source
    priority = 95               # ниже правил проекта (100), выше NER (50)

    def __init__(self, specs: Sequence[CustomTypeSpec]) -> None: ...
    def detect(self, document: Document) -> list[Entity]: ...
```

`Source.USER` добавляется в `model.py` — аддитивно, `isinstance(entity.source,
Source)` в `_validate` продолжает работать. Смысл: в отчёте графа «кем найдено»
должно быть видно различие между правилом проекта с контрольной суммой и
регуляркой, которую написал пользователь. `confidence = 1.0` для литералов
(пользователь буквально указал строку) и `0.9` для регулярки.

Приоритет 95 обсуждаем: пользовательский литерал не перебивает ИНН, но
перебивает NER. Если литерал накрыл ИНН, ИНН всё равно останется
замаскированным — изменится только маркер, а не факт маскировки, так что
инвариант «утечки нет» не страдает ни при каком выборе.

## GLiNER: решение отложено до конца T1.3

| | Natasha (уже стоит) | GLiNER |
|---|---|---|
| Вес зависимостей | 36 МБ в `site-packages`, уже установлено | `torch` 2.13 — колесо `manylinux_2_28_x86_64` **527 МБ** (плюс `nvidia-*` пакеты ≈ 2–3 ГБ, если не ставить с CPU-индекса); `transformers`, `tokenizers`, `onnxruntime`, `sentencepiece`, `huggingface_hub` |
| Веса модели | внутри пакета, в git не тянутся | скачиваются с HuggingFace при первом `from_pretrained`, 0.5–1.2 ГБ |
| Работа офлайн | **да, проверено** — сеть не нужна вообще | только после ручного прогрева кэша и `HF_HUB_OFFLINE=1`; из коробки — нет |
| Загрузка | 0.28 с (замерено) | секунды, плюс первое скачивание |
| Инференс | 4 мс на абзац, 0.24 с на 510 абзацев (замерено) | на CPU на порядок-два медленнее |
| Детерминизм | два процесса дали идентичные спаны (замерено) | eval-режим детерминирован по построению, но пороговые решения зависят от числа BLAS-потоков и версии torch; нужен `torch.set_num_threads(1)` и запас от порога |
| Python 3.14 | работает (после починки `dawg_python`) | колёса `cp314` у torch 2.13 есть, но связка torch+transformers+gliner на 3.14 в проекте не проверялась |
| Что даёт сверх | — | zero-shot метки: пользовательский тип описывается словами, без регулярки |

**Статус: сейчас не берём, но и не закрываем.** Цифры выше — материал для
решения, а не сам приговор. Спорить с ними бессмысленно (заказчику нужен
полностью локальный контур и «легковесность» из `docs/BRIEF.md`, а это
гигабайты и скачивание с HuggingFace при первом запуске), но и решать «никогда»
до того, как измерено качество Natasha, — гадание.

Точка расширения при этом уже есть и ничего не стоит: `EntityDetector` из
`detect/base.py` — Protocol с одним методом, `GlinerDetector` подключается
экземпляром в `default_detectors()` и записью в реестре. Ни `model.py`, ни
`DetectAgent`, ни формат `masker.types.yaml` при этом не меняются. Поэтому
откладывание решения не создаёт долга.

### Какой замер решает

Вход для решения — **шаг 9 плана T1.3**, тест
`tests/masker/detect/test_ner_corpus.py`: он печатает precision/recall/FN/FP по
типам на размеченном корпусе после того, как отработали расширение спанов по
словарю организационно-правовых форм, стоп-лист ролевых слов и вырезание дыры.
То есть после того, как из Natasha выжато всё, что выжимается детерминированно
и бесплатно. Правило чтения этих цифр:

| Что показал корпусный тест T1.3 | Вывод по GLiNER |
|---|---|
| `recall(org_name) >= 0.90` и `recall(person) >= 0.90` при `precision >= 0.90` | GLiNER не нужен: 527 МБ torch ради нескольких процентов — плохая сделка. Закрыть вопрос. |
| `recall` 0.75–0.90, и большинство FN — **границы** спана (нашли, но обрезали) | GLiNER не нужен: границы чинятся словарём и правилами, а не другой моделью. Расширять словарь. |
| `recall < 0.75`, и большинство FN — **пропуски целиком** (организация или ФИО не найдены вообще) | Вот здесь GLiNER имеет смысл: это ровно то, что zero-shot делает лучше, а правилами не лечится. |
| Дефицит только на пользовательских типах, а не на `org_name`/`person` | GLiNER не нужен: пользовательские типы закрыты литералами, регуляркой и LLM-арбитром. |

Дополнительное условие независимо от цифр: пока не проверено, что связка
torch + transformers + gliner собирается и работает на Python 3.14, никакого
GLiNER быть не может — это проверяется одной командой в отдельной ветке, а не
в `feat/detect-ner`.

### Условия подключения, если решение будет «да»

Записываются сразу, чтобы не обсуждать их второй раз: отдельный extra
`[gliner]`, никогда не в `dev`; импорт `gliner` только внутри
`GlinerDetector.__init__`, никогда на уровне модуля; веса предзагружаются в
каталог репозитория скриптом, тесты идут с `HF_HUB_OFFLINE=1`; тесты —
`pytest.importorskip("gliner")` плюс маркер `models`; `torch.set_num_threads(1)`
и порог с запасом, иначе пороговые решения поплывут между машинами; `make gate`
не имеет права скачать ни байта — проверяется прогоном с отключённой сетью.

## Что происходит со `SKILL.md`

`.dsh/skills/add-entity-type/SKILL.md` **не заменяется**. Он описывает
добавление *встроенного* типа, а это по-прежнему шесть мест — и должно ими
остаться: встроенный тип обязан иметь контрольную сумму или регулярку в коде
проекта, разметку в корпусе, порог в воротах и, возможно, место в
`CRITICAL_TYPES`. Скилл получает преамбулу:

> Сначала ответь на вопрос: это тип для всех или для одного заказчика?
> Если для одного («замазать даты отгрузки в этом договоре») — кода не трогай,
> опиши тип в `masker.types.yaml` (см. `docs/plans/T1.13-entity-type-registry.md`).
> Шесть шагов ниже — только для встроенных типов, которые становятся частью
> продукта и попадают в метрики ворот.

Плюс в шаге 1 скилла уточнение: новый член `EntityType` теперь обязан получить
`EntityTypeSpec` в `builtin_specs()` — там же `title` для отчёта, что закрывает
бывший шаг 6 (человекочитаемое имя) одним местом вместо двух.

## Что уже решено и что осталось

Решено человеком, обсуждению в ходе работы не подлежит:

1. **Реестр плюс `Entity.type: str`** — принято. `EntityType` и
   `CRITICAL_TYPES` остаются как перечень встроенных типов. Правка `model.py`
   санкционирована; список потребителей в разделе выше — исчерпывающий, кодер
   обязан пройти его целиком.
2. **GLiNER** — решение отложено до конца T1.3 и принимается по цифрам
   корпусного теста (таблица правил чтения выше). В T1.13 кода GLiNER нет.

Осталось открытым:

3. **Критичность пользовательских типов.** Разрешать ли `critical: true`?
   Разрешено в этом плане, но это значит, что пользовательская регулярка
   получает право уронить ворота проекта. Альтернатива — запретить и
   документировать, что критичность назначает только команда.
