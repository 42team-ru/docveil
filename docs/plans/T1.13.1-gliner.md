# T1.13.1 — GLiNER2 как executor пользовательских типов

Вынесено из T1.13 решением пользователя. Основной план —
`docs/plans/T1.13-custom-types-rest.md`; предпланирование и обоснования —
`docs/plans/T1.13-design-notes.md`; эмпирика — `backend/spikes/gliner_ru/`.

## Решение в одном абзаце

Одна модель `fastino/gliner2-privacy-filter-PII-multi` (Apache-2.0, M4 в
спайке) подключается как ещё один `EntityDetector` за уже существующим
протоколом и обслуживает **только пользовательские типы** классов C
(семантическая категория: «должность», «наименование товара») и D (роль
поверх формата: «дата отгрузки» против «даты подписания»). Встроенные
`person`/`org_name`/`location` она не трогает — спайк показал, что на них она
Natasha не бьёт, а по `org_name` проигрывает вдвое. Модель живёт за extra
`[gliner]`, импортируется лениво внутри
`GlinerDetector.__init__`, веса берёт **только** из локального каталога и
никогда не качает их сама; единственное место, которому позволено ходить в
HuggingFace, — `scripts/warm_gliner.py`. `make gate` после этой задачи обязан
проходить в сетевой изоляции — это проверяется командой, а не обещанием.

---

## Зависимости и порядок

1. Сначала **T1.13** целиком (блоки A–C основного плана). Причина: GLiNER —
   это два новых executor'а в паспорте компилятора и две новые записи в
   `available_executors()`. Пока компилятора нет, подключать их некуда.
2. Шаг 14 (инфраструктура) можно делать параллельно с блоком C — он не
   трогает ни один файл компилятора. Шаги 15–18 идут строго после T1.13.
3. Шаг 18 (combo B) зависит от T1.3: без корпусных цифр по `org_name`
   сравнивать «до и после» не с чем.

## Отвергнутые альтернативы

**Заменить Natasha на GLiNER для встроенных типов.** Хендофф это предлагает,
спайк это опровергает: `person` 1.000 → 0.933, `org_name` 0.941 → 0.636 при
снятии постобработки. Отдельное направление после замеров, не здесь.

**Модель M2 `fastino/gliner2.5-multi-v1`.** README спайка рекомендует её —
ради идеального класса D (1.000 против 0.928). **Пользователь выбрал M4**, и
это совпадает с тем, что предлагал хендофф `docs/handoff/2026-09-02-detect-render-fixes.md`.
Обоснование выбора: M4 — специализированная PII-модель, ближе к предметной
области продукта, и в среднем по классу C сильнее (0.783 против 0.744).
Цена — 0.928 на классе D вместо 1.000; порог приёмки шага 17 (≥ 0.9)
берётся, но запас мал, поэтому замер на фикстуре класса D обязателен, а не
формален. Если замер на нашей фикстуре даст ниже 0.9 — это повод вернуться
к M2, а не понижать порог.

**Две модели (M2 + M4).** +1.2 ГБ, +9 с загрузки, выбор модели внутри
компилятора — ради разницы в 0.04 F1. При живом preview на компиляции
пользователь корректирует спеку дешевле, чем мы платим гигабайтами.

**Глобальный порог уверенности.** Разные типы стабильны на разных порогах:
у M4 `job_title` берёт пик на 0.3, `certification_number` — на 0.7,
`person` — на 0.7. Порог кладётся в спеку executor'а, компилятор его
выбирает.

**Ставить `torch` в основные зависимости.** `masker.detect` обязан
импортироваться без torch: иначе ворота, CLI и API тянут 527 МБ ради кода,
который в дев-петле не исполняется.

**Скачивание весов при первом `from_pretrained`.** Тихий сетевой вызов из
прод-кода в проекте, чья ценность — полностью локальный контур. Отсутствие
весов обязано быть явной ошибкой с именем каталога и командой разогрева.

## Шаги

### Шаг 14 — инфраструктура: extra, офлайн, разогрев весов

Файлы: `backend/pyproject.toml`, `backend/scripts/warm_gliner.py` (новый),
`backend/scripts/gate.sh`.

- extra `[gliner]`: `gliner2`, `peft`, `torch` (CPU-индекс). В `dev` не
  попадает никогда.
- маркер `gliner` в `pyproject.toml` рядом с `models` и `e2e`; в воротах
  `-m "not gliner"`.
- `scripts/warm_gliner.py` — единственное место, которому позволено ходить в
  HuggingFace. Качает `fastino/gliner2-privacy-filter-PII-multi` в
  `backend/models/gliner/` (каталог уже в `.gitignore` строкой
  `backend/models/`), печатает путь и суммарный размер.
- `scripts/gate.sh` экспортирует `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`.

**Приёмка:**
```bash
cd backend
HF_HUB_OFFLINE=1 .venv/bin/python -c "import masker.detect; print('ok')"
unshare -rn ./scripts/gate.sh     # или: strace -f -e trace=connect ./scripts/gate.sh
```
Первая команда работает на машине **без** torch. Вторая проходит все шаги
ворот в сетевой изоляции; ни одного `connect` наружу.

### Шаг 15 — `GlinerDetector`

Файлы: `backend/src/masker/detect/gliner.py` (новый),
`backend/tests/masker/detect/test_gliner.py` (новый).

`source = Source.NER`, `priority = 50` (как у Natasha — правила с
контрольной суммой остаются выше и `_carve` вычтет их спаны).
`import gliner2` — **внутри** `__init__`, не на уровне модуля. Путь к весам
— `MASKER_GLINER_PATH`; при отсутствии каталога `__init__` падает с
сообщением, содержащим путь и команду `scripts/warm_gliner.py`.

Восстановление смещений: GLiNER2 возвращает **тексты** спанов, не позиции —
адаптер ищет их через `str.find` (референс —
`spikes/gliner_ru/run_spike.py::_spans_from_label_texts`). При переносе
обязательно **отсортировать обход словаря меток**: в спайке он идёт в
порядке вставки, и это скрытая зависимость от порядка, которая ломает
детерминизм.

Детерминизм: `torch.set_num_threads(1)`, `model.eval()`, сортировка выхода
по `(segment_order, start, end, type)`.

**Приёмка:**
```bash
cd backend && MASKER_GLINER_PATH=models/gliner .venv/bin/python -m pytest -q -m gliner
```
Тесты: два прогона на одном документе дают идентичный список; сущность
проходит `DetectAgent._validate` (`entity.text` посимвольно равен срезу
сегмента); отсутствие каталога весов даёт понятную ошибку, а не
`OSError` из `transformers`; `masker.detect` импортируется без torch.

### Шаг 16 — executor'ы `gliner_label` и `gliner_structure`

Файлы: `backend/src/masker/typeconfig.py`,
`backend/src/masker/compile/` (модули компилятора из T1.13),
`backend/tests/masker/test_typeconfig.py`.

- `gliner_label` — `extract_entities(text, {label: description}, threshold=X)`,
  порог по умолчанию 0.3, значение — поле спеки.
- `gliner_structure` — `create_schema().structure(...).field(name, dtype,
  description)`. Для класса D и любых многополевых типов.
- Схема спеки требует **и метку, и описание**: спека класса C без описания
  отклоняется валидацией. Прямое следствие замера класса C на M4:
  S1 0.676 → S2 0.713 → S3 0.783.
- Паспорт executor'ов компилятора строится из **фактически доступных**:
  без установленного extra `gliner_*` в промпт не попадают и в
  `engine_capabilities` не возвращаются. Никакой мягкой деградации —
  молча непоискаемый тип есть утечка.

**Приёмка:**
```bash
cd backend && .venv/bin/python -m pytest -q tests/masker/test_typeconfig.py -k gliner
```
Тесты: `gliner_label` без описания отклонён с id типа в сообщении; порог вне
`[0, 1]` отклонён; без extra `available_executors()` не содержит `gliner_*`.

### Шаг 17 — фикстура класса D и замер

Файлы: `backend/scripts/make_fixtures.py`,
`backend/fixtures/labeled/contract_10_roles_dates.docx` и разметка рядом,
`backend/tests/masker/detect/test_gliner_corpus.py` (новый).

Документ, где одна и та же дата `12.02.2026` стоит один раз как дата
отгрузки и один раз как дата подписания — то есть формат неразличим, а роль
различна. Это ровно класс D — самое слабое место M4 (0.928) и потому
обязательный, а не формальный замер.

**Приёмка:**
```bash
cd backend && MASKER_GLINER_PATH=models/gliner .venv/bin/python -m pytest -q -m gliner -k corpus -s
```
F1 по `shipment_date` ≥ 0.9 (эмпирика спайка для M4 — 0.928, запас мал:
результат ниже 0.9 означает возврат к M2, а не понижение порога). Без extra тест
пропускается **с явной строкой** «пропущено: gliner не установлен», а не
молча — иначе отсутствие метрики выглядит как её наличие.

### Шаг 18 — combo B, только по замеру

Файлы: `backend/src/masker/detect/gliner_boundary.py` (новый, **если** замер
положительный).

`GlinerBoundaryExtender` расширяет границы ORG-спанов Natasha через GLiNER на
окне (референс — `spikes/gliner_ru/natasha_adapter.py`). Замер `org_name`
precision/recall на `fixtures/labeled/contract_pdf_02_school.pdf` до и после.

**Включать только если precision вырос и recall не упал.** На фикстуре спайка
combo B не дал ничего и стоил +44 мс — отрицательный результат тоже результат:
записать замер в этот файл и не включать. Ворота должны показать, что
`org_name` не деградировал.

**Приёмка:** таблица «до / после» с числами в этом плане; `make eval`
показывает `org_name` не хуже базовой линии.

### Шаг 19 — ворота

**Приёмка:** `make gate` = 0 (либо метрики красные ровно теми же цифрами,
что до задачи, если T1.3 к тому моменту ещё не закрыт), вывод целиком;
ворота проходят в сетевой изоляции.

## Риски

| Риск | Как проявится | Чем обнаруживается |
|---|---|---|
| torch 2.x + transformers + gliner2 не собираются на Python 3.14 | установка extra падает | шаг 14, до всякого кода; если так — задача останавливается и обсуждается смена интерпретатора для extra |
| Ворота ушли в сеть через `from_pretrained` | зелёные ворота на машине разработчика, красные на стенде без интернета | `unshare -rn ./scripts/gate.sh` |
| Пороговые решения плывут между машинами | тест то зелёный, то красный | `torch.set_num_threads(1)`, порог с запасом от границы |
| 200 мс/сегмент × 500 сегментов = 2 минуты на документ | демо «висит» | GLiNER работает только по типам, которые его запросили, а не по всему документу; замер скорости — часть шага 15 |
| Веса 1.1 ГБ попали в git | репозиторий распух необратимо | `backend/models/` в `.gitignore`; шаг 14 проверяет `git status` после разогрева |
| Компилятор выбрал GLiNER там, где хватает regex | лишние 200 мс/сегмент и F1 0.75 вместо 1.0 | паспорт executor'ов прямо предписывает regex для явных ID-шаблонов |
| Класс D на нашей фикстуре не дотянул до 0.9 | шаг 17 красный | у M4 запас всего 0.028 — план заранее говорит, что делать: возврат к M2, а не правка порога |
