# T1.14 — ADDRESS: сборка адреса правилом

Постановка — `TASKS.md`, раздел T1.14. Здесь: как именно собирается спан,
почему адрес не живёт в `rules.py`, чем доказывается исчезновение
`person 'Жукова'` и где метрика могла бы соврать.

## Решение в одном абзаце

Появляется отдельный детектор `AddressDetector`
(`src/masker/detect/address.py`, `source=RULE`, `priority=90`), а не новая
запись в `rules.PATTERNS`: адрес — это сборка из нескольких компонентов, а не
одна регулярка с контрольной суммой, и внутренний `rules.resolve_overlaps`
выбрасывает проигравшего целиком, чего для адреса нельзя. Словарь маркеров —
данные (`src/masker/detect/data/address_markers.yaml`), как словарь
организационно-правовых форм в T1.3. Спан считается **достаточным для маскирования**, если в
нём есть почтовый индекс или пара «населённый пункт + улица/дом»; такой спан
выпускается с уверенностью 0.9. Слово «полный» здесь не годится: измеренный
кусок `309512, Белгородская область, г. Старый Оскол,` — это половина адреса,
но индекс с городом уже идентифицируют человека, и маскировать их надо.
**Недостаточный** (регион и/или город без индекса, улицы и дома) выпускается
с уверенностью 0.5 **только** при явной метке
(«Адрес», «Место нахождения», «зарегистрирован») — и уходит судье, потому что
`address` не входит в `CRITICAL_TYPES`. Голое упоминание города («г. Воронеж,
15 января 2026 г.») не выпускается ничем. LOC от Natasha используется только
как дополнительный сигнал уверенности, спан по нему не строится.

Включение таблиц показало то, чего в первом замере не было видно: **адрес в

|---|---|
| `("table", 0, 0, 0, 4)` | `адрес регистрации по месту жительства:` |

| `("table", 0, 0, 0, 6)` | `мкр. Жукова, д. 20, кв. 15` |

Это переносы строк внутри одной ячейки, а не разные поля. Последствия для
конструкции — в разделе «Адрес, разорванный границей абзаца». Там же
измеренное состояние FP: `person 'Жукова'` живёт в сегменте 6 и после T1.11
попал в отчёт (10 сущностей, из них одна ложная).

Отсюда три вывода, определяющие конструкцию:

1. Индекс, дом, корпус, квартиру Natasha не отдаёт **никогда**. Спан строит
   правило.
2. Маркеры встречаются без точки и в сокращённой форме: `г Воронеж`,
   `пер Здоровья`, `д 86а`, `мкр. Жукова`. Регулярка обязана принимать обе
   формы, и «ул.» в адресе может отсутствовать вовсе.
3. `мкр. Жукова` даёт ложное `PER 'Жукова'` — это ровно тот FP, который
   правило обязано поглотить.

Текущие метрики корпуса: `person` P=R=0.909, `org_name` P=R=1.0, критичные
1.0; `address` в корпусе отсутствует — есть тест `test_no_address_in_corpus`,
который это фиксирует и в этой задаче обязан быть **заменён**, а не удалён.

## Почему поглощение «Жукова» произойдёт — трассировка, а не надежда

`DetectAgent._resolve_overlaps` (`src/masker/detect/agent.py:59`) сортирует
кандидатов по `(-detector.priority, -confidence, -length, type, …)`:

1. `rules` (priority 100) → приняты;
2. `AddressDetector` (90) → адресный спан `[0, 73)` принят (не пересекается ни
   с чем из правил, см. «стоп-метки»);
3. `natasha` (50) → `PER 'Жукова' [52, 58)` пересекается с принятым адресом.
   Кандидат не `Source.RULE`, поэтому идёт в `_carve`
   (`agent.py:88`): из `[52, 58)` вычитается `[52, 58)`, фрагментов не
   остаётся, `carved == []`. Сущность исчезает.

Условие корректности одно: адресный спан обязан **включать** `мкр. Жукова`.
Если правило остановится на «г. Старый Оскол», `PER 'Жукова'` выживет.
Поэтому тест ставится не на «адрес найден», а на **отсутствие** `person` в
этом сегменте — исчезновение FP доказывается, а не предполагается.

## Контракт детектора

```python
# src/masker/detect/address.py
class AddressDetector:
    name = "address"
    source = Source.RULE
    priority = 90                      # ниже checksum-правил, выше NER
    types = frozenset({EntityType.ADDRESS})

    def __init__(self, tagger: NerTagger | None = None) -> None: ...
    def detect(self, document: Document) -> list[Entity]: ...
```

- `priority=90`, а не 100: адрес собран эвристикой, у него нет контрольной
  суммы, и при конфликте с ИНН/счётом побеждать должен реквизит. Выше NER —
  чтобы работало поглощение из предыдущего раздела.
- Детектор возвращает **непересекающиеся** спаны: сканирование
  «крайний левый — самый длинный», после принятия спана поиск продолжается с
  его конца. Иначе два адресных кандидата подерутся в `_resolve_overlaps`
  и результат станет зависеть от порядка.
- Сигнатуры в `src/masker/model.py` не меняются: `EntityType.ADDRESS` уже есть.

## Алгоритм сборки (детерминированный, слева направо)

Внутри **одного сегмента**. Сборка через границу абзацев вне скоупа — в
реальных документах «Адрес:» и сам адрес иногда стоят в разных абзацах ячейки;
это честно уходит в `limitations`, а не притворяется решённым.

1. Сегмент режется на чанки по запятым и точкам с запятой (позиции
   сохраняются — спан обязан оставаться смещениями исходного текста).
2. Чанк помечается компонентом, если он содержит:
   - `index` — `(?<!\d)\d{6}(?!\d)`;
   - `region` — «обл.», «область», «край», «респ.», «республика», «р-н», «район», «АО»;
   - `settlement` — «г.», «гор.», «город», «пос.», «п.», «с.», «ст.», «ст-ца»,
     «мкр.», «микрорайон», «снт», «д.» *(только если следующий токен начинается
     с буквы — иначе это дом)*;
   - `street` — «ул.», «улица», «пер.», «переулок», «пр-т», «просп.»,
     «проспект», «пр-д», «проезд», «наб.», «набережная», «ш.», «шоссе»,
     «б-р», «бульвар», «туп.», «аллея», «линия», «кв-л»;
   - `building` — «д.», «дом», «влд.», «корп.», «корпус», «стр.», «строение»,
     «лит.», «литера» *(либо чанк, начинающийся с цифры, если предыдущий чанк
     был `street`)*;
   - `premises` — «кв.», «квартира», «оф.», «офис», «пом.», «помещение», «комн.».
3. Точка после маркера **необязательна** (`г Воронеж`, `д 86а`). Маркер
   `settlement`/`street` засчитывается, только если за ним идёт слово с
   заглавной буквы; это отсекает «2026 г.» и «в 2025 г.».
4. Спан растёт вправо, пока следующий чанк — компонент или продолжение
   компонента. Останов: чанк со **стоп-меткой**, конец предложения, конец
   сегмента.
5. Классификация: **полный** — есть `index`, либо есть `settlement` и
   (`street` или `building`). Иначе — **частичный**.
6. Обрезка краёв по пунктуации и пробелам; спан не должен начинаться с
   метки-подписи («Адрес:» в спан не входит — маскируется значение, не подпись).

## Стоп-метки: адрес не имеет права проглотить реквизит

Стоп-список (данные): «ИНН», «КПП», «ОГРН», «ОГРНИП», «СНИЛС», «БИК», «р/с»,
«к/с», «счёт», «счет», «тел», «телефон», «e-mail», «email», «паспорт»,
«выдан», а также любой чанк, содержащий подряд ≥ 6 цифр, кроме индекса в
начале спана.

Зачем: если адресный спан накроет валидный ИНН, `_resolve_overlaps` увидит
пересечение двух `Source.RULE`-кандидатов и **выбросит** проигравшего целиком
(`agent.py:79`, `if entity.source is Source.RULE: continue`). При
`priority=90` проигравшим будет адрес — потеря адреса. При `priority=100` и
большей длине проигравшим мог бы оказаться **ИНН** — это утечка критичного
типа. Ни один из исходов не годится, поэтому пересечение не допускается по
построению и проверяется тестом.

## Частичный адрес и место рождения — принятые решения

**Частичный** = регион и/или населённый пункт без улицы и дома. Выпускается
с `confidence=0.5` только при метке слева в пределах 60 символов: «адрес»,
«место нахождения», «местонахождение», «зарегистрирован», «проживающ»,
«почтовый». Без метки не выпускается ничего.

Почему не «выпускать всегда с низкой уверенностью»: в договоре город
упоминается в преамбуле, в названии суда, в реквизитах банка. Каждое такое
упоминание превратилось бы в вопрос человеку, а инвариант требует одной пачки
вопросов, а не допроса. Почему не «не выпускать вовсе»: тогда «Адрес: г.
Воронеж» (без дома, встречается) уходит в документ открытым текстом.

**Место рождения** («гор. Старый Оскол Белгородской обл.») этим правилом
как `ADDRESS` **не покрывается**. Три причины:

1. Семантика другая. Маркер строится от профиля и роли
   (`[ПРОДАВЕЦ-АДРЕС]`), и «место рождения: [ПРОДАВЕЦ-АДРЕС]» читается как
   адрес проживания. Обезличенный договор обязан остаться читаемым — это
   инвариант, а не вкусовщина.
2. Структурно это частичный адрес без улицы и дома, и триггера «адрес» рядом
   нет — под правилом выше он не выпускается, FP не создаёт.
3. Механизм для него — тот же, что у даты рождения: метка-триггер плюс спан
   справа. Он появится в T1.16 (`birth_place`) вместе со своим маркером.

До T1.16 место рождения — **известная непокрытая ПДн**: строка в
`limitations` отчёта и запись в `TASKS.md`. Молча не покрывать нельзя.

## Адрес, разорванный границей абзаца

Измерено на реальном договоре (см. выше). `Entity.start/end` локальны сегменту
по контракту `model.py`, поэтому одна сущность через границу абзаца
**невозможна** — и не нужна. Требования:

1. Каждая половина обязана ловиться **сама по себе**, иначе одна из них
   утечёт. Проверка по алгоритму: сегмент 5 достаточен по индексу; сегмент 6
   достаточен по паре «`мкр.` + `д. 20`» (маркер `building`, потому что за
   `д.` идёт цифра). Обе половины выпускаются, `person 'Жукова'` поглощается
   именно на второй. Это и есть тест.
2. **Метка-триггер ищется не только внутри сегмента.** «адрес регистрации по
   месту жительства:» стоит в отдельном абзаце той же ячейки. Правило:
   контекст для недостаточного спана — предыдущие непустые сегменты **той же
   ячейки** (или предыдущий сегмент тела), не более двух, и только если они
   заканчиваются двоеточием или являются подписью-меткой. Дальше по документу
   не ходить: чем шире окно, тем случайнее срабатывание.
3. Склейка двух половин в один маркер — **не задача детекции**. Две сущности
   `address` подряд в одной ячейке склеивает `PlanAgent` (T1.6) на уровне
   профиля; до T1.6 в документе будет два маркера подряд, и это честно видно
   в отчёте. Записать в `limitations`.

## LOC как сигнал, а не как спан

Отдельный шаг (можно выкинуть, если не окупится):

- LOC **никогда** не создаёт сущность и не задаёт границы спана;
- LOC внутри частичного спана поднимает уверенность 0.5 → 0.7;
- LOC, не попавший ни в один адресный спан, не даёт ничего (ровно как
  сейчас — см. `NatashaDetector`, метка LOC игнорируется).

Стоимость: второй прогон модели по тем же сегментам. Чтобы не платить дважды,
`natasha_tagger()` оборачивается мемоизацией по тексту сегмента
(`functools.lru_cache` на методе-обёртке, размер ограничен), и в
`default_detectors()` в `NatashaDetector` и `AddressDetector` передаётся
**один и тот же** объект теггера. Кэш — по значению текста, не по `id`,
иначе результат зависит от сборки мусора.

## Поля отчёта, которые обязаны измениться

| поле | было | стало |
|---|---|---|
| `detection_coverage.active_detector_types` | из `PATTERNS` ∪ `LABEL_TO_TYPE` | объединение `detector.types` реально собранного набора |
| `detection_coverage.requested_without_detector` | `[address, bank_name, contract_number, date, money]` | `[bank_name, contract_number, date, money]` |
| `limitations` | — | + «Адрес собирается в пределах одного абзаца», + «Место рождения не покрыто (T1.16)» |
| `document_coverage.safe_to_export` | `false` | `false` |

`--rules-only` теперь означает «набор из `RuleDetector` и `AddressDetector`»
(обе — `Source.RULE`, обе офлайн и без модели); LOC-сигнал в этом режиме
выключен. Это надо явно проверить тестом, иначе `requested_without_detector`
в двух режимах разъедется.

### Шаг 2а — адрес, разорванный границей абзаца

## Где метрика могла бы соврать

1. **Recall выше фактического.** Если частичный спан («г. Воронеж») будет
   выпускаться под тем же типом, а в разметке лежит полный адрес, то пара
   `(файл, текст)` не совпадёт — это FP, а не TP. То есть завысить recall
   частичными спанами технически невозможно, зато **precision** просядет
   честно. Именно поэтому частичный выпускается только по метке.
2. **Разметка под правило.** Единственная реальная опасность. Контрмера —
   порядок шагов: разметка (шаг 8) содержит два случая, которых первая
   реализация правила скорее всего не поймает (дом без маркера, район без
   города).
3. **Пары `(файл, значение)`.** Два одинаковых адреса в теле и в ячейке дают
   одну пару. Проверка по вхождениям введена в T1.11 для критичных типов;
   `address` в неё не входит и не должен — он не критичный. Не выдавать
   «recall 1.0 по адресу» за «ни один адрес не утёк»: это разные утверждения.

## Детерминизм: где он может протечь

- Порядок альтернаций в регулярке зависит от порядка ключей YAML → явная
  сортировка по длине и алфавиту.
- Мемоизация теггера по `id(text)` вместо значения → плавающие результаты.
  Только по значению.
- Два адресных кандидата, пересекающихся между собой, разрешались бы через
  сортировку агента с ключом по имени детектора — формально стабильно, но
  зависит от длины и уверенности. Детектор обязан отдавать непересекающиеся
  спаны сам.
