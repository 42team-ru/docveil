# T1.2 — DetectAgent: правила и агрегированные PII-чанки

## Цель

Слой правил по-прежнему находит и валидирует все формальные сущности из
`EntityType`. Но его результатом для последующих контекстных стадий будет не
«одна сущность — один фрагмент текста», а список непересекающихся чанков.
Каждый чанк содержит текстовую окрестность и все PII, найденные в ней.

Пример: при последовательности `ИНН → КПП → ОГРН → счёт` в реквизитах
поставщика должен получиться один чанк с четырьмя `Entity`, а не четыре почти
одинаковых фрагмента, отправленных в ProfileAgent/LLM.

## Подключаемый интерфейс DetectAgent

Regex — первая реализация, а не особый случай. Вводится общий контракт
детектора в `masker.detect.base`; для подключения новой технологии достаточно
реализовать один метод и зарегистрировать экземпляр в конфигурации агента.

```python
class EntityDetector(Protocol):
    name: str
    source: Source
    priority: int

    def detect(self, document: Document) -> list[Entity]: ...
```

Контракт намеренно принимает целый `Document`, а не одну строку: regex-слою
нужны соседние сегменты для проверки счёта по БИК, а модельным детекторам
доступны и `Document.text()`, и якоря, необходимые для перевода глобальных
смещений обратно в `segment_order/start/end`. Каждый детектор обязан вернуть
только `EntityType`, `Source` и локальные смещения из общего `model.py`;
внутренние метки модели (`PER`, `ORG`, произвольные GLiNER labels) наружу не
выходят.

Реализации и их ответственность:

| Реализация | `name` / `source` | Что делает |
|---|---|---|
| `RuleDetector` | `rules` / `RULE` | Адаптирует текущий `detect_by_rules(document.segments)`, включая checksum и БИК |
| `NatashaDetector` | `natasha` / `NER` | Преобразует `PER`/`ORG`/`LOC` в `PERSON`/`ORG_NAME`/`ADDRESS` и сохраняет спаны Natasha |
| `GlinerDetector` | `gliner` / `NER` либо новый `Source.MODEL` при необходимости аудита | Передаёт настраиваемый набор русских меток и порог, преобразует ответ модели в `Entity` |

Natasha действительно выдаёт позиционные `start`/`stop` спаны через `Doc.spans`;
GLiNER загружает модель через `GLiNER.from_pretrained(...)` и получает метки с
порогом в `predict_entities`. Поэтому оба естественно укладываются в этот
контракт, но загрузка модели происходит в конструкторе/фабрике детектора один
раз на процесс — не внутри `detect` и не для каждого чанка.

У детектора нет права создавать чанки, принимать решение по конфликтам или
мутировать `Document`: это гарантирует одинаковое поведение для regex, Natasha,
GLiNER и следующих реализаций.

## Оркестрация и контракт результата

`DetectAgent` (например, `DetectionOrchestrator`) получает упорядоченный
список внедрённых `EntityDetector`, а не импортирует конкретные модели. По
умолчанию регистрируется только `RuleDetector`; подключение Natasha/GLiNER —
явная конфигурация приложения и зависимость в extras, чтобы T1.2 не требовал
скачивать модели или добавлять тяжёлые пакеты.

Добавляется общий результат в `masker.detect.result`:

```python
@dataclass(slots=True)
class PiiChunk:
    segment_order: int
    start: int              # [start, end) внутри Segment.text
    end: int
    entities: list[Entity]  # все Entity с полностью покрытым спаном

@dataclass(slots=True)
class DetectionResult:
    entities: list[Entity]
    chunks: list[PiiChunk]
```

`DetectAgent.detect(document) -> DetectionResult` запускает все зарегистрированные
детекторы, валидирует их результаты, разрешает пересечения и только затем
однократно строит чанки. Следующий шаг использует `entities` для профилирования,
а `chunks` — для контекстной эвристики и LLM. Текст чанка не дублируется:
потребитель получает его как
`segments[chunk.segment_order].text[chunk.start:chunk.end]`.

Перед merge оркестратор проверяет все ответы плагина: `segment_order` существует,
`0 <= start < end <= len(segment.text)`, а `entity.text` посимвольно равен
указанному спану. Ошибка контракта детектора должна падать с именем детектора;
некорректный спан нельзя молча отбросить, иначе получится утечка.

Конфликты разрешаются централизованно и детерминированно: сначала приоритет
детектора (правила выше NER/GLiNER), затем `confidence`, длина спана, тип и
координаты. Принятая сущность блокирует пересекающийся менее приоритетный спан.
Так ИНН внутри широкого `ORG_NAME` остаётся `INN`; при одинаковой реализации
модели выбор стабилен между запусками.

На T1.2 чанк не пересекает границу `Segment`: якорь рендера и все смещения
`Entity` уже локальны к сегменту. Склейка соседних абзацев — отдельное
архитектурное решение, а не неявный эффект группировки.

## Алгоритм построения чанков

Константы выносятся в один модуль и покрываются тестами:

- `CHUNK_TARGET = 300` символов;
- `CHUNK_MIN = 200` символов;
- `CHUNK_MAX = 500` символов.

Для каждой сущности после `resolve_overlaps`, в порядке
`(segment_order, start, end)`, строится её желаемая окрестность:

1. центрировать окно длиной `CHUNK_TARGET` на спане PII;
2. сдвинуть его к началу/концу сегмента, чтобы сохранить целевую длину;
3. если сегмент короче `CHUNK_MIN`, взять весь сегмент; если сама сущность
   длиннее окна, взять её целиком; никогда не выходить за `[0, len(text)]`.

Для очередной сущности алгоритм смотрит только на последний чанк того же
сегмента.

1. Если её спан пересекает текущие границы чанка (`entity.start < chunk.end`
   и `chunk.start < entity.end`), сущность добавляется в `chunk.entities`.
   Границы расширяются до объединения текущего окна и её желаемой окрестности,
   только если итоговая длина не превышает `CHUNK_MAX`.
2. Если объединение шире `CHUNK_MAX`, чанк не растягивается: создаётся новый
   чанк вокруг текущей сущности. Это жёсткий предохранитель от превращения
   длинного блока реквизитов в один неконтролируемый prompt.
3. Если спан не пересекает текущий чанк, создаётся новый чанк вокруг сущности.

После прохода соседние чанки, которые пересеклись из-за расширения, сливаются
только если их объединённая длина не больше `CHUNK_MAX`; списки `entities`
сливаются, дубликаты исключаются по `(segment_order, start, end, type)`.

Таким образом, фраза «следующий PII попал в предыдущий чанк» означает именно
агрегацию в этот же `PiiChunk`, а не создание второй копии контекста. Порядок
и результат детерминированы.

## Изменения в слое правил и дальнейшее расширение

1. Оставить регулярные выражения, checksum-валидацию БИК/счёта и
   `resolve_overlaps` единственным источником истинных `Entity`.
2. Обернуть текущую функцию в `RuleDetector`; `detect_by_rules` временно
   оставить как обратносуместимый публичный helper для существующих тестов и
   потребителей.
3. Вынести построение чанков в чистую функцию
   `build_pii_chunks(segments, entities) -> list[PiiChunk]`; она не запускает
   регулярки и не меняет входные объекты.
4. Добавить `DetectAgent.detect(document)`, возвращающий единый
   `DetectionResult`; именно он строит чанки после merge всех реализаций.
5. Не вкладывать в чанк кандидаты, отброшенные checksum-валидатором или при
   разрешении пересечений: например, СНИЛС внутри расчётного счёта не должен
   попасть в контекст отдельным PII.
6. Natasha/GLiNER не вызываются из `rules.py`; добавление новой реализации
   меняет только её модуль, точку композиции и собственные тесты. Общий merge,
   чанки и контракт `Entity` остаются нетронутыми.

## Тесты

Добавить `tests/test_rule_chunks.py` с синтетическими `Segment` и следующими
кейсами.

| Сценарий | Ожидаемый результат |
|---|---|
| Один валидный ИНН в длинном сегменте | один чанк 200–300 символов (если позволяют границы), один `Entity` |
| ИНН и ОГРН, второй спан попадает в первый чанк | один чанк, оба `Entity`, границы расширены при необходимости |
| Три PII в реквизитах, итоговое объединение ≤500 | один чанк, все три PII в порядке текста |
| PII за границей текущего чанка | два чанка без пересечения и без дублирования PII |
| Расширение превысило 500 символов | два чанка; первый не изменён сверх лимита |
| Сегмент короче 200 символов | чанк равен всему сегменту |
| Одинаковые/перекрывающиеся кандидаты после `resolve_overlaps` | PII в чанке не дублируется; победившая сущность сохраняется |
| Счёт и БИК | оба попадают в общий чанк, checksum-правило счёта не меняется |
| Сущности в соседних сегментах | разные чанки, даже при малом расстоянии по `order` |

Для каждого чанка проверять инварианты: границы валидны, размер не больше
500 (кроме единичной сущности длиннее лимита), список `entities` отсортирован,
и каждый спан `Entity` полностью лежит в границах своего чанка.

Добавить `tests/test_detect_orchestrator.py`:

- два тестовых детектора через внедрение зависимостей подтверждают порядок
  вызовов и то, что их сущности проходят единый merge и попадают в общий чанк;
- сущность `RULE` внутри более широкого модельного `ORG_NAME` сохраняет правило;
- некорректный `Entity` от плагина завершает выполнение диагностической ошибкой;
- пустой список/только `RuleDetector` не импортирует Natasha и GLiNER;
- фейковый Natasha/GLiNER-адаптер доказывает, что оркестратор не зависит от
  классов конкретной библиотеки.

Тесты реальных адаптеров не скачивают модели: их публичный API подменяется
stub/mock. Отдельные smoke/E2E-тесты с настоящими моделями помечаются `e2e`.

## Приёмка

1. Все прежние проверки T1.2 сохраняются: регулярки на типы из `EntityType`;
   для ИНН, ОГРН, СНИЛС, счёта и БИК — соответствующая проверка; `make eval`
   показывает recall = 1.0 по критичным типам и precision ≥ 0.95.
2. Новый тест на блок реквизитов доказывает, что ИНН, КПП, ОГРН и счёт,
   попавшие в одно окно до 500 символов, возвращаются одним чанком со всеми
   четырьмя PII.
3. Тест на расстояние/лимит доказывает, что далёкие реквизиты не склеиваются,
   а ни один сформированный обычный чанк не превышает 500 символов.
4. Новый тестовый детектор подключается без изменения `DetectAgent`,
   `build_pii_chunks` и кода `RuleDetector`; приоритет правила над моделью
   доказан отдельным тестом.
5. `make gate` завершается с кодом 0; в сдаче приложен полный вывод.
