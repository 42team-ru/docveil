# T1.4 — ProfileAgent (структурная кластеризация + задел на T3.2 «роли»)

## Решение в одном абзаце

Между `PiiChunk` и профилем вводится **второй уровень группировки — блок**
(`ContextBlock`): непрерывный участок документа, ограниченный структурными
признаками (заголовок, ролевая метка, преамбульная формула, разрыв без PII).
Блок собирается из *спанов* — кусков сегментов, а не из целых сегментов,
поэтому он умеет и склеивать соседние абзацы («Реквизиты Поставщика» + счёт +
БИК + телефон), и резать один абзац на две стороны (типовая преамбула
«…, именуемое Поставщик, … и …, именуемое Покупатель, …»). Блоки сливаются в
профили по идентификационным ключам (ИНН → ОГРН → ролевая метка → название
организации) через union-find. Всё это — без модели. LLM получает **один
запрос на документ** только на блоки, которые не слились ни с чем и не имеют
ролевой метки; чанки при этом используются как источник текста для промпта.

## Ответ на вопрос про `build_pii_chunks`

**Не трогаем.** Ни алгоритм, ни контракт `PiiChunk`. Три причины:

1. `PiiChunk.start/end` — смещения внутри `Segment.text`. На них завязан
   будущий рендер и LLM-арбитр (T3.3), которому нужно возвращать решения по
   спанам. Чанк, пересекающий границу сегмента, потребует другой модели
   смещений и сломает `tests/masker/detect/test_rule_chunks.py`.
2. Чанк строится **вокруг сущности**. Самый ценный контекст для профиля —
   сегменты, где сущностей нет вообще: «1. Реквизиты Поставщика»,
   «Поставщик: ______ И.И. Иванов». Расширение чанка на соседей их подхватит
   только случайно, по расстоянию; блок подхватывает их по смыслу, как
   границу.
3. Разные потребители — разный размер окна. Детекции нужны 300 символов,
   профилю нужен весь блок реквизитов. Смешивать это в одном контракте значит
   тюнить `CHUNK_TARGET` под две несовместимые цели.

Единственное изменение в `detect/result.py` — **аддитивная** чистая функция
`chunk_text(segment_text: str, chunk: PiiChunk) -> str`. Никаких изменений
сигнатур.

## Контракты

### `src/masker/model.py` (добавляется)

```python
class Role(StrEnum):
    SUPPLIER = "supplier"
    BUYER = "buyer"
    THIRD_PARTY = "third_party"
    UNKNOWN = "unknown"


@dataclass(frozen=True, slots=True)
class ProfileMember:
    entity: Entity
    anchor: Anchor  # приёмка T1.4: элемент профиля носит свой якорь


@dataclass(slots=True)
class Profile:
    id: str  # "P1", "P2" — по минимальному (order, start)
    role: Role
    members: list[ProfileMember]
    label: str = ""  # «поставщик» — как названо в документе
    role_confidence: float = 0.0
    role_source: Source = Source.RULE
    evidence: list[str] = field(default_factory=list)
```

`evidence` — человекочитаемые причины («заголовок «Реквизиты Поставщика»»,
«ИНН совпал с блоком B2», «LLM»). Это то, что уйдёт в отчёт T1.9 и что
показывают на защите.

### `src/masker/profile/blocks.py`

```python
@dataclass(frozen=True, slots=True)
class BlockSpan:
    segment_order: int
    start: int
    end: int


@dataclass(slots=True)
class ContextBlock:
    id: str  # "B1"
    spans: list[BlockSpan]
    entities: list[Entity]
    label: str = ""  # нормализованная ролевая метка или ""
    heading: str = ""  # текст открывающего заголовка или ""


def split_segments_into_spans(segments: list[Segment]) -> list[BlockSpan]: ...


def build_context_blocks(segments: list[Segment], entities: list[Entity]) -> list[ContextBlock]: ...


def block_text(segments: list[Segment], block: ContextBlock, chunks: list[PiiChunk]) -> str: ...
```

**Инвариант покрытия:** спаны одного сегмента без дырок и пересечений
покрывают `[0, len(text))`. Отсюда — каждая сущность принадлежит ровно одному
спану (по позиции `start`) и ровно одному блоку. Это гарантия «ни одна
сущность не потерялась на стадии профилей», проверяемая тестом.

### `src/masker/profile/agent.py`

```python
@dataclass(slots=True)
class ProfileResult:
    profiles: list[Profile]
    blocks: list[ContextBlock]
    llm_used: bool = False


class ProfileAgent:
    def __init__(self, llm: LLMProvider | None = None) -> None: ...

    def profile(self, document: Document, detection: DetectionResult) -> ProfileResult: ...
```

`profile()` — чистая функция от входа: без глобального состояния, без
обращения к файлам, единственный внешний эффект — не более одного вызова
`llm.complete`. Узел графа `profile` в T1.10 будет трёхстрочным адаптером:
`{"profiles": …, "blocks": …}` в `State`. Все возвращаемые типы — dataclass'ы
без ссылок на `Document`, иначе SQLite-чекпойнтер их не сериализует.

## Правила границ блока (детерминированные, в этом порядке)

Пре-пасс по сегментам режет их на спаны: если в тексте одного сегмента
встречаются **две и более различные** ролевые метки — режем по позициям
меток (типовая преамбула с двумя сторонами в одном абзаце).

Далее спаны идут по порядку `(segment_order, start)`, новый блок начинается
если:

- **B1** это первый спан документа;
- **B2** спан — заголовок: нумерованный («`^\d+(\.\d+)*\.?\s`»), либо короткий
  (≤ 80 символов) без завершающей точки, либо содержит стем «реквизит»,
  «подпис», «сторон», «адрес… и реквизиты»;
- **B3** спан начинается с ролевой метки в позиции подписи («Поставщик:»,
  «Покупатель:», «Заказчик:»…);
- **B4** спан содержит преамбульную формулу «именуем* в дальнейшем «X»»;
- **B5** накопился разрыв: ≥ `MAX_EMPTY_GAP` (=2) подряд спанов без сущностей,
  а текущий спан сущности содержит;
- **B6** предохранители: блок уже содержит `MAX_BLOCK_SPANS` (=12) спанов или
  `MAX_BLOCK_CHARS` (=4000) символов.

`MAX_EMPTY_GAP`, `MAX_BLOCK_SPANS`, `MAX_BLOCK_CHARS` — константы модуля, не
магические числа в коде.

## Правила слияния блоков в профили (union-find, порядок ключей фиксирован)

1. `K1` нормализованный ИНН (контрольная сумма уже проверена — сильнейший ключ);
2. `K2` нормализованный ОГРН;
3. `K3` ролевая метка блока («поставщик» ↔ «Реквизиты Поставщика» ↔
   «Поставщик: ___ И.И. Иванов»);
4. `K4` нормализованное название организации.

Ключ берётся из `entity.normalized`, если детектор его заполнил, иначе
считается `profile/keys.py`. Union-find даёт разбиение, не зависящее от
порядка обхода; `id` профиля назначается по возрастанию минимального
`(segment_order, start)` его членов, поэтому `P1` — всегда первый по тексту.

Роли (задел T3.2): метка блока → `Role` по таблице стемов
(поставщик/продавец/исполнитель/подрядчик → `SUPPLIER`;
покупатель/заказчик/арендатор/клиент → `BUYER`). Дополняющее правило: если
ровно два профиля имеют ролевые блоки и роль установлена только у одного —
второму ставится противоположная с `role_confidence = 0.7` и пометкой в
`evidence`. Профиль без метки получает `Role.UNKNOWN`, а **не** угаданную
роль: это прямое требование приёмки T3.2.

## Что уходит в LLM

Один вызов на документ, только если после структурной стадии остались блоки с
сущностями, у которых нет ни ключа для слияния, ни ролевой метки. Запрос
несёт: список профилей (id, метка, роль, ключевые сущности), список
неразрешённых блоков (id, заголовок, текст — собранный из чанков через
`chunk_text`, поэтому окна уже ограничены), список сущностей с короткими
ссылками `E1..En`. Ссылки нумеруются по отсортированному
`(segment_order, start, end, type)` — стабильны между прогонами.

Ответ строгий: для каждого неразрешённого блока `{block_id, profile_id | null,
role, confidence}` плюс роли профилей. Применение ответа может **только**
(а) присоединить неразрешённый блок к существующему профилю или создать
новый, (б) проставить роль. Ответ не может ни забрать сущность из
структурно установленного профиля, ни создать/удалить сущность. Невалидный
JSON, неизвестный `block_id`/`profile_id`, неизвестная роль — молча
игнорируются, структурный результат остаётся в силе, `llm_used=False`.
Падать нельзя: недоступная модель не должна ронять обезличивание.

## Шаг 12 — метрики профилей в воротах

**Файлы:** `src/masker/eval.py`, `tests/masker/test_gate_selftest.py`.
Метрики считаются напрямую по `ingest → detect → profile`, **не** дожидаясь
`masker.pipeline` (иначе шаг молча пропускается, как сейчас). Три числа:
`role_accuracy` — доля верных ролей среди сущностей в профилях с
установленной ролью (сверка с полем `party` в разметке); `role_coverage` —
доля размеченных и найденных сущностей, попавших в профиль с ролью;
`cluster_purity` — доля сущностей стороны, попавших в её основной профиль.

**Приёмка:** `make eval` печатает блок «профили» с этими тремя числами по
каждому документу и итогом; пороги `MIN_ROLE_ACCURACY = 1.0`,
`MIN_CLUSTER_PURITY = 1.0` для документов с ролевыми метками,
`MIN_ROLE_COVERAGE = 0.70` (в T3.2 поднимается до 0.90, о чём в коде висит
комментарий со ссылкой на задачу). Селф-тест ворот: подмена таблицы стемов на
пустую роняет `make eval --gate` ненулевым кодом.

# Детерминизм: где он может протечь

- Итерация по `set`/`dict` при сборке ключей и блоков. **Правило: наружу
  выходят только отсортированные списки**, ни один публичный результат не
  строится обходом множества. Ловится `test_request_is_byte_stable` и
  `test_agent.py::test_idempotent`.
- `id` профилей от порядка слияния в union-find. Лечится назначением `id`
  после кластеризации, по минимальному `(segment_order, start)`.
- LLM. Температура 0, фиксированный промпт, ответ влияет только на
  присоединение остатка и роли. В воротах `MASKER_LLM=fake`, живая модель —
  только в `@pytest.mark.e2e`. Цифры на защите берутся из прогона с `fake`.
- `str.lower()` по кириллице локале-независим — дополнительной защиты не
  требует, но нормализация должна быть в одном месте (`keys.py`/`labels.py`),
  а не размазана по модулям.
