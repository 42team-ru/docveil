# T1.5.1 — Человек в цикле: выбор типов и выбор профилей

Расширяет T1.5 и забирает из T1.10 то, без чего T1.5.1 не существует: сборку
`StateGraph`, `compile(checkpointer=SqliteSaver)` и проведение CLI через граф.

## 1. Что просит заказчик и что для этого нет в репозитории

Человек принимает **два независимых решения** до маскирования:

1. какие **типы** полей маскировать — интерактивно, увидев, что реально нашлось
   в документе, а не через `--types` при запуске;
2. какие **профили** (стороны) маскировать, а какие оставить в оригинале —
   «реквизиты Продавца замазать, Покупателя оставить».

Заявленное направление развития (дословно от пользователя): «в будущем хочу
чтоб пользователь мог выбирать что замазать прям по PII + сам выбирать какие
данные у него в документе это PII». Реализуется это не сейчас, но модель решений
проектируется сразу под него — см. раздел 4. Переписывать её второй раз нельзя.

Проверено на текущем дереве (ветка `feat/profile-judge`):

- `profile_node`, `judge_node`, `ask_human_node` (с `interrupt()`),
  `apply_answers_node`, `needs_human` — есть в `src/masker/graph/nodes.py`;
- `StateGraph` **нигде не собирается**: `grep -rn "StateGraph\|compile(" src/`
  даёт пусто, единственная сборка — в `spikes/langgraph_pipeline_spike.py`;
- `src/masker/cli.py::inspect_docx` зовёт `ProfileAgent(llm).profile(...)` и
  `JudgeAgent().judge(...)` напрямую, чекпойнтера в коде нет;
- `profile_node` создаёт `ProfileAgent()` **без LLM** — то есть даже если бы граф
  собирался, он работал бы не так, как CLI. Это шов, который надо закрыть здесь.

Значит «пауза, переживающая перезапуск процесса» из `AGENTS.md` сегодня не
существует, и центральная часть задачи — граф с чекпойнтером, а не диалог в
терминале.

## 2. Что проверено экспериментом на установленных версиях

`langgraph 1.2.11`, `langgraph-checkpoint 4.2.0`,
`langgraph-checkpoint-sqlite 3.1.1`, Python 3.14.4. Пробы гонялись на
одноразовом графе, результаты — не из документации, а из вывода.

| Факт | Следствие для плана |
|---|---|
| `invoke(...)` при паузе возвращает обычный словарь состояния плюс ключ `__interrupt__` со списком `Interrupt(value=…, id=…)` | наружу отдаём `value`, а не объект |
| `graph.get_state(config).interrupts` даёт тот же кортеж `Interrupt` **без повторного прогона узлов** | «показать вопросы ещё раз» делается через `get_state`, а не через повторный `invoke` |
| Повторный `invoke(<входные данные>, config)` на **приостановленном** треде запускает граф с START заново (счётчик вызовов узла вырос с 1 до 2) | повторный `--ask` обязан идти через `get_state`; иначе второй запуск заново позовёт детекцию и LLM |
| `invoke(Command(resume=…), config)` с **неизвестным** `thread_id` **не бросает исключение**, а запускает новый прогон с нуля и снова встаёт на паузе | CLI обязан сам проверять существование треда, иначе опечатка в id тихо превращается в новый прогон |
| `get_state` неизвестного треда: `next == ()`, `created_at is None`, `values == {}` | это и есть проверка существования треда |
| Повторный `Command(resume=…)` на **завершённом** треде возвращает прежнее финальное состояние, новые ответы игнорируются молча | второй ответ на тот же вопрос — ошибка уровня CLI/сервиса, а не graceful no-op |
| `Interrupt.id` **не детерминирован**: два прогона одного графа на чистых БД дали `cb97a744…` и `aea9c2fb…` | id прерывания не попадает ни в `questions.json`, ни в отчёт; возобновление идёт через `Command(resume=<значение>)`, а не через отображение id → значение |
| `SqliteSaver.delete_thread(thread_id)` существует и после него `get_state(...).created_at is None` | «свежий прогон» реализуется удалением треда, а не удалением файла БД |
| Узел с `interrupt()` при возобновлении выполняется **с начала** | `ask_human_node` обязан оставаться без побочных эффектов |

## 3. Критичные типы: решение принято (вариант A)

`AGENTS.md`: «Сущность из `CRITICAL_TYPES` маскируется молча при любой
уверенности и в `questions` не попадает», «пропущенный ИНН — это утечка».
Заказчик просит максимум контроля вплоть до отдельного PII. Прямой запрет
снятия отпадает: он ломает заявленное направление и делает выбор по профилю
(«Покупателя оставить целиком») наполовину фиктивным.

**Принято: снятие маски с критичного типа возможно, но только при двух
независимых подтверждениях.** Обоснование: контроль отдаётся человеку, но
случайным одним кликом утечку не сделать, а сам факт становится записью в
аудите, а не молчаливым поведением.

- инвариант судьи **не трогается вообще**: вопросы вида «маскировать ли эту
  конкретную сущность» по критичным типам как не задавались, так и не задаются
  (`Question.refs` по-прежнему не ссылается на критичную сущность);
- вопрос политики по критичному типу в пачку попадает (иначе человек не увидит,
  что ИНН вообще нашёлся), но в его `options` есть только «маскировать»;
- вариант «оставить» появляется в `options` только если прогон стартовал с явным
  флагом `--unmask-critical`, и тогда это отдельная строка
  `KEEP_CRITICAL_OPTION = "оставить (осознанное решение)"` — обычным «оставить»
  критичный тип снять нельзя;
- **то же правило действует для профиля**: ответ «оставить» на `PROFILE-*`
  снимает маску с некритичных сущностей субъекта, а его критичные реквизиты
  остаются замаскированными, пока нет обоих подтверждений; чтобы оставить
  сторону целиком, нужен `--unmask-critical` и ответ `KEEP_CRITICAL_OPTION` на
  вопросе профиля;
- каждое снятие громко пишется в отчёт (`decisions.critical_unmasked`), в
  `limitations` и красным баннером в HTML;
- `masker.eval --gate` держит метрику `critical_unmasked == 0` для
  неинтерактивного режима, чтобы ворота нельзя было пройти со снятым ИНН.

## 4. Модель решений: единица — ссылка на сущность

Это главный раздел плана. Он определяет, что будет лежать в `State`, в отчёте и
в контракте возобновления на годы вперёд.

**Единица решения — `ref` (`E1..En` из `masker/refs.py`), а не тип и не профиль.**
Выбор по типу и выбор по профилю — это *групповые операции*, порождающие набор
решений по ссылкам, а не самостоятельные сущности состояния. В `State` и в отчёт
ложится по одной записи на каждый `ref`:

```json
{"ref": "E7", "action": "keep", "decided_by": "type",
 "question_id": "TYPE-phone", "reason": "тип отключён человеком",
 "overridden": [{"decided_by": "judge", "action": "mask"}]}
```

Почему так, а не «список отключённых типов + список отключённых профилей»:
будущий выбор «прям по PII» — это ещё один источник решений по тем же `ref`;
ручная пометка «вот это тоже PII» — это новая сущность с новым `ref` и решением
`mask`. При ref-центричной модели оба расширения добавляют **только новый вид
вопроса**, не трогая ни `State`, ни контракт паузы, ни формат отчёта. При
модели «списки отключённых типов» пришлось бы переписывать всё перечисленное.

**Пространства ссылок** (детерминированные, непересекающиеся):
`E1..En` — сущности детекции, `C1..Cn` — кандидаты PII от модели (уже есть),
`H1..Hn` — **зарезервировано** за сущностями, размеченными человеком вручную;
в T1.5.1 `H*` не создаётся, но `EntityIndex` и сериализация обязаны терпеть
ссылку из чужого пространства, а не падать на ней. Это дешёвая страховка:
одна проверка в тесте сегодня против переписывания состояния завтра.

### Источники решений и порядок разрешения конфликтов

Побеждает более частное. Порядок фиксирован, задан константой
`DECISION_PRECEDENCE` и продублирован в докстринге `PolicyAgent.apply`:

| Приоритет | Источник (`decided_by`) | Откуда берётся | Может дать |
|---|---|---|---|
| 0 (жёсткий) | `critical_guard` | инвариант `CRITICAL_TYPES` без двойного подтверждения | только `mask` |
| 1 | `entity` | персональное решение по сущности: ответы `Q*` судьи сегодня, вопросы «по каждому PII» завтра | `mask` / `keep` |
| 2 | `profile` | ответ на `PROFILE-*` | `mask` / `keep` |
| 3 | `type` | ответ на `TYPE-*` | `mask` / `keep` |
| 4 | `judge` | вердикт судьи по уверенности | `mask` / `keep` |
| 5 | `default` | «маскировать» | `mask` |

Читается так: **персональное решение по сущности сильнее решения по её профилю,
решение по профилю сильнее решения по её типу.** Если человек отключил тип
`phone`, но персонально сказал «маскировать» про конкретный телефон — телефон
маскируется. Если человек оставил профиль `P2`, но персонально сказал
«маскировать» его ИНН — ИНН маскируется. Иначе будущий выбор «по каждому PII»
затирался бы групповым, и вся фича обесценилась бы.

Профиль частнее типа, потому что адресует конкретное подмножество ссылок этого
документа, а тип — весь класс. Уровень 0 стоит над всем и снимается только
двойным подтверждением из раздела 3; при снятии он просто не применяется, и
решение принимает следующий по частности источник.

Каждая запись хранит `overridden` — перечень применимых, но проигравших
решений. Это то, что показывает человеку в отчёте, почему его галочка по типу
не сработала на конкретной сущности.

### Где происходит разворачивание группы в ссылки

`PolicyQuestion` **не носит список `refs`** в конверте: у типа их могут быть
сотни, дублирование раздувает payload и создаёт второй источник истины.
Разворачивание делает `PolicyAgent.apply` детерминированным предикатом
(тип сущности; принадлежность профилю по `ProfileMember.ref`), а связь
«решение ← вопрос» сохраняется в поле `question_id` каждой ref-записи. Аудит
полный, payload маленький. Отвергнутая альтернатива — класть `refs` в вопрос —
не даёт ничего сверх этого и рискует разъехаться с состоянием.

### Два вида вопросов: почему отдельный датакласс

`Question` (`model.py`) — вопрос **про сущность**: у него есть `refs` и
`anchors`, судья применяет ответ по `refs`. Вопрос политики адресует **класс**
(тип или субъект); ему нужны счётчики, образцы значений и подсказки о связанных
профилях, и не нужны `refs` (см. выше). Смешивать в `Question` нельзя:
`Question.refs` для типа стал бы списком из сотен ссылок, а `apply_answers`
судьи получил бы вторую, чужую семантику.

**Решение: отдельный датакласс `PolicyQuestion` в `model.py`** (добавление, не
изменение существующих сигнатур). Требование «одна пачка в одном прерывании»
сохраняется: **прерывание одно на документ**, а внутри — один плоский список
вопросов в едином JSON-формате (раздел 5). Разные внутренние датаклассы, один
провод наружу; добавление третьего вида вопроса («это PII?») не меняет провод.

Идентификаторы непересекающиеся и детерминированные:
`TYPE-<тип>` (`TYPE-inn`), `PROFILE-<id профиля>` (`PROFILE-P3`,
`PROFILE-UNASSIGNED`), `Q<n>` — как сейчас у судьи. Пространство `PII-<ref>`
зарезервировано за будущими персональными вопросами и сегодня не занимается.

## 5. Контракт паузы и возобновления (то, поверх чего вешается веб)

**`thread_id`** — детерминированная строка:
`sha256(RUN_SCHEMA_VERSION | sha256(байты файла) | канонизированные опции)[:16]`.
Опции: список типов, `rules_only`, `profile`, `unmask_critical`, идентификатор
конфига LLM. Один и тот же файл с теми же опциями даёт тот же `thread_id`;
изменение опций или версии схемы даёт другой. `RUN_SCHEMA_VERSION` поднимается
руками при изменении состава `State` — это защита от чтения устаревшего
чекпойнта после правки кода.

**Файл чекпойнтера** — `--state-db`, по умолчанию `<--out>/state.sqlite`.
Каталог создаётся, файл получает права `0600`: **в нём лежит полный текст
документа и все найденные PII**. `/out/` уже в `.gitignore`.

**Что отдаётся наружу в момент паузы** — один JSON-конверт, он же значение
`interrupt()`, он же содержимое `questions.json`:

```json
{
  "schema_version": 1,
  "thread_id": "0f3a…",
  "document": {"name": "contract_01.docx", "format": "docx"},
  "questions": [
    {"id": "TYPE-inn", "kind": "type", "target": "inn", "title": "ИНН",
     "prompt": "Маскировать все ИНН (найдено 3)?",
     "options": ["маскировать"], "default": "маскировать",
     "critical": true, "found": 3,
     "samples": ["3662103003", "7743013902"],
     "anchors": ["абзац 6", "таблица 1, строка 1, ячейка 1, абзац 2"]},
    {"id": "PROFILE-P3", "kind": "profile", "target": "P3",
     "title": "СТОРОНА-3", "role_title": "",
     "prompt": "Маскировать реквизиты субъекта СТОРОНА-3 (4 сущности)?",
     "options": ["маскировать", "оставить"], "default": "маскировать",
     "critical": false, "found": 4,
     "by_type": {"inn": 1, "address": 2, "person": 1},
     "samples": ["3662103003", "309512, Белгородская область…"],
     "anchors": ["таблица 1, строка 1, ячейка 1, абзац 6"],
     "linked_profiles": ["P4", "P5"]},
    {"id": "Q1", "kind": "entity", "target": "phone:79001234567", …}
  ]
}
```

Обязательные ключи у **любого** вопроса: `id`, `kind`, `target`, `title`,
`prompt`, `options`, `default`, `critical`, `found`, `samples`, `anchors`.
Веб рендерит их обобщённо и не знает про виды вопросов — поэтому будущий вид
`kind: "pii"` не потребует правок ни во фронте, ни в контракте.

**В каком виде принимаются ответы** — плоский словарь «id вопроса → выбранная
строка из `options`»:

```json
{"schema_version": 1, "thread_id": "0f3a…",
 "answers": {"TYPE-phone": "оставить", "PROFILE-P3": "оставить", "Q1": "оставить"}}
```

Веб умеет ровно две операции, обе — функции `src/masker/run.py`:
`start_run(...) -> RunOutcome` («начать прогон и получить вопросы») и
`resume_run(thread_id, answers) -> RunOutcome` («прислать ответы»). Логика узлов
при переезде на веб не трогается: меняется только вызывающий и чекпойнтер
(`SqliteSaver` → серверный) — поэтому чекпойнтер передаётся снаружи, а не
создаётся внутри узлов.

**Граничные случаи — поведение задано жёстко, каждое покрыто тестом:**

| Случай | Поведение |
|---|---|
| Неполные ответы | недостающие вопросы берут `default`; второго прерывания не возникает; список попадает в `decisions.unanswered_defaults` |
| Неизвестный `thread_id` | `UnknownThreadError`, код возврата 3; **новый прогон не запускается** (проверка через `get_state(...).created_at is None` до `invoke`) |
| Повторный ответ на завершённый прогон | `AlreadyFinishedError`, код возврата 3; артефакты не переписываются; сообщение «прогон завершён, для нового используйте `--fresh`» |
| Неизвестный id вопроса в ответах | ответ игнорируется, id попадает в `decisions.ignored_answers` и печатается предупреждением; не фатально (веб может прислать устаревшие id) |
| Значение вне `options` | трактуется как `default`, id попадает в `decisions.invalid_answers`; для критичного типа это означает «маскировать» |
| `--ask` на приостановленном треде | вопросы **читаются из `get_state`**, узлы не пересчитываются, `questions.json` побайтово тот же |
| `--ask` на завершённом треде | код 3 и подсказка про `--fresh` |
| `--fresh` | `checkpointer.delete_thread(thread_id)` перед прогоном |

## 6. Граф

```
extract ─► detect ─► profile ─► judge ─► policy ─┬─(нужен человек)─► ask_human ─┐
                                                 │                             │
                                                 └────────(не нужен)───────────┤
                                                                               ▼
                                                                        apply_answers
                                                                               │
                                                                               ▼
                                                                           finalize ─► END
```

- `extract` — `ingest_docx(path)` → `segments`, `meta`;
- `detect` — `DetectAgent` по `options.rules_only`, фильтр по `options.types`;
- `profile`, `judge` — существующие узлы, но `ProfileAgent` получает LLM из
  зависимостей прогона (сейчас узел молча создаёт `ProfileAgent()` без LLM);
- `policy` — новый узел: строит `policy_questions`;
- `ask_human` — существующий, ровно один `interrupt()`, теперь с общим конвертом;
- `apply_answers` — применяет ответы судьи **и** политику, порождая решения по
  ссылкам;
- `finalize` — сводит решения по каждому `ref` с разрешением конфликтов
  (раздел 4) и собирает блок `decisions` (запись файлов остаётся снаружи графа,
  в CLI: узлы не пишут артефакты).

Роутер: `needs_human` возвращает `"ask_human"` только если
`state["options"]["interactive"]` истинно **и** есть хотя бы один вопрос любого
вида **и** ответы ещё не заданы заранее. Иначе — сразу `apply_answers`. Это
единственная защита ворот от зависания, и она обязана быть проверена тестом.

**LLM в `State` не кладётся.** Узлы собираются фабриками, замыкающими
`RunDeps` (провайдер LLM, трейсер): `make_profile_node(deps)`. В `State` — только
JSON. При возобновлении LLM не вызывается (граф стартует с `ask_human`), поэтому
отсутствие `--llm-config` во второй фазе не ошибка.

`State` пополняется: `meta`, `options`, `policy_questions`, `answers`
(единый словарь на все виды), `decisions` (сводка для отчёта) и
`final_actions` — список записей по каждому `ref` в формате раздела 4.

## 7. Как решения складываются в одно действие

Алгоритм `finalize` на каждый `ref`, ровно один проход, без исключений из
правил:

1. собрать все применимые решения: `judge` (вердикт), `entity` (ответ `Q*`,
   если сущность в `refs` вопроса), `profile` (ответ на `PROFILE-*` профиля
   сущности; для сущностей без профиля — `PROFILE-UNASSIGNED`), `type` (ответ на
   `TYPE-<тип>`), `default`;
2. если `is_critical(entity.type)` и снятие не подтверждено обоими
   подтверждениями (раздел 3) — добавить решение уровня 0
   `critical_guard: mask` с причиной «критичный тип: снятие требует явного
   подтверждения» и записью в `decisions.diagnostics`;
3. выбрать решение с наименьшим номером приоритета из таблицы раздела 4;
   остальные применимые уходят в `overridden` той же записи;
4. записать `{ref, action, decided_by, question_id, reason, overridden}`.

Итоговый список сортируется `entity_sort_key` — порядок не зависит от порядка
обхода словарей и от порядка ключей в файле ответов.

## 8. Показ профиля, когда роли нет

На реальном документе P3/P4/P5 имеют пустой `role_title` и `marker_label`
«СТОРОНА-3/4/5» (см. `cluster.py`: `profile.marker_label = f"СТОРОНА-{number}"`),
и это куски реквизитов одного лица. Фрагментация профилей — **известный
незакрытый дефект**, план на «одна сторона = один профиль» не опирается.

Поэтому карточка профиля в вопросе не спрашивает «выберите роль», а показывает:
`id`, `marker_label`, `role_title` если непустой, число сущностей, разбивку
`by_type`, до 5 образцов значений (в порядке `entity_sort_key`, значение
обрезается до 60 символов) и до 3 меток якорей (`Anchor.label`: «таблица 1,
строка 1, ячейка 1, абзац 6»).

Дополнительно — `linked_profiles`: профили, делящие нормализованное значение
критичного ключа (`inn`, `ogrn`, `snils`) или нормализованное ФИО. Это
**подсказка человеку**, что P3/P4/P5 — вероятно одно лицо. Автоматического
слияния здесь нет: слияние — отдельная задача по дефекту фрагментации. Ref-центричная
модель решений от фрагментации не страдает: даже если человек отключит только
P3, решения по ссылкам P4/P5 останутся видимыми в отчёте отдельными строками.

## 9. Инварианты, которые шаги обязаны сохранить

- **Детерминизм.** Ни `random`, ни `uuid`, ни времени в артефактах. Все списки
  сортируются явно. `Interrupt.id` не попадает никуда (доказано пробой: он
  меняется от прогона к прогону). Два прогона с одинаковыми ответами дают
  побайтово одинаковые `report.json` и `questions.json`.
- **Идемпотентность в границах задачи.** Повторный `--ask` не пересчитывает и не
  меняет `questions.json`; повторный `resume` завершённого треда не меняет
  артефакты. Идемпотентность по обезличенному документу проверяется в T1.7/T1.8 —
  сейчас маскированного файла не существует.
- **Согласованность псевдонимов** не затрагивается: решения человека только
  выбирают, какие ссылки идут в маскирование, ключи и маркеры считает T1.6.
- **Утечки.** `state.sqlite`, `questions.json` и `preview.docx` содержат исходные
  PII: права `0600` и строка в `limitations`, как уже сделано для `llm-trace`.
- **Судья не спрашивает про критичное**: ни один `Question.refs` по-прежнему не
  ссылается на критичную сущность — существующий тест остаётся зелёным.
- **Ворота не висят.** Ни в одном модуле `src/` нет `input()`; неинтерактивный
  режим — по умолчанию.

### Шаг 2 — `PolicyAgent.questions()`
**Файлы:** `src/masker/policy/__init__.py`, `src/masker/policy/agent.py`,
`tests/masker/policy/test_questions.py`.

Строит вопросы по типам (по одному на каждый тип, реально найденный в

образцы, якоря, `linked` (раздел 8). Для критичного типа `options` содержит
только «маскировать», а при `allow_unmask_critical=True` — ещё
`KEEP_CRITICAL_OPTION`; то же для профиля, среди сущностей которого есть
критичные.

**Приёмка:** тесты на синтетических сегментах (сеть не нужна):
- документ с `inn`, `phone`, `person` даёт вопросы `TYPE-inn`, `TYPE-person`,
  `TYPE-phone` именно в этом порядке;
- `TYPE-inn`: `options == ("маскировать",)`, `critical is True`; с

- профиль с пустым `role_title` даёт вопрос с `title == "СТОРОНА-3"`, непустыми
  `samples` и `anchors`, и в `prompt` нет слова «роль»;
- профиль с критичной сущностью помечен `critical is True` и без флага не
  предлагает «оставить (осознанное решение)»;
- два профиля с одинаковым нормализованным ИНН ссылаются друг на друга в
  `linked`, но остаются двумя вопросами;
- сущности вне профилей дают ровно один `PROFILE-UNASSIGNED`;
- два вызова на одном входе дают идентичные списки (детерминизм).

Тест падает без шага: модуль `masker.policy` отсутствует.

### Шаг 3 — разрешение конфликтов и защита критичного
**Файлы:** `src/masker/policy/agent.py`, `tests/masker/policy/test_apply.py`.

`PolicyAgent.apply(...) -> PolicyResult` реализует раздел 7: собирает
применимые решения по каждому `ref`, добавляет `critical_guard`, выбирает
победителя по `DECISION_PRECEDENCE`, складывает проигравших в `overridden`.
`PolicyResult`: `decisions: list[Decision]` (по одной на `ref`, отсортированы),
сводка по типам и профилям с пометкой `human`/`default`, `critical_unmasked`,
`unanswered_defaults`, `ignored_answers`, `invalid_answers`, `diagnostics`.

**Приёмка:**
- ответ `TYPE-phone: оставить` даёт всем телефонам `Decision(decided_by="type",
  action=KEEP)`, ИНН не трогает;
- ответ `PROFILE-P2: оставить` затрагивает только сущности P2, и у каждой
  записи `question_id == "PROFILE-P2"`;
- **конфликт «персональное против группового»:** `TYPE-phone: оставить` плюс
  ответ `Q1: маскировать` на конкретный телефон → у этого `ref`
  `action == MASK`, `decided_by == "entity"`, а в `overridden` лежит решение
  `type/keep`; у остальных телефонов `keep`. Тест падает при любом порядке
  приоритетов, кроме заданного;
- **конфликт «профиль против типа»:** `TYPE-person: маскировать` плюс
  `PROFILE-P2: оставить` → ФИО из P2 остаётся, `decided_by == "profile"`;
- ответ `TYPE-inn: оставить` **без** `allow_unmask_critical` → все ИНН `MASK` с
  `decided_by == "critical_guard"`, в диагностиках строка про требуемое
  подтверждение, `critical_unmasked == []`;
- ответ `TYPE-inn: оставить (осознанное решение)` **с**
  `allow_unmask_critical` → ИНН в `KEEP`, `critical_unmasked` содержит тип и
  число вхождений;
- то же для `PROFILE-*`: без двойного подтверждения критичные реквизиты
  оставленного профиля остаются замаскированными;
- отсутствующий ответ даёт `default` и попадает в `unanswered_defaults`;
- неизвестный id и значение вне `options` попадают в `ignored_answers` /
  `invalid_answers` и не меняют действий;
- порядок итогового списка не зависит от порядка входного словаря ответов
  (тот же вход, перемешанные ключи → тот же результат);
- ссылка из чужого пространства (`H1`) в ответах не роняет разбор, а попадает в
  `ignored_answers` — страховка под будущую ручную разметку.

### Шаг 8 — сервис прогона `run.py` (то, что потом позовёт веб)

### Шаг 9 — CLI: две фазы, коды возврата, печать
**Файлы:** `src/masker/cli.py`, `tests/masker/test_cli_human.py`.

Новые флаги (в стиле существующих `--profile`, `--llm-config`, `--llm-trace`,
`--allow-remote-pii`):

| Флаг | Смысл |
|---|---|
| `--ask` | остановиться на вопросах, записать `questions.json`, выйти с кодом 10; требует `--profile` |
| `--answers PATH` | файл ответов; допустим и в первой фазе (тогда прерывания нет), и со `--resume` |
| `--resume THREAD_ID` | продолжить приостановленный прогон; позиционные файлы не нужны |
| `--thread-id ID` | задать идентификатор вручную |
| `--state-db PATH` | файл чекпойнтера, по умолчанию `<--out>/state.sqlite` |
| `--fresh` | удалить тред перед прогоном |
| `--unmask-critical` | разрешить снятие маски с критичных типов (первое из двух подтверждений) |

Коды возврата: `0` — готово, `2` — ошибка аргументов (argparse), `3` — ошибка
прогона (неизвестный тред, прогон завершён, тред существует), `10` — прогон
приостановлен и ждёт ответов. Без `--ask` и без `--resume` прогон
неинтерактивный: тред удаляется и считается заново — так работают `make demo`
и `make gate`, они не имеют права зависать.

`files` становится `nargs="*"`; парсер требует либо файлы, либо `--resume`.

**Приёмка:**
- `main([fixture, "--out", tmp, "--profile", "--rules-only", "--ask"]) == 10`;
  в `tmp/<stem>/questions.json` лежит конверт, права `600`, в stdout напечатаны
  `thread_id`, число вопросов и вопросы человекочитаемо;
- повторный тот же вызов снова даёт 10 и **побайтово тот же** `questions.json`;
- `main(["--resume", tid, "--out", tmp, "--profile", "--answers", answers]) == 0`,
  в `report.json` появился блок `decisions`;
- `main(["--resume", "нет-такого", …]) == 3`, в stdout русское сообщение, новых
  файлов не появилось;
- повторный `--resume` с другими ответами даёт `3` и не меняет `report.json`
  (сравнение sha256 до и после);
- прогон без `--ask` завершается кодом 0 при закрытом stdin
  (`monkeypatch.setattr(sys, "stdin", io.StringIO())`) — доказательство, что
  ворота не зависнут;
- `--ask` без `--profile` → код 2 с внятным сообщением.

- прогон со снятым ИНН (оба подтверждения): `decisions.critical_unmasked`
  непуст, в `limitations` есть строка про осознанное снятие, в HTML есть баннер;
- `grep -c "interrupt" report.json` = 0 — идентификатор прерывания в отчёт не

### Шаг 11 — детерминизм и ворота

## 11. Что может пойти не так и как это будет замечено

| Риск | Как обнаруживается |
|---|---|
| Опечатка в `thread_id` тихо запускает новый прогон вместо возобновления (реальное поведение LangGraph, проверено) | тест шага 8: `UnknownThreadError` + отсутствие треда после вызова |
| Второй ответ на завершённый прогон молча игнорируется, человек думает, что решение применено | тест шага 9: код 3 и неизменный sha256 отчёта |
| Повторный `--ask` заново гоняет детекцию и LLM (деньги и разъезжающиеся цифры) | тест шага 7/9 со счётчиком вызовов детектора и побайтовым сравнением `questions.json` |
| Групповое решение затирает персональное — и будущий выбор «по каждому PII» окажется бесполезным | тесты конфликтов в шаге 3 и шаге 10, падающие при любой перестановке `DECISION_PRECEDENCE` |
| `Interrupt.id` попадает в артефакты и ломает побайтовую воспроизводимость | тест детерминизма шага 11 |
| Устаревший чекпойнт после правки кода даёт старые цифры на защите | `RUN_SCHEMA_VERSION` в `thread_id` + неинтерактивный режим всегда стартует со свежего треда; тест на смену id при смене опций |
| Ворота зависают в ожидании ввода | `interactive=False` по умолчанию, тест с закрытым stdin, тест `test_no_stdin_in_src` |
| Узел `ask_human` выполняется дважды (LangGraph переисполняет узел при возобновлении) и удваивает побочный эффект | тест шага 6 на отсутствие побочных эффектов |
| `state.sqlite` с полным текстом договора уезжает в репозиторий или к контрагенту | права `0600`, `/out/` в `.gitignore`, строка в `limitations`, тест на права |
| Человек отключает ИНН и получает «обезличенный» документ с ИНН | два независимых подтверждения, громкая запись в отчёт, `critical_unmasked == 0` в воротах |
| Фрагментация профилей: человек оставляет P3, а те же реквизиты уезжают через P4 | `linked_profiles` в карточке; тест шага 2 на взаимные ссылки; в отчёте перечислены решения по **каждой** ссылке, а не по профилям |
| `SqliteSaver` однопоточный и не годится под веб | чекпойнтер внедряется фабрикой в `run.py`; в докстринге прямо сказано, что серверу нужен свой saver |

## 12. Принятые решения и что ещё открыто

**Принято (пользователем, направление «максимум контроля»):**

1. **Критичные типы — вариант A.** Снятие маски возможно при двойном
   подтверждении (`--unmask-critical` + ответ «оставить (осознанное решение)»),
   с записью в `decisions.critical_unmasked`, строкой в `limitations`, баннером
   в HTML и порогом `critical_unmasked == 0` в воротах. Отключение профиля
   снимает маску с его критичных реквизитов по тому же двойному подтверждению.
   Запрет отпал: он противоречит заявленному направлению и делает выбор по
   профилю наполовину фиктивным. Двойное подтверждение остаётся страховкой от
   случайного клика — раздел 3.
2. **Единица решения — ссылка на сущность**, групповые вопросы по типам и
   профилям — способ задать много решений разом; персональное решение сильнее
   группового — раздел 4.

**Ещё требует решения человека (не блокирует старт работ, влияет на шаг 11):**

1. **Порог `MAX_QUESTIONS` в воротах.** Вопросов на документ станет заметно
   больше (типы + профили + вопросы судьи). Поднять общий порог по факту
   прогона или считать пороги раздельно для вопросов политики и вопросов судьи?
   Второе честнее, но добавляет метрику в `make eval`.
2. **Что делать с `--types` при интерактивном выборе.** Сейчас `--types`
   фильтрует ещё до детекции, то есть человек не увидит того, что отфильтровано.
   Оставить как есть (`--types` — предфильтр, `TYPE-*` — уточнение внутри
   найденного) или сделать `--types` дефолтом ответов на `TYPE-*`, детектируя
   всегда всё? Второе дороже по времени и меняет метрики `make eval`. В плане
   заложен первый вариант.

### Про «сам выбирать, какие данные это PII»

Что **уже покрыто** T1.13 (`docs/plans/T1.13-entity-type-registry.md`) и
дублировать не надо: `EntityTypeRegistry` + `Entity.type: str` вместо закрытого
enum; пользовательские типы в `masker.types.yaml` (`literals` — «замазать вот
эти конкретные строки», `regex` с AST-валидатором и бюджетом времени,
`detector: "llm"` + `description` для семантических типов через T3.3);
`Source.USER`; фильтр «что искать» на уровне плана; `critical: true` для
пользовательского типа. То есть «объявить, что в моих документах ИНН партнёров и
номера складских накладных — это PII» решается реестром, а вопросы `TYPE-*`
из этого плана автоматически появятся и для пользовательских типов, потому что
строятся по фактически найденным типам, а не по `EntityType`.

Что **не покрыто ничем** и потребует отдельной задачи (здесь только не
закрывается дорога):

- **ручная пометка произвольного участка текста как PII** в конкретном
  документе, без правила и без переиспользования: человек указывает
  `segment_order` + `start`/`end` (в вебе — выделение мышью), возникает сущность
  с `Source.USER` и ссылкой из зарезервированного пространства `H1..Hn`, а
  решение по ней — обычная запись `entity/mask` с высшим негвардейским
  приоритетом. Ни `State`, ни конверт вопросов, ни формат отчёта при этом не
  меняются — это и есть цель ref-центричной модели;
- **персональные вопросы «маскировать ли вот эту сущность»** (`kind: "pii"`,
  id `PII-<ref>`) — новый вид вопроса в том же конверте и том же одном
  прерывании; приоритет `entity` уже зарезервирован за ними;
- **снятие пометки с ложной сущности** как переиспользуемое правило
  (стоп-лист) — это уже реестр типов плюс отдельная задача про исключения.

Не сюда: роли из контекста (T3.2), слияние фрагментированных профилей
(отдельный дефект), веб-эндпоинты (здесь готовится только контракт `run.py`),
LLM-арбитр детекции (T3.3).
