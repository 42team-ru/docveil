# T1.6 + T1.8 — PlanAgent (сущность → маркер) и ValidateAgent (проверка утечек)

Ветка: `feat/plan-validate`. Постановка — `TASKS.md`, разделы T1.6 и T1.8.
Здесь: где именно рвётся цепочка «профиль → маркер», как выглядит `MaskPlan`,
какая таксономия утечек не даёт воротам врать в обе стороны, и что в этом
плане может испортить детерминизм.

## Решение в одном абзаце

Появляется пакет `src/masker/mask/` (сейчас пустой) с `PlanAgent`, который
превращает список сущностей плюс профили плюс итоговые решения в
**`MaskPlan`** — упорядоченный набор `Replacement` с готовой строкой маркера.
Согласованность обеспечивает `group_key(entity)` поверх уже существующей
`detect/normalize.normalize_value`, номера групп присваиваются по порядку
первого вхождения в документе (`refs.entity_sort_key`), а не по обходу
словаря. Маркер собирается из ролевой части профиля (`Profile.marker_label`,
которая уже считается в `profile/cluster.py` и до рендера сегодня **не
доезжает вообще**) и короткой типовой метки: `[ПОСТАВЩИК-ИНН]`,
`[ПОКУПАТЕЛЬ-ФИО-2]`. Рендеры перестают строить маркер сами: `_build_marker`
в `render/docx_redact.py:26` и `render/pdf_render.py:111` берут готовое
`Replacement.marker` и оставляют себе только паддинг под стиль. Фильтр по
запрошенным типам переезжает из детекции в план. Затем появляется
`src/masker/validate/` с `ValidateAgent`, который по каждому **обезличенному**
артефакту делает три независимые проверки: повторный прогон детекторов по
всем типам, поиск исходных строк побайтово по всем частям контейнера
(включая `docProps/*`) и поиск по извлечённому тексту (ловит разрыв по
run'ам, который побайтовый поиск пропускает). Непустой `leaked` → CLI
возвращает 4.

## Два противоречия в постановке — назвать, а не угадать

### П1. `[ПОКУПАТЕЛЬ-ДИРЕКТОР]` требует того, чего никто не детектит

Инвариант в `AGENTS.md` приводит пример `[ПОКУПАТЕЛЬ-ДИРЕКТОР]`. «Директор» —
это **должность лица**, а не тип сущности и не роль стороны. В коде её никто
не извлекает: `EntityType.PERSON` знает только «это ФИО», `profile/labels.py`
достаёт роль **стороны** («Поставщик», «Покупатель») из преамбулы, реквизитов
и подписи.

- **Вариант A (рекомендуемый, взят в план).** Маркер лица —
  `[ПОКУПАТЕЛЬ-ФИО]`, при нескольких лицах стороны — `[ПОКУПАТЕЛЬ-ФИО-2]`.
  Инвариант «маркер строится от профиля и роли» выполнен буквально: роль
  стороны в маркере есть. Цена: пример из `AGENTS.md` воспроизводится не
  дословно.
- **Вариант B.** Дополнительно тянуть должность из формулы «в лице
  генерального директора Иванова И.И.» регуляркой и подставлять её вместо
  `ФИО`. Цена: новый источник ролей вне `profile/labels.py`, новая ветка
  недетерминированного разбора падежей («в лице директора» / «действующего на
  основании»), а при неудаче разбора — разные маркеры у одного и того же лица
  в разных местах документа, то есть прямой удар по согласованности.

Взят A. Если человек выбирает B — это отдельная задача **после** T1.6, она
меняет только `mask/labels.py` и `profile/`, а не структуру плана.

### П2. «Проверить оба выходных файла» vs. сегодняшний `preview.docx`

`ARCHITECTURE.md` (раздел «Три артефакта») обещает `masked_black.*` и
`masked_highlight.*` — оба обезличенные. Сегодня же CLI пишет
`preview.docx`, который **намеренно** содержит исходный текст
(`render/docx_preview.py`, докстринга: «Текст не заменяется… не для передачи
наружу»), и печатает про это предупреждение (`cli.py:_print_graph_report`).
Натравить Validate на `preview.docx` — гарантированный красный результат на
артефакте, который таким и задуман.

- **Вариант A (взят в план).** `ValidateAgent.validate()` принимает **список
  путей** обезличенных артефактов. Проверяются только те, что произведены
  редактирующими рендерами (`render_*_redacted`). `preview.docx` в список не
  попадает никогда, и в `report.json` рядом с `validation` пишется
  `"preview_excluded": true` с причиной. Когда T1.7 начнёт делать
  `masked_highlight.docx` (подсветка **поверх маркера**, исходный текст
  удалён), он просто добавит второй путь в тот же список — сигнатура не
  меняется.
- **Вариант B.** Переименовать `preview.docx` в этой же задаче и сделать его
  обезличенным. Цена: это и есть T1.7 целиком, плюс ломается
  `report/html.py:_full_document` и тесты `tests/masker/test_cli*.py`,
  которые на preview с исходным текстом опираются.

Взят A.

## Контракты

### Новое в `src/masker/model.py`

`model.py` — единственное место для типов, пересекающих границы агентов.
`MaskPlan` пересекает четыре (Plan → Render → Validate → Report), поэтому
живёт там. Существующие сигнатуры не меняются — только добавляются.

```python
@dataclass(frozen=True, slots=True)
class MaskGroup:
    """Группа сущностей с одним значением и одним маркером."""
    id: str            # "G1", по порядку первого вхождения
    key: str           # ключ согласованности, см. mask/keys.py
    type: EntityType
    marker: str        # "[ПОСТАВЩИК-ИНН-2]"
    profile_id: str    # "" — сущность без профиля
    role_label: str    # "ПОСТАВЩИК" | "СТОРОНА-2" | "" (без профиля)
    number: int        # порядковый номер внутри пары (role_label, type), от 1
    refs: tuple[str, ...]   # ссылки EntityIndex, в текстовом порядке
    sample: str        # первое встреченное написание — для отчёта

@dataclass(frozen=True, slots=True)
class Replacement:
    """Одна замена: что, где, на что."""
    ref: str
    entity: Entity
    marker: str
    group_id: str
    profile_id: str
    anchor: Anchor

@dataclass(frozen=True, slots=True)
class SkippedRef:
    """Сущность, не попавшая в план, и почему."""
    ref: str
    type: EntityType
    reason: str        # "type_not_requested" | "kept" | "no_anchor"

@dataclass(frozen=True, slots=True)
class MaskPlan:
    replacements: tuple[Replacement, ...]   # в текстовом порядке
    groups: tuple[MaskGroup, ...]           # в порядке номеров
    skipped: tuple[SkippedRef, ...]
    requested_types: tuple[str, ...]        # отсортированные значения
```

`Replacement.entity` + `Replacement.marker` — именно то, чего ждёт уже
написанный `eval.py:207` (`result.replacements`, `repl.entity.type.value`,
`repl.entity.text`). Придумывать другое имя нельзя: сломается ещё не
подключённая метрика.

```python
@dataclass(frozen=True, slots=True)
class Leak:
    kind: str          # "detector" | "raw" | "metadata"
    artifact: str      # имя файла артефакта
    part: str          # "word/document.xml" | "docProps/core.xml" | "page 3" | ""
    entity_type: str
    value: str         # исходная строка или найденный текст
    ref: str = ""
    group_id: str = ""
    detail: str = ""

@dataclass(frozen=True, slots=True)
class ValidationReport:
    leaked: tuple[Leak, ...]        # провал прогона
    residual: tuple[Leak, ...]      # найдено, но не провал — см. таксономию
    checked_artifacts: tuple[str, ...]
    checked_parts: tuple[str, ...]
    ok: bool
```

def group_key(entity: Entity) -> str: ...

### `src/masker/validate/`

```python
# validate/parts.py
@dataclass(frozen=True, slots=True)
class DocPart:
    name: str        # "word/document.xml" | "docProps/core.xml" | "page 3"
    raw: bytes       # для побайтового поиска
    text: str        # видимый/извлечённый текст, "" если неприменимо

def docx_parts(path: Path) -> list[DocPart]: ...   # все элементы zip, имена отсортированы
def pdf_parts(path: Path) -> list[DocPart]: ...    # текстовый слой постранично + метаданные

# validate/agent.py
class ValidateAgent:
    def __init__(self, detector: DetectAgent | None = None) -> None: ...
    def validate(
        self,
        plan: MaskPlan,
        artifacts: Sequence[Path],
    ) -> ValidationReport: ...
```

**Почему у `validate()` нет параметра `kept_refs`.** В черновике сигнатуры
он был — идея в том, чтобы вызывающий код мог явно сказать «эти ссылки
оставлены осознанно, не считай их утечкой». На шаге 9 выяснилось, что он
не нужен: классификация повторной детекции на `leaked`/`residual` целиком
определяется совпадением `group_key(entity)` с `plan.groups[].key`.
Сущность, которую план не собирался маскировать — решение человека
«оставить», незапрошенный тип, новая находка второго прохода — никогда не
формирует группу плана (`PlanAgent` кладёт её в `plan.skipped`, а не в
`plan.groups`), и поэтому механически попадает в `residual`, без
дополнительного фильтра. Кодер реализовал `kept_refs` в первой версии, но
единственный технически возможный смысл параметра при сигнатуре
`validate(plan, artifacts)` — ссылки в **собственной** нумерации
`ValidateAgent` (по артефакту, который он сам передетектировал), а не
ссылки исходного документа/плана: `SkippedRef` не хранит текст сущности,
поэтому сопоставить «оставленную» сущность плана с находкой второго
прохода напрямую по ссылке нельзя. Такая семантика — не то, что ожидал бы
вызывающий код по имени параметра, и ни один тест приёмки её не требовал.
Параметр, который делает не то, что думает вызывающий, хуже отсутствующего
— убран. Если на шаге 10 у реального вызывающего кода возникнет настоящая
потребность («это конкретное значение оставлено осознанно, не считай
совпадение по этому ключу утечкой»), возвращать его нужно с честной
семантикой поверх **значения**, а не ссылки — то есть сначала придётся
дать `SkippedRef` поле с текстом/нормализованным значением сущности, и это
уже правка `model.py` и `mask/agent.py`, а не только `validate/`.

## Как строится маркер

1. **Ролевая часть.** `Profile.marker_label` профиля, которому принадлежит
   сущность (`ProfileMember.ref` → профиль). Уже даёт `ПОСТАВЩИК` при
   найденной метке и `СТОРОНА-3` при её отсутствии (`cluster.py:86`).
   Сущность **без профиля** получает пустую ролевую часть → `[ИНН-2]`.
   Обоснование: выдуманный префикс хуже отсутствующего. Профиля не бывает
   ровно у тех сущностей, которые не привязаны ни к одной стороне (название
   банка в реквизитах, дата, номер договора), и `[СТОРОНА-?-ДАТА]` в таком
   месте прямо врёт читателю обезличенного договора.
2. **Типовая часть.** Короткая русская метка из `MARKER_TYPE_LABELS`:
   `ИНН, КПП, ОГРН, СНИЛС, СЧЁТ, БИК, БАНК, ОРГАНИЗАЦИЯ, ФИО, АДРЕС,
   ТЕЛЕФОН, ПОЧТА, ПАСПОРТ, ДОГОВОР, СУММА, ДАТА, САЙТ`.
   Не переиспользуем `policy/agent.py:_TYPE_TITLES` — те метки написаны для
   текста вопроса человеку («Название организации») и в маркер не влезают.
   Тест обязан проверять, что оба словаря покрывают **все** члены
   `EntityType` (защита от нового типа, забытого в одном из мест).
3. **Номер.** Внутри пары `(role_label, type)` группы нумеруются от 1 по
   порядку первого вхождения. Если группа в паре одна — суффикс не
   добавляется: `[ПОСТАВЩИК-ИНН]`. Если их две и больше — суффикс есть у
   **каждой**: `[ПОСТАВЩИК-ФИО-1]`, `[ПОСТАВЩИК-ФИО-2]`. Асимметрия «первый
   без номера, второй с номером» запрещена: она заставляет читателя гадать,
   один ли это человек.

Итог: `[` + `-`.join(непустые части) + `]`.

## Согласованность: `group_key`

```
group_key(entity) = f"{entity.type.value}:{normalize_value(entity.type, entity.text)}"
```

`normalize_value` из `detect/normalize.py` уже умеет ровно то, что просит
T1.6: снимает организационно-правовую форму по YAML-словарю `orgforms()` и
кавычки всех видов (`_normalize_org`), сводит ФИО к «фамилия и.о.»
(`_normalize_person`), выбрасывает пробелы и дефисы у цифровых типов.
«ООО "Ромашка"», «ООО «Ромашка»» и «Ромашка» дают `org_name:ромашка`.

Две ловушки, которые обязаны быть покрыты тестами:

- `_normalize_org("ООО")` возвращает **пустую строку** (строка 62
  `normalize.py`). Две разные организации, от которых осталась одна форма,
  склеятся в один маркер. Правило: при пустой нормализации ключ строится от
  сырого текста с отдельным префиксом — `f"{type}:~{casefold(text)}"` — чтобы
  такой ключ не мог совпасть ни с одним нормализованным.
- **Не** переиспользовать `profile/keys.merge_key`. Он решает другую задачу
  (склейка блоков) и режет формы захардкоженной регуляркой `_FORMS`
  (`keys.py:20`), где нет половины словаря `orgforms.yaml`. Два разных ключа
  для двух разных задач — нормально; один ключ, который «почти» подходит
  обеим, — источник плавающих расхождений. В докстринге `mask/keys.py` это
  расхождение назвать явно.

Полная форма ФИО против инициальной («Иванов Иван Иванович» / «И.И. Иванов»)
`normalize_value` не сводит — это прямо написано в её докстринге со ссылкой
на T1.6. **В этой задаче она тоже не сводится.** Причина: сведение требует
знания отчества и порождает ложные склейки однофамильцев; вместо этого две
формы попадают в разные группы одного профиля и получают
`[ПОСТАВЩИК-ФИО-1]` / `[ПОСТАВЩИК-ФИО-2]`. Это видимый дефект читаемости, но
не утечка, и он фиксируется тестом с `xfail`-семантикой в виде явной
проверки текущего поведения плюс строкой в разделе «Известные ограничения»
отчёта. Склейка — отдельная задача.

## Детерминизм — где он мог бы утечь

| Место | Опасность | Что делает план |
|---|---|---|
| Сбор групп | обход `dict` по вставке зависит от порядка входного списка | сущности сортируются `refs.entity_sort_key` **до** группировки |
| Номера групп | нумерация по хэшу ключа | нумерация по позиции первого вхождения |
| `EntityIndex` | ссылки по `id()` объекта | индекс строится один раз из отсортированного списка, `PlanAgent` не создаёт второй |
| Части контейнера | `zipfile.namelist()` даёт архивный порядок | `sorted(names)` |
| `leaked`/`residual` | множества | сортировка по `(artifact, part, kind, entity_type, ref, value)` перед упаковкой в кортеж |
| `page.search_for` | порядок прямоугольников на странице | не влияет: маркер один на группу, а порядок — как отдаёт PyMuPDF, стабильный для одного файла |
| `set` в `_detection_coverage` и рядом | уже обёрнуты `sorted` | не трогать |

Проверяется не рассуждением, а тестом: два прогона → побайтовое сравнение
`report.json` и сериализованного плана.

## Таксономия утечек — почему не «любая сущность = провал»

Буквальное «любая сущность запрошенного типа в выходном файле — провал»
даёт красный результат там, где всё правильно: человек ответил «оставить»
(`Action.KEEP`, `decisions.by_ref`), или Natasha приняла за организацию сам
вставленный маркер. Поэтому:

| Класс | Условие | Куда попадает |
|---|---|---|
| `raw` | точная исходная строка любой замены найдена побайтово в любой части контейнера | `leaked` |
| `metadata` | то же, но часть — `docProps/*`, `/Info`, XMP | `leaked` |
| `detector` (жёсткий) | детектор нашёл сущность, чей `group_key` совпал с ключом группы из плана | `leaked` |
| `detector` (мягкий) | найдена сущность запрошенного типа, которой в плане не было: решение `keep`, либо новая находка | `residual` |
| — | находка целиком лежит внутри вставленного маркера | отбрасывается |

Такой раскрой не ослабляет ворота: тест, который ломает Render и пропускает
одну замену, попадает и в `raw`, и в жёсткий `detector` — то есть в `leaked`
дважды и по двум независимым механизмам.

Побайтового поиска **недостаточно** самого по себе: Word режет значение по
run'ам (`ИНН 36` + `62103003`, см. `ingest/docx_ingest.py:16`), и в
`document.xml` исходная строка целиком не встретится. Поэтому третья
проверка — поиск по `DocPart.text`: для docx это текст, собранный
`ingest_docx` (он склеивает run'ы), для pdf — `page.get_text()`. Ищется и
точная строка, и её вариант со схлопнутыми пробелами.

## Что может пойти не так и чем это будет замечено

| Риск | Как проявится | Чем ловится |
|---|---|---|
| Маркер длиннее исходного значения ломает вёрстку таблиц реквизитов | колонки разъезжаются, `[ПОСТАВЩИК-ОРГАНИЗАЦИЯ]` не влезает в ячейку | `test_marker_longer_than_source_does_not_pad` + глазами на `make demo`; при неприемлемости — короткие метки типов, но **не** возврат к латинице |
| Снятие фильтра типов с детекции увеличивает число сущностей в отчёте и меняет метрики | `make eval` показывает другие P/R | фильтр в плане не меняет вход детектора, а `eval.py` зовёт `mask_document(types=list(EntityType))` — то есть уже считает по всем типам; расхождение обязано быть нулевым, проверяется прогоном `make eval` до и после шага 6 |
| Профиль есть, роли нет → маркеры вида `[СТОРОНА-3-ИНН]` в половине документа | нечитаемый результат на защите | `role_coverage` в `make eval` (порог 0.70) уже это меряет; новых порогов не вводим |
| Побайтовый поиск даёт ложную утечку на коротких значениях (дата, сумма), встречающихся в служебных частях (`app.xml`, `settings.xml`) | красный `leaked` на чистом прогоне | `test_clean_render_has_no_leaks` покажет это сразу; лечение — не ослабление правила, а исключение бинарных и заведомо служебных частей **поимённо**, с обоснованием в докстринге |
| Natasha принимает вставленный маркер за ORG | ложный `detector`-leak | отбрасывание находок внутри маркеров + `test_marker_recognised_as_org_is_ignored` |
| Полная и инициальная форма ФИО дают два маркера | `[ПОСТАВЩИК-ФИО-1]` и `-2` для одного человека | известное ограничение, зафиксировано тестом и строкой в `limitations` отчёта |
| Validate медленный: детектор гоняется второй раз по каждому артефакту | `make gate` заметно дольше | замерить время шага «тесты» до и после; если рост больше чем вдвое — Natasha в Validate отключается (`DetectAgent([RuleDetector(), AddressDetector()])`), потому что критичные типы ловятся правилами, а `org/person` дублируются текстовым поиском по значениям плана |
| Один `EntityIndex` в CLI и другой в `PlanAgent` дают разные `ref` | ссылки в `report.json` и в плане расходятся | индекс строится один раз и передаётся; тест `test_plan_refs_match_report_refs` |
