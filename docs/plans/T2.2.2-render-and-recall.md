# T2.2.2 — Вёрстка PDF и недобор рекалла: дефекты, вскрытые глазами заказчика

Продолжение `T2.2.1-pdf-defects.md` (шаги 1–12 реализованы в ветке
`fix/pdf-detect-render-defects`). Источник — просмотр
`out/kontrakt2/Договор № 2025.334807/masked_black.pdf` заказчиком.
Дефекты Д9–Д14. Всё, что ниже названо «проверено», проверено на машине на
артефакте того же прогона и на `fixtures/labeled/contract_pdf_02_school.pdf`.

Ветка та же: `fix/pdf-detect-render-defects` (в ней незакоммиченная работа
по T2.2.1). Отдельная ветка не заводится — предыдущий план ещё не закрыт
воротами, и Д10 отменяет часть его приёмки (шаг 9).

---

## Резюме в одном абзаце

Из четырёх содержательных дефектов три сводятся к двум корневым причинам.
Д10 (текст исчезает вне прямоугольника) — не ошибка смещений, а свойство
`apply_redactions`: прямоугольник, построенный из символьных боксов одной
строки, по вертикали залезает на соседнюю строку, и MuPDF удаляет её глифы
на всю ширину этого прямоугольника. Д12 (адрес «не замаскирован») по
текстовому слою **не воспроизводится** — зато на страницах 10/31/37 видны
обрубки `бласти, г. Екатеринбург` и `й адрес: 620091,`, то есть ровно
последствия Д10; диагностику Д12 надо повторить после Д10. Д11 (гимназия
не находится) — не про расширение спана вправо: Natasha **не отдаёт спана
вовсе**, расширять нечего, нужен словарный детектор по оргформе. Д13
подтверждён: 50 записей на один невычищенный `2025.334807` — счётчик врёт,
но и детектор действительно пропускает голое значение. Д9 — трёхстрочный
откат.

## Что проверено на машине

### Д10 — корневая причина: вертикальное перекрытие строк

Смещения и боксы верны, дефект целиком в геометрии прямоугольника.
Измерено на стр. 1 фикстуры:

```
строка A («Мокиной … Общество с»)   глифы y ∈ [110.81, 125.48]
строка B («Ограниченной … № 11»»)   глифы y ∈ [123.46, 138.13]
```

Строки перекрываются по вертикали на ~2 pt (шаг строк 12.7 pt при высоте
бокса глифа 15.2 pt — бокс включает выносные элементы). Прямоугольник
второй половины `org_name`, посчитанный сегодняшним `_entity_rects`, —
`Rect(42.55, 123.46, 366.5, 138.13)`. Проверено по одному прямоугольнику
за прогон:

```
Rect(42.5, 123.5, 366.5, 138.1)   стирает на строке A: «Мокиной … действующего на основании »
Rect(460.1, 123.5, 555.5, 138.1)  стирает на строке A: «роны, и Общество с»
Rect(42.5, 110.9, 223.2, 126.1)   (сама сущность) — стирает ровно себя, ничего лишнего
```

То есть удаляются символы соседней строки, попавшие в полосу перекрытия,
по всей ширине прямоугольника. `apply_redactions` удаляет глиф по
**пересечению** бокса с прямоугольником, а не по вложенности; порог
пересечения не документирован (замерено: перекрытие 1.3 pt из 12.2 —
удаляет, 0.27 pt — не удаляет), поэтому на него опираться нельзя.

Прототип лечения проверен: если прямоугольник по вертикали обрезать
серединой полосы перекрытия с соседней строкой, страница 1 восстанавливается
дословно — `, действующего на основании Устава, с одной стороны, и ` снова
на месте, все сущности удалены (`leaks == []`). В том же прототипе всплыл
и способ промахнуться: «своя» строка была вычислена сравнением координат,
для `Ивановны` она определилась неверно, прямоугольник схлопнулся в
высоту 0 и сущность **утекла**. Отсюда порядок шагов: сначала строка
приходит из ingest'а явным номером, потом обрезка, потом метрика, которая
ловит обе стороны — и потерю чужого текста, и недоудаление своего.

### Д11 — Natasha не отдаёт спана, расширять нечего

На реальной строке стр. 1 модель возвращает:

```
ORG 'Мокиной'
PER 'Светланы Владимировны'
ORG 'Общество с  Ограниченной Ответственностью'
PER 'Директора Зубрицкой'
PER 'Татьяны  Ивановны'
```

Спана на `Муниципальное автономное общеобразовательное учреждение
гимназия № 144` **нет ни одного**. Гипотеза постановки («оргформа без
кавычек, а расширение вправо ищет кавычку») описывает следствие: код
расширения к этой строке не вызывается вовсе. При этом словарь уже знает
форму: `has_organization_evidence("Муниципальное автономное … гимназия
№ 144") == True`, `is_public_body(...) == False`. Значит недостающее
звено — детектор по словарю оргформ, а не правка `expand_org_span`.

Проверено по всему документу: `гимназ` встречается 26 раз, и **каждое**
вхождение имеет слева либо полную форму, либо аббревиатуру `МАОУ`
(`МАОУ гимназия №144`, `МАОУ гимназии № 144`, `… учреждение гимназия
№ 144`). То есть словарного детектора с расширением вправо достаточно для
всех 26 — при условии, что `МАОУ` заведена в `abbreviations`.
Побочное: `shrink_span("… гимназия № 144")` сегодня срезает `№ 144` —
для словарного детектора срезать нельзя, номер входит в название.

### Д12 — по текстовому слою не воспроизводится

```
masked_black.pdf        : 'Банникова' 0 раз
masked_highlight.pdf    : 'Банникова' 0 раз
preview.pdf             : 'Банникова' 15 раз   (preview неразрушающий по замыслу)
```

`Г. Екатеринбург, ул. Банникова, 2` со стр. 15 есть в отчёте как
`address` с решением `mask` (сегмент 342), заглавная `Г.` детектору не
мешает — проверено отдельно на пяти вариантах написания, все находятся.
Зато в `masked_black.pdf` остались куски `бласти, г. Екатеринбург`,
`й адрес: 620091,` (стр. 10, 31, 37) — слова разрезаны посреди буквы,
это подпись Д10, а не детекции. **Вывод: наблюдение заказчика надо
уточнить после починки Д10.** Варианты — в разделе «Противоречие».

### Д13 — объяснение кодера верно, но чинить надо оба конца

В отчёте 124 записи `leaked`, из них 100 — `('raw', 'contract_number',
'2025.334807', 'page 45')`: одно уцелевшее вхождение × 50 `Replacement`
× 2 артефакта. `_search_values` перебирает `plan.replacements`, а не
уникальные значения, поэтому один физический дефект даёт 50 строк.
Дефект детекции при этом настоящий: правило `contract_number`
контекстное, а на стр. 45 значение стоит голым.

Тот же перебор показывает третий класс, которого в постановке нет:
`('raw','org_name','Администрации города','page 18')`,
`('raw','person','Мокина Светлана  Владимировна','page 45')` — значение
замаскировано в одном месте документа и осталось открытым в другом.
Лечится тем же средством, что и голый номер договора: сквозным досмотром
уже запланированных значений по всему документу.

### Д9 — метки действительно есть в текстовом слое чёрного файла

`masked_black.pdf`: `ОРГАНИЗАЦИЯ` 49, `ФИО` 31, `АДРЕС` 15, `БИК` 16.
`render_degradations` при этом длиной 1 — подтверждение, что метка на
чёрном рисуется как штатный результат стиля, а не как деградация.

### Д14 — фикс `--html` на PDF

Коммит `5ebe8c3` в ветке `fix/html-report-pdf-guard` не влит; в рабочем
дереве патч применён вручную. Отдельного шага нет, но **до сдачи ветку
надо влить или перенести коммит** — иначе `--html` на PDF снова упадёт
`KeyError: 'body'` у любого, кто возьмёт ветку.

## Противоречие, которое нельзя угадать: Д12

Заказчик видит незамаскированный адрес; текстовый слой обоих выходных
файлов адреса не содержит. Возможные объяснения не сводятся друг к другу:

- **Вариант A (рекомендуется).** Заказчик смотрел `preview.pdf` —
  неразрушающий артефакт, где исходный текст сохранён по замыслу
  (жёлтая подсветка). Тогда дефект не в детекции, а в том, что три
  файла лежат рядом и различаются только именем. Последствие: шага по
  адресам нет, вместо него — шаг «preview обязан объявлять себя
  необезличенным» (водяной знак/имя `preview_НЕ_ОБЕЗЛИЧЕН.pdf`).
- **Вариант B.** Заказчик смотрел `masked_black.pdf` и принял за
  «незамаскированный адрес» обрубки `бласти, г. Екатеринбург` и
  `й адрес: 620091,` — последствия Д10. Тогда шаг по адресам не нужен
  вовсе, дефект закрывается шагом 3.

Оба варианта не требуют трогать `detect/address.py`, поэтому шаг 8 в
плане — диагностический и условный: сначала повторить наблюдение на
свежем прогоне после шага 3, и только если адрес действительно остался в
`masked_*.pdf`, заводить правку детектора. Спросить у заказчика: **какой
из трёх файлов и какая страница**.

## Шаги

### Шаг 1. Чёрный прямоугольник — просто чёрный (Д9)

Файлы: `src/masker/render/pdf_render.py`, `tests/masker/render/test_pdf_render.py`,
`tests/masker/graph/test_render_node.py`.

- В `_insert_marker_ladder` для стиля `blackbox` не собирается ни одной
  ступени с текстом: прямоугольник закрашивается и всё.
  `_BEST_SHOWN_AS_BY_STYLE["blackbox"]` перестаёт существовать вместе с
  веткой; `blackbox` **никогда** не порождает `MarkerDegradation` —
  «без текста» для него не деградация, а замысел стиля.
- Лестница (полный маркер → короткая метка → без текста) остаётся
  целиком и без изменений для стиля `marker`.
- Докстринги модуля и `render_pdf_redacted` переписываются под новое
  решение заказчика, старое (пачка 5 плана T2.2.1) помечается отменённым
  со ссылкой на этот план — чтобы через месяц его не «починили» обратно.
- `tests/masker/graph/test_render_node.py::test_render_node_surfaces_pdf_marker_degradations`
  переводится на стиль `marker` (на `blackbox` деградаций больше не будет).

**Приёмка:**
- `render_pdf_redacted(..., style="blackbox")` возвращает `()` на
  фикстуре, где сегодня возвращает непустой кортеж;
- в текстовом слое `masked_black.pdf` полного прогона счётчики
  `ОРГАНИЗАЦИЯ`/`ФИО`/`АДРЕС`/`БИК` падают с 49/31/15/16 до числа
  естественных вхождений этих слов в исходном документе (проверяется
  сравнением с исходником, а не «на глаз»); строго ноль вставленного
  текста доказывается шагом 4;
- `report["render_degradations"]` для прогона со стилями
  `blackbox`+`marker` не содержит ни одной записи с
  `"role": "masked_black"`.

**Тесты (падают без шага):** `test_blackbox_inserts_no_text`,
`test_blackbox_never_reports_degradation`,
`test_marker_style_ladder_unchanged` (регрессия: лестница `marker` жива).

### Шаг 2. `page_chars` отдаёт номер строки каждому символу

Файлы: `src/masker/ingest/pdf_ingest.py`,
`tests/masker/ingest/test_pdf_ingest.py`, точка вызова в
`src/masker/render/pdf_render.py` (`_PageCharsCache`).

- `page_chars` возвращает `PageChars` — frozen dataclass с полями
  `text: str`, `boxes: tuple[Rect, ...]`, `line_ids: tuple[int, ...]`.
  Инвариант: длины всех трёх равны. Номер строки сквозной по странице,
  считается в том же единственном обходе `_walk_page`; символу-склейке
  (`Rect(0,0,0,0)`) присваивается номер строки, которую он закрывает.
- `ingest_pdf` не меняется по поведению; меняется только распаковка.
- Смена возвращаемого типа — публичный контракт модуля; потребителей
  ровно два, оба правятся здесь же.

**Приёмка:** на стр. 1 фикстуры все символы
`Мокиной Светланы Владимировны` имеют один и тот же `line_id`, а первый
символ `Ограниченной` — `line_id + 1`; `len(text) == len(boxes) ==
len(line_ids)`; два вызова подряд дают идентичный результат.

**Тесты:** `test_page_chars_line_ids_are_monotonic`,
`test_page_chars_line_id_changes_on_line_break`,
`test_page_chars_lengths_agree`. Без шага не компилируются — поля нет.

### Шаг 3. Прямоугольник редакции не залезает на соседнюю строку (Д10)

Файлы: `src/masker/render/pdf_render.py`,
`tests/masker/render/test_pdf_render.py`.

Правило (детерминированное, без подобранных порогов):

1. Прямоугольник строится, как сейчас, по срезу боксов, но **только из
   символов одной строки** — строка берётся из `line_ids`, а не
   угадывается по координате.
2. Полоса строки `L` = объединение боксов **всех** символов этой строки
   (не только символов сущности) — так полоса не зависит от того, какой
   кусок строки маскируется.
3. Для каждой другой строки `M` той же страницы, у которой пересекается
   с прямоугольником и горизонтальный, и вертикальный диапазон:
   - если `M` выше (`M.y_центр < L.y_центр`): `y0 = max(y0, (M.y1 + L.y0) / 2)`;
   - если ниже: `y1 = min(y1, (M.y0 + L.y1) / 2)`.
4. Если после обрезки `y1 - y0 <= 0` (строки перекрываются целиком —
   наложенный текст, штамп), обрезка для этого прямоугольника
   отменяется: берётся исходный прямоугольник, а факт записывается в
   `render_collisions` отчёта. Тихо оставлять текст нельзя — утечка
   дороже вёрстки; но и молчать об этом нельзя.
5. Порядок обхода строк — по `line_id`, а не по множеству.

Заливка (`fill`) и вставка текста работают по **обрезанному**
прямоугольнику: рисовать чёрное поверх соседней строки так же плохо, как
её стирать.

**Приёмка (машинная):**
- на стр. 1 фикстуры после применения всех замен страницы текстовый слой
  посимвольно (с схлопнутыми пробелами) равен «текст страницы минус
  символьные диапазоны замен» — сегодня расходится на 46 символов;
- ни одна из замаскированных строк стр. 1 не встречается в выводе
  (обрезка не должна недоудалять — именно так упал прототип на
  `Ивановны`);
- `grep -c "бласти, г. Екатеринбург" ` по тексту `masked_black.pdf` = 0
  (стр. 10, 31, 37).

**Приёмка глазами (обязательная, просил заказчик):**
- открыть `masked_black.pdf`, стр. 1: строка должна читаться как
  `<чёрный> , действующего на основании Устава, с одной стороны, и <чёрный>`
  — то есть между двумя чёрными полями стоит живой текст, а не пустота;
- `make demo` печатает строку вида
  `текстовый слой вне замен: 118 342 символа до, 118 342 после, потеряно 0`
  (метрика из шага 4) — цифра, которую человек сверяет за секунду;
- число страниц 46 до и после.

**Тесты (падают без шага):**
- `test_redaction_does_not_erase_neighbour_line` — синтетический PDF из
  двух строк с перекрывающимися боксами: после редакции первой строки
  вторая цела посимвольно;
- `test_redaction_still_removes_own_line` — та же фикстура: своя строка
  удалена (защита от переобрезки);
- `test_overlapping_lines_fall_back_and_report_collision` — две строки,
  наложенные друг на друга: обрезка отменена, текст удалён, коллизия
  попала в возвращаемое значение.

### Шаг 4. Метрика «текстовый слой вне замен сохранён»

Файлы: `src/masker/validate/pdf_layout.py` (новый),
`src/masker/validate/agent.py`, `tests/masker/validate/test_pdf_layout.py`.

- Функция `layout_diff(source_pdf, artifact_pdf, plan, *, markers)` →
  `LayoutDiff(expected_chars, actual_chars, removed, inserted, pages)`.
  Ожидаемый остаток = текст исходной страницы (`page_chars`) минус
  символьные диапазоны `Replacement` этой страницы; фактический = текст
  страницы артефакта, из которого удалены вхождения маркеров плана.
  Сравнение — по последовательности непробельных символов.
- Для `masked_black.pdf` после шага 1 вставленного текста нет вовсе,
  значит сравнение строгое и без вычитания маркеров — самый честный
  вариант проверки.
- `ValidationReport` получает поле `layout` (по артефакту:
  `removed_chars`, `inserted_chars`, список страниц с расхождением и
  первое расхождение текстом — чтобы дефект можно было открыть, а не
  гадать).

**Приёмка:** на сегодняшнем коде (до шага 3) метрика печатает
`removed_chars > 0` и называет стр. 1 — то есть она красная раньше, чем
дефект починен; после шага 3 — `removed_chars == 0` по обоим артефактам
на обеих PDF-фикстурах.

**Тесты:** `test_layout_diff_catches_collateral_removal` (искусственно
раздутый прямоугольник → `removed_chars > 0`),
`test_layout_diff_is_zero_on_clean_render`,

## Что может пойти не так и как это будет видно

| # | Риск | Как обнаружится |
|---|---|---|
| Р1 | Обрезка прямоугольника переусердствует, и своя сущность перестаёт удаляться — ровно так упал прототип на `Ивановны` | `leaked_total > 0` (шаг 4/5 меряет обе стороны: и потерю чужого текста, и недоудаление своего); `test_redaction_still_removes_own_line` |
| Р2 | Порог удаления глифа в MuPDF отличается на другой версии PyMuPDF, и «серединная» обрезка перестанет удалять | метрика шага 4 покажет `leaked`, а не тихо; версия PyMuPDF (1.28.2) фиксируется в `pyproject.toml`, поведение — тестом на синтетическом PDF, а не на фикстуре |
| Р3 | Обрезанная заливка визуально не закрывает выносные элементы своей строки (хвост `у`, `р`) | приёмка глазами на стр. 1; при появлении — рисовать заливку отдельным `draw_rect` по полной полосе строки **после** `apply_redactions` (текст уже удалён, инвариант «чёрное поверх живого текста» не нарушен) |
| Р4 | Сквозной досмотр тиражирует ложное срабатывание: `Мармит` или `ТР ТС` замаскируются во всех 40 вхождениях | precision по `person`/`org_name` в `make eval` падает; митигация — белый список типов и минимальная длина 6, но если precision уйдёт ниже 0.90, досмотр ограничивается критичными типами и `contract_number` |
| Р5 | Словарный детектор организаций съедает `гимназия № 144, в лице директора …` целиком | стоп-список и лимит 6 токенов; `test_org_form_stops_at_role_words`; precision по `org_name` |
| Р6 | `МАОУ` как аббревиатура ловит `МАОУ` в составе чужого текста без названия | `is_organization_form_only` отбрасывает; тест `test_org_form_without_name_is_dropped` уже есть в T2.2.1 |
| Р7 | Отмена метки на чёрном делает документ нечитаемым: одни чёрные поля без подсказки, что там было | это осознанное решение заказчика; читаемость обеспечивает `masked_highlight.pdf` со стилем `marker` и отчёт — записать в `ARCHITECTURE.md`, чтобы решение не выглядело случайным |
| Р8 | Смена типа возврата `page_chars` ломает потребителя, о котором забыли | потребителей два, оба в шаге 2; `mypy` в воротах ловит третьего |
| Р9 | `layout_diff` считает расхождением нормальную перестановку пробелов PyMuPDF | сравнение только по непробельным символам; тест `test_layout_diff_is_zero_on_clean_render` на нетронутом документе |

### Детерминизм

- Обрезка прямоугольника зависит от порядка обхода строк — порядок задан
  `line_id`, а не координатами и не множеством.
- Сквозной досмотр (шаг 8) — сортировка значений и вхождений задана явно;
  без неё два прогона дадут разные `ref` у одинаковых сущностей.
- `render_collisions` (шаг 3, п. 4) сортируется по `(page, line_id)`.
- `random` в плане не появляется.
