# План доведения triema-masker до демонстрации и пилота

База анализа: `9c2e18d` (merge PR #17, 2026-09-07). Это проектное решение
и очередь реализации, а не заявление о готовности перечисленных функций.
Рабочий язык интерфейса и отчётов: русский. Главные ограничения остаются
в AGENTS.md; этот документ не отменяет TASKS.md и предметные инварианты.

## 1. Продуктовый результат

Пользователь загружает договор, проверяет стороны и коммерческие условия,
настраивает скрываемые сведения, исправляет найденные маски и получает
читаемый документ исходного формата с настоящим удалением исходных данных.
Каждое поле карточки и каждая маска связаны с местом в оригинале.

Демонстрационная ценность: «вижу условия, проверяю источник, управляю
маскированием, получаю проверенный результат». Новые модели оцениваются
по корпусу, а не по размеру или новизне. Natasha и действующий граф остаются.

| Пользовательские типы и предварительный просмотр | `customtypes/`, REST `/custom_types` | Сохраняемые версии настроек и редактор на фронтенде |

PR #17 также улучшает фильтрацию организаций. Старые цифры precision из
предыдущего обсуждения нельзя выдавать за измерения этого коммита.

В `eval.py` появились исключения precision 0.50 для адресов и коммерческих
типов, recall адресов 0.80, порог role_accuracy 0.60 и лимит вопросов политики
13 вместо 10. Это изменения критериев, не доказательство улучшения качества.
Оценку прогресса вести на фиксированной разметке и явно показывать смену порогов.

В handoff одновременно написано «make gate = 0» и «leaked_total = 8».
Текущий код требует `MAX_LEAKED_TOTAL = 0`: эти утверждения требуют проверки.
Дедупликация повторных находок не устраняет саму утечку.

## 3. Почему маркеры сейчас выглядят плохо

### PDF: причины непосредственно в коде

Файл: `backend/src/masker/render/pdf_render.py`.

1. `_MARKER_FONT_SIZES` фиксирован: 10, 9, ... 2 pt. Исходный шрифт и его
   базовая линия не учитываются. Полный длинный маркер пробуется вплоть до
   2 pt раньше короткой подписи. Микроскопическая подпись считается успехом.
2. Подпись всегда ставится в первый прямоугольник многострочной сущности.
   Первая строка может содержать только инициалы или короткий обрывок.
3. Поле подписи получено из области удаления с произвольными поправками
   -1/+2 pt. Область удаления уже могла быть сужена ради соседней строки.
   Это не полноценный расчёт размещения текста и проверки соседних объектов.
4. Заливка стиля marker белая. Она стирает текст, но на белой странице
   почти не показывает протяжённость изменения. Короткая подпись занимает
   лишь часть прежнего имени: это само по себе не означает неполное удаление.
5. Короткий fallback содержит только тип, теряя номер/идентичность группы.
   После него возможна пустая область с записью деградации.

### DOCX: другая причина и другое решение

Файл: `backend/src/masker/render/docx_redact.py`.
`_build_marker` дописывает `(len(original) - len(marker)) * 2` пробелов.
Константа `_NBSP` фактически содержит обычный пробел. Количество символов
не равно ширине пропорционального шрифта; хвостовые пробелы не дают
надёжной заливки. Клонирование первого run также наследует его размер и
особенности, даже если он представляет лишь маленький фрагмент сущности.

PDF имеет фиксированные координаты. DOCX перевёрстывается приложением.
Один алгоритм «добавить пробелов / уменьшить шрифт» не решит обе задачи.

## 4. Предлагаемый контракт читаемой маски

Разделить три вещи: какие данные удалить, какую область подсветить,
какую подпись показать. Подпись не обязана растягиваться на ширину имени.

| Поле | Назначение |
|---|---|
| `group_id` | Стабильная идентичность сущности в ревизиях одного документа |
| `canonical_label` | Полная метка, например `[ПОСТАВЩИК-ФИО-1]` |
| `compact_label` | Однозначная короткая метка, например `ФИО_1` |
| `occurrence_id` | Конкретное вхождение, независимо от подписи |
| `erase_regions` | Все области настоящего удаления |
| `paint_regions` | Подсветка всех удалённых частей, отдельно от подписи |
| `label_region` | Проверенная область размещения подписи |
| `font_size`, `baseline`, `shown_label`, `fallback_reason` | Фактический результат рендера |

Это проект новых полей, а не текущий API. Изменение model.py проводить
с обновлением сериализации, всех потребителей и версии контрактов.
Соответствие короткой и полной меток включать в обезличенную легенду отчёта.
Номера не переназначать при удалении одной маски: допустимы пропуски номеров.

### Алгоритм PDF

1. До изменения страницы сохранить боксы, базовые линии, размеры, направление
   текста, границы страницы и доступные препятствия. Геометрия редактора
   учитывает CropBox, поворот и масштаб просмотра.
2. Построить области удаления по существующим anchors. Не расширять область
   удаления ради длинной подписи. Применить настоящее удаление.
3. Закрасить все удалённые фрагменты согласованным светлым фоном; для blackbox
   оставить непрозрачную чёрную заливку без текста, согласно текущему решению.
4. Для обычного текста начать с характерного размера исходной строки.
   Предлагаемая нижняя граница подписи: 8 pt, проверяемая на демонстрационном
   корпусе. Для исходного микротекста отмечать ограничение, не увеличивать
   шрифт поверх соседнего содержимого.
5. Сначала проверить полную метку при читаемом размере, затем компактную.
   Ширину считать метриками реально встраиваемого шрифта. По вертикали
   использовать ascender/descender и baseline. Для однострочной подписи
   рассмотреть `insert_text` после собственного расчёта, без автопереноса.
6. Среди удалённых фрагментов выбрать пригодное место по стабильному правилу:
   первая область, где подпись помещается при целевом размере, затем лучшая
   по допустимому размеру. Не обязательно первый короткий фрагмент.
7. Расширять только область подписи и только в доказанно свободное место
   той же строки/ячейки. Проверить соседний текст, линии таблицы, другие
   подписи, изображения и край страницы. Нет надёжной геометрии: не расширять.
8. Если даже короткая подпись не помещается, оставить подсветку с явным
   `needs_review` и ссылкой на запись в панели. Допустима размещённая в
   проверенном свободном месте выноска, но не обязательная для первой версии.
   Не считать пустую маску полноценным результатом читаемого режима.
9. После вставки повторно извлечь текст, проверить утечки, подпись и
   столкновения. Сохранить фактические параметры в отчёт рендера.

Пример: длинное ФИО занимало 130 pt. Вся область получает фон; `ФИО_1`
печатается обычным читаемым кеглем и не растягивается на 130 pt.
Смысл номера стабилен, а полноту покрытия показывает фон.

Для сканов текущий `PDF_REDACT_IMAGE_NONE` непригоден: изображение сохраняется.
Нужен отдельный режим удаления пикселей/пересборки обработанной страницы,
новый очищенный текстовый слой и проверка изображений, вложений и объектов.
Параметры обработки векторной графики задавать явно и проверять линии таблиц.

### Алгоритм DOCX и будущий XLSX

- DOCX: убрать символьный padding как способ сохранения ширины. Вставлять
  компактный маркер в run с контролируемым стилем и заливкой; учитывать
  наследуемые размеры, верхний/нижний индекс и смешанные run. Проверять
  переносы, таблицы, нумерацию и число структурных элементов.
- Не обещать пиксельное совпадение DOCX после замены текста разной длины.
  Сохранение структуры обязательно; одинаковую пагинацию принимать отдельно
  на выбранном движке просмотра. Для неизменной геометрии давать также PDF.
- XLSX: подпись и заливка ячейки без автоматического изменения ширины всех
  колонок. Формулы, объединённые ячейки и скрытые листы проверять отдельно.
  Ссылки формул на скрываемое значение могут снова раскрыть его: при конфликте
  сохранности формулы и удаления данных нужен явный статус и решение.

## 5. Фронтенд: что означает «редактировать маски»

Нужны два независимых действия: изменить конкретную маску документа и
изменить правило поиска для будущих документов. Интерфейс не смешивает их.

### Рабочий экран

Слева список сущностей с поиском и фильтрами по типу, стороне и статусу.
В центре документ, масштаб, страницы и переключение оригинал/результат.
Справа свойства выбранной маски или карточка договора с переходом к источнику.
На мобильном панели открываются по очереди. Все скачивания привязаны к ревизии.

Команды пользователя:

- Выделить текст и добавить маску; сервер проверяет совпадение текста с anchor.
- На скане выделить область; она удаляется независимо от успешности OCR.
- Исправить границы вхождения, тип, сторону и подпись.
- Применить изменение к одному вхождению или ко всей группе; перед массовым
  действием увидеть число затрагиваемых вхождений и их preview.
- Найти другие вхождения: показать кандидатов перед подтверждением.
- Объединить ошибочно разделённые сущности или разделить ошибочную группу.
- Удалить ручную маску / отменить действие; для критичных типов сохранить
  существующее двойное подтверждение раскрытия.
- Добавить пользовательский тип описанием, проверить preview, сохранить
  версию настройки и отдельно применить её к текущему документу.

Метка не является идентификатором. Переименование `ФИО_1` не меняет anchors.
Произвольная подпись проверяется на пустоту, длину, управляющие символы,
конфликт с другой группой и возврат исходного скрываемого значения.
HTML-отчёт экранирует подписи. Правки не обучают модель автоматически.

### Хранение и граф

Оригинал неизменяем. Правки хранятся как события с автором, ревизией и
ссылками на группы/вхождения. `expected_revision` предотвращает потерю
изменений из второй вкладки; повтор команды использует idempotency key.

Предлагаемый маршрут: extract -> detect -> profile -> judge/policy ->
review (interrupt) -> apply_edits -> plan -> summary -> render -> validate -> report.
Обязательная пауза редактора существует и при отсутствии вопросов судьи.
После завершения прогона новая правка создаёт новую ревизию и производный
прогон; нельзя просто resume уже законченного треда с произвольным payload.

Обновление рендера всегда идёт из оригинала и эффективного плана. Изменения
стиля не требуют повторного NER. Изменение правил требует новой детекции с
явным переносом/конфликтами ручных правок. Не редактировать экспортированный
PDF последовательно: это теряет якоря и накапливает ошибки.

Ключ артефакта включает хэш оригинала, ревизию плана, версии типов,
профиль отображения, версию рендера и проверки. Сейчас styles не входят
в `RunOptions.canonical()`: существующий thread_id нельзя использовать как
единственный ключ кеша экспортов. Разделить идентичность анализа и экспорта.

### Предлагаемые операции API (ещё не реализованы)

| Операция | Контракт |
|---|---|
| Запуск анализа | file_id, выбранные типы, версии настроек; job_id |
| Чтение состояния | стадия, ревизия, покрытие, вопросы, доступные действия |
| Чтение страницы/сегментов | стабильные anchors и геометрия из backend |
| Пакет правок | expected_revision, idempotency_key, типизированные команды |
| Создание экспорта | ревизия, формат, стиль; отдельный статус проверки |
| Получение артефакта | проверка владельца, ревизии и разрешённого состояния |

Повторно использовать auth, files, custom_types и run.py. Тяжёлый рендер
выполнять фоновой задачей с ограничением параллелизма. Ошибка/перезапуск
воркера не теряет подтверждённые правки. Не возвращать абсолютные серверные
пути и не позволять скачивание чужих файлов по известному job_id.

## 6. Довести карточку договора до проверяемых фактов

Сейчас сумма выбирается первой найденной сущностью, условия оплаты
склеиваются через `;`, стороны берутся из первого подходящего профиля.
`ContractSummary` не содержит anchors или состояния конфликтов.
Контекст суммы может включать соседние сегменты: рядом с ценой договора
могут оказаться НДС, аванс, обеспечение и штраф. Нужна проверка на корпусе.

Ввести представление факта: значение, исходная цитата, список anchors,
источник, статус `found/ambiguous/not_found/confirmed`, альтернативы.
`not_found` означает «не обнаружено», а не доказанное отсутствие условия.
Упоминание ФЗ не равно доказанному режиму закупки; хранить эти понятия отдельно.

Для оплаты: этапы, процент/сумма, событие отсчёта, число и вид дней.
Для поставки: объект/партия, событие отсчёта, срок, календарные/рабочие дни.
Для суммы: валюта, НДС, назначение суммы, альтернативы и выбранный источник.
Правила дают кандидатов; модель через LLMProvider помогает на неоднозначном.
Её результат принимается только с проверяемыми ссылками на оригинал.

Внутренняя карточка содержит исходные данные. Экспортируемая обезличенная
карточка и отчёт применяют ту же политику, включая ручные маски. JSON,
HTML, легенда и логи не должны незаметно возвращать скрытые значения.

## 7. Приоритетная очередь с критериями приёмки

Оценки предварительные, в человеко-днях, включая тесты и review.
Каждый блок разбить на короткие задачи с фикстурами до реализации.

| ID | Работа и зона изменений | Приёмка | Оценка |
|---|---|---|---|
| Q1 | `eval.py`, fixtures: разбор находок, полнота разметки, метрики вхождений и чистоты профилей | Реальные пропуски не исчезают от дедупликации; смешанный профиль роняет тест; новые типы размечены | 1-2 |
| R1 | `pdf_ingest.py`, `pdf_render.py`, отчёт: отдельное размещение подписей | Нет скрытой деградации до 2 pt; стабильные короткие метки; нет повреждения соседей | 2-3 |
| R2 | `docx_redact.py`: padding и наследование стиля | Нет искусственных хвостов; маркер читается в смешанных run и таблицах | 1-2 |
| V1 | `validate/`, graph: конфигурация типов, остатки, покрытие | Новое неразрешённое вхождение запрошенного типа блокирует успешный экспорт; явный KEEP не блокирует | 2-3 |
| E1 | model/state/run: группы, команды правок и ревизии | Добавление, изменение, undo, конфликт вкладок и повтор запроса проверены; export из оригинала | 2-4 |
| W1 | API и frontend: полный рабочий экран | Анализ, правки, вопросы, preview, скачивание проходят без CLI; сервер валидирует правки | 3-5 |
| C1 | summary и contract_params: факты с источниками | Сумма/НДС/аванс различаются; оплата и поставка сохраняют события отсчёта; альтернативы видны | 2-4 |
| F1 | DOCX coverage, ingest/render/validate | Колонтитулы, вложенные таблицы и другие поддержанные части проходят проверку; неподдержанные явно блокируют полноту | 2-4 |
| F2 | XLSX ingest/render/validate | Таблицы и формулы проверены; скрытые части не обходят политику | 2-4 |
| O1 | OCR и обработка изображений | Скан и смешанный PDF: удалены пиксели и исходный OCR-текст; результат читаем и проверен | 3-5 |
| D1 | Корпус и сценарий защиты | Живой сквозной прогон, замеры качества/времени, настоящий GigaChat и второй провайдер | 1-2 |

Порядок зависимостей: Q1 -> R1/R2/V1 -> E1 -> W1; C1 использует Q1 и
подключается в W1. F1/F2/O1 закрывают заявленный охват форматов до приёмки.
Пакетное сравнение и поиск противоречий добавлять после C1; общий чат и
дообучение модели не входят в обязательный объём первой демонстрации.

## 8. Матрица проверки рендера и редактора

- Короткое/длинное ФИО, инициалы, два одинаковых имени, несколько сторон.
- Исходные размеры 7/9/12/18 pt, узкие ячейки, плотные и многострочные записи.
- Повороты страниц и текста, CropBox, масштаб 50/100/200%, границы страницы.
- DOCX: три run на одну сущность, разные размеры, стили, таблицы, переносы.
- PDF: одна подпись на вхождение, фон на всех его частях; две соседние маски.
- Ручная область скана, смешанная страница, OCR-ошибка в одной цифре ИНН.
- После сохранения: исходные значения отсутствуют в извлекаемом тексте,
  контейнере, метаданных и изображениях в пределах заявленного покрытия.
- Визуальные проверки растеризованных страниц: видимость, размер текста,
  покрытие фоном, отсутствие наложений; текстовые тесты не заменяют их.
- Preview и скачанный артефакт показывают одну ревизию. Устаревший результат
  не выдаётся за текущий, правки переживают обновление страницы и рестарт.
- Попытка раскрыть критичный тип, чужой file_id, устаревшая ревизия,
  повтор команды и недопустимая подпись имеют проверяемый результат.

Предлагаемые продуктовые цели: ноль подтверждённых утечек и повреждений
структуры; recall критичных типов 1.0 на отложенном корпусе; полные ссылки
на источники заполненных фактов; отсутствие масок мельче согласованного
минимума без `needs_review`. Время анализа измерять отдельно от времени
применения правок, на зафиксированном оборудовании и документах.

## 9. Демонстрация

Договор -> карточка со ссылкой на пункт -> исправление стороны -> ручная
маска пропущенного фрагмента -> правило «сроки поставки» с preview ->
читаемый `ФИО_1` в таблице -> скачанный DOCX/PDF -> результат проверки.
Второй пример показывает скан. Финальный экран: реальные метрики и
ограничения, а не обещание стопроцентного распознавания любых документов.

## 10. Источники решения

Документация PyMuPDF проверена через Context7 по `/pymupdf/pymupdf`.

- [PyMuPDF: Page](https://pymupdf.readthedocs.io/en/latest/page.html):
  `apply_redactions`, отдельная обработка текста, изображений и графики.
- [PyMuPDF: Shape](https://pymupdf.readthedocs.io/en/latest/shape.html):
  `insert_textbox`, переносы и отрицательный результат при нехватке высоты.
- [PyMuPDF: TextPage](https://pymupdf.readthedocs.io/en/latest/textpage.html):
  `origin`, `size`, `ascender`, `descender` для геометрии текста.

Указанные размеры, политика fallback, события правок и очередь задач являются
нашими проектными решениями. Библиотечная документация не гарантирует
качество конкретного рендера: его принимаем по матрице выше.
