### 0.1 К3 и И3 — блокировки

**И3 заблокирована по-настоящему.** `src/api/routers/` содержит `auth.py`,
`custom_types.py`, `files.py`, `users.py` — роутера прогонов нет вовсе.
`masker.run.start_run/resume_run` из API не вызывается. И3 требует
«предпросмотр находок на текущем документе» и «применение к прогону», то
есть объект «прогон» по HTTP. Его нет → В1 → В3 → И3. В план не берём.

**К3 заблокирована только формально.** В `backend/Makefile` цели `bench`
нет, но приёмка К3 («`make bench` печатает таблицу; цифры в README») не
содержит ни одного пункта, требующего HTTP: время обработки, `leaked_total`,
recall, память меряются на CLI-пути (`masker.cli`, `masker.eval`), который
работает сегодня. Зависимость `В1` в TASKS.md — редакционная, а не
техническая. Решение: **в волны не берём** (так просил оркестратор), но
фиксируем: если В1 не будет сделан к защите, К3 можно закрыть на CLI без
единой правки в `src/api/`. Это отдельное решение, а не часть этого плана.

### 0.2 Р9 → Р7: зависимость подтверждена частично, и это важно

Корень дефекта Р9 найден и локализован **однозначно**. Natasha отдаёт
верный спан, портит его наша пост-обработка:

```
сегмент 2, holdout_02_lease.docx:
  'Гражданин Российской Федерации Соловьёв Николай Петрович, ...'
  natasha: LOC(10,30)='Российской Федерации'  PER(31,56)='Соловьёв Николай Петрович'
  detect.persons.expand_person_left(text, 31, 56) -> (21, 56) = 'Федерации Соловьёв Николай Петрович'
```

`expand_person_left` принимает любой соседний слева токен с заглавной
кириллической буквы, если он не ролевое слово, не оргформа и не уличный
маркер. «Федерации» не подпадает ни под один запрет.

Проверенное лечение (прототип прогонялся, код не коммитился): расширяться
влево только если у токена **хотя бы один** морфоразбор OpenCorpora несёт
`Surn`/`Name`/`Patr`. Замер по всему корпусу (`fixtures/labeled/*.docx`,
`fixtures/holdout/*.docx`, `fixtures/negative/*.docx`, `fixtures/labeled/*.pdf`):

```
изменился ровно ОДИН спан на весь корпус:
  - (2, 21, 56, 'Федерации Соловьёв Николай Петрович')
  + (2, 31, 56, 'Соловьёв Николай Петрович')
```

Ни один другой person-спан не поехал; на PDF-корпусе изменений нет.
Ключевая проверка: разбор по ПЕРВОМУ варианту (как в `morph._classify_word`)
не годится — «Мокиной» и «Зубрицкой» первым разбором не Surn, и нужные
расширения сломались бы. Нужен **любой** разбор, как уже сделано в
`verifier._any_name_grammeme`.

**А теперь то, чего в TASKS.md нет.** Утверждение «`r_filter` на holdout
0.0 вызван дефектом границ спана» верно только для `holdout_02`. Замер
`measure_filter_coverage` по трём holdout-документам:

| документ | до Р9 | после Р9 |
|---|---|---|
| holdout_01_supply | missed=1, covered=0 → r_filter 0.0 | missed=1, covered=0 → **0.0** |
| holdout_02_lease | missed=1, covered=0 → r_filter 0.0 | missed=0 → r_filter **не определён** |
| holdout_03_transport | missed=0 | missed=0 |

То есть Р9 убирает *фантомный* пропуск на `holdout_02`, но не даёт
`r_filter > 0`: после него на holdout **нечего восстанавливать**.
Оставшийся пропуск на `holdout_01` — другой дефект того же класса:

```
gold : 'Государственное бюджетное учреждение здравоохранения «Городская клиническая больница № 15»'
base : '«Городская клиническая больница № 15»'   (ner, 0.8)
build_windows(...) на этом документе вернул 0 окон
```

`expand_org_span` тянет влево только формы из `detect/data/org_forms.yaml`,
а «Государственное бюджетное учреждение здравоохранения» там нет. Спан
обрезан слева, слабый сигнал в сегменте целиком покрыт принятыми
сущностями → окон нет → фильтр не показывает модели ничего.

**Вывод для плана.** Р9 действительно идёт первой, но состоит из двух
независимых дефектов (PERSON слева, ORG слева), и после обоих
приёмка Р7 «на holdout верификатор находит пропущенную сущность»
становится **невыполнимой по построению** — см. противоречие в §4.

### 0.3 Р7 — что физически отсутствует в коде

- `graph/nodes.py::make_detect_node` создаёт `DetectAgent(detectors, registry)`
  **без** `llm=` → верификатор в графе не включается никогда, ни при каком
  `MASKER_LLM`. Слой существует только для прямых вызовов из тестов.
- `DetectionResult` (`detect/result.py`) содержит только `entities` и
  `chunks`; `verify_recall` возвращает `verdicts`, и `DetectAgent` их
  **выбрасывает**. Проводить в `report.json` сейчас нечего — сначала нужен
  канал наружу.
- `LLMProvider.complete(messages)` не принимает схему ответа → `strict: true`
  для GigaChat некуда положить без правки контракта провайдера.

### 0.4 И2 — метрика меряет не то, что написано в задаче

`eval._profile_judge_metrics` вызывает `ProfileAgent()` **без LLM**. Значит
`role_accuracy` сегодня и всегда — метрика чистой эвристики; любая работа

### М6-1 · Геометрия подписи считается ПОСЛЕ `apply_redactions`

Закрывает пункт 1 приёмки М6 (единственное видимое глазом наложение
12.18 pt) и снимает причину, по которой метрика меряет не то, что нарисовано.

**Владеет файлами**
- `src/masker/render/pdf_render.py`
- `tests/masker/render/test_pdf_render.py`

**Что сделать.** Двухпроходный рендер: проход 1 — считаем `erase_regions`
и выполняем `apply_redactions()`; проход 2 — по **уже отредактированной**
странице читаем символьные боксы и строим `label_box`/вставляем текст.
Сопоставление кандидатов между проходами — **по геометрии
`erase_rect` на странице, а не по `line_id`**: именно перенумерация
`line_id` (71→75 строк) завалила прошлую попытку. `erase_rect` в
координатах страницы редактирование не двигает, поэтому ключ
`(page, round(x0,2), round(y0,2))` устойчив.
`compute_label_geometry` обязана повторить ровно тот же путь (открыть копию
исходника в памяти, применить редактирование, потом считать) — иначе
`count_highlight_overlaps` и сертификат начнут мерить геометрию, которой
на бумаге нет.

**Приёмка**
1. `count_highlight_overlaps` на `contract_pdf_02_school.pdf` больше не
   содержит наложения ≥ 5 pt: приложить раскладку по величине (было
   `<1pt ~267 / 1–5pt ~47 / 12.18pt 1`).
2. Геометрия удаления не изменилась: `compute_erase_geometry(source, plan)`
   до и после правки совпадает **побайтово** (сравнение сериализованного
   json-дампа регионов; тест-эталон положить рядом с тестом).
3. `leaked_total = 0` и `certificate_failures = 0` на школьном PDF

4. Раскладка `fallback_reason` по группам не ухудшилась: `blank ≤ 3`.

### К4-1 · Растровая проверка: дифференциальный тест без эталона в репозитории

**Что сделать.** Модуль: `render_page_png(pdf, page, dpi) -> bytes`,
`phash(png) -> int`, `diff_ratio(a, b) -> float`. Рендер жёстко

без системных шрифтов (шрифт маркера уже лежит в репозитории).

   подписи на строку вниз.
3. Два прогона подряд дают побайтово одинаковый PNG (детерминизм рендера)
   — отдельный ассерт.
4. Версия PyMuPDF, `dpi` и порог различия записаны константами в модуле с

### И2-3 · GigaChat только там, где эвристика не сошлась (+ детерминизм ворот)

**Владеет файлами**
- `src/masker/profile/prompt.py`, `src/masker/profile/agent.py`

- `tests/masker/profile/test_role_llm.py`, `tests/masker/llm/test_cassette.py`

**Проблема, которую шаг обязан решить.** `eval` вызывает `ProfileAgent()`
без LLM (факт §0.4). Значит либо ворота никогда не увидят вклад модели,
либо в ворота попадёт сеть — и метрики станут невоспроизводимыми.
Решение: провайдер-кассета. `CassetteProvider` отвечает записанным ответом
по ключу `sha256(messages)`; ключа нет → `LLMError`, а не тихий фолбэк.
Запись кассеты — ручная операция с живым GigaChat, отдельным коммитом.
`make eval` идёт через кассету → воспроизводимо и офлайн; живой GigaChat
живёт только в `@pytest.mark.e2e`.

**Что сделать в самом сценарии.** Роль запрашивается у модели одним
запросом на документ и **только** для профилей, у которых после И2-1/И2-2
роли нет либо уверенность ниже порога. Ответ ниже порога уверенности →
роль не назначается, маркер вырождается в `СТОРОНА-N` (уже поддержано
`compose_marker` и `cluster.marker_label`).

**Приёмка**
1. `MASKER_LLM=fake` — пайплайн проходит целиком, роли берутся из
   эвристики, `role_accuracy` не ниже, чем в И2-2.
2. `MASKER_LLM=cassette` — два прогона подряд дают побайтово одинаковый
   `report.json` (детерминизм).
3. Профиль с неуверенной ролью получает `СТОРОНА-N`, а не выдуманную роль —
   отдельный тест.
4. E2E-тест `@pytest.mark.e2e` на живом GigaChat: провайдер меняется,
   поведение графа — нет.
5. Отсутствующий ключ в кассете даёт `LLMError` с внятным текстом; тест на
   это есть.

**Узкая проверка**
```
.venv/bin/python -m pytest -q tests/masker/llm/test_cassette.py tests/masker/profile/
.venv/bin/python -m pytest -q -m e2e tests/masker/profile/test_role_llm.py   # только вручную, с ключом
```
